🎯 Principes clés de sécurité

🚫 Deny by Default

Tout est interdit sauf ce qui est explicitement autorisé.

🔑 Least Privilege

Permissions minimales nécessaires pour accomplir la tâche.

🛡️ Defense in Depth

Plusieurs couches de sécurité indépendantes.

⛔ Fail Secure

En cas d'erreur, refuser l'accès plutôt que l'accorder.

🔍 Never Trust User Input

Valider et échapper TOUTES les données utilisateur.

📋 Keep It Simple

Code simple = plus facile à auditer et moins de bugs.

✅ Validation des entrées

Whitelist vs Blacklist

❌ Blacklist
  • Bloquer "<script>"
  • Bloquer "DELETE"
  • Problème: Contournements faciles
✅ Whitelist
  • Accepter seulement [a-zA-Z0-9]
  • Formats RFC validés
  • Avantage: Contrôle total

Exemple : Validation de nom d'utilisateur

❌ Mauvaise approche
// Accepter tout sauf les < et > function validateUsername($input) { return str_replace(['<', '>'], '', $input); } // Attaquant : "admin<img src=x>" // Résultat : "adminimg src=x" ☠️
✅ Bonne approche
// Accepter UNIQUEMENT autorisé function validateUsername($input) { if (!preg_match('/^[a-zA-Z0-9_-]{3,20}$/', $input)) { throw new ValidationException("Invalid"); } return $input; } // Attaquant : "admin<img src=x>" // Résultat : Exception levée ✓

Checklist de validation

  • Type : Vérifier le type de donnée
  • Format : Pattern attendu ?
  • Longueur : Entre min et max ?
  • Valeur : Dans la plage ?
  • Whitelist : Seulement les valeurs autorisées
  • Rejeter plutôt que nettoyer : Zéro tolérance

Exemple 1 : Configuration d'API Key

❌ Hardcodé
// ❌ JAMAIS ! class ApiClient { private const string API_KEY = "sk-1234567890abcdef"; // Commit = compromission ☠️ }
✅ Depuis configuration
// ✅ Sécurisé class ApiClient { private readonly IConfiguration _config; public ApiClient(IConfiguration config) { _config = config; } string apiKey = _config["ApiKeys:Service"]; }

🔐 Authentification et gestion de session

Hachage des mots de passe

❌ En clair
// ❌ JAMAIS string password = "MyPassword123"; db.Users.Add(new User { Password = password // ☠️ });
✅ Bcrypt sécurisé
// ✅ Bcrypt - Lent par design using BCrypt.Net; string hash = BCrypt.HashPassword( password, workFactor: 12); // ~250ms db.Users.Add(new User { PasswordHash = hash });

Sécurisation des cookies

  • HttpOnly = true (Pas accessible via JS)
  • Secure = true (HTTPS uniquement)
  • SameSite = Strict (CSRF protection)
  • Expiration courte (15-30 min)
  • Regenerate ID après login

🔓 Autorisation et contrôle d'accès

Différence clé :

  • Authentification = "Qui êtes-vous ?" (login)
  • Autorisation = "Avez-vous le droit ?" (permissions)

Implémentation sécurisée

❌ Vérification manquante
// ❌ Aucune vérification [HttpDelete("users/{id}")] public IActionResult DeleteUser(int id) { var user = db.Users.Find(id); db.Users.Remove(user); db.SaveChanges(); return Ok(); } // N'importe qui peut supprimer !
✅ Vérification présente
// ✅ Sécurisé [HttpDelete("users/{id}")] [Authorize(Roles = "Admin")] public IActionResult DeleteUser(int id) { var current = GetCurrentUser(); if (!current.HasPermission("users.delete")) { return Forbid(); } var target = db.Users.Find(id); db.Users.Remove(target); db.SaveChanges(); return Ok(); }

⚠️ Gestion d'erreurs sécurisée

Exemple : Gestion d'erreurs sécurisée

❌ Trop détaillée
try { var user = db.Users.Single(u => u.Id == userId); } catch (Exception ex) { // ❌ Expose tout return BadRequest(new { error = ex.Message, stackTrace = ex.StackTrace }); }
✅ Sécurisée
try { var user = db.Users.Single(u => u.Id == userId); } catch (Exception ex) { // ✅ Log serveur _logger.LogError(ex, "Error fetching user"); // ✅ Réponse générique return StatusCode(500, "An error occurred"); }

Erreurs à éviter

  • ⚠️ Exposer la structure BD
  • ⚠️ Révéler chemins de fichiers
  • ⚠️ Énumération d'utilisateurs
  • ⚠️ Timing attacks

Exemple : Logging d'authentification

❌ Dangereux
try { var user = Authenticate(username, password); // ❌ JAMAIS logger le mot de passe _logger.LogInformation( $"Login: {username}/{password}"); } catch { _logger.LogError("Login failed"); }
✅ Sécurisé
try { var user = Authenticate(username, password); _logger.LogInformation( "Login OK: User={User}, IP={IP}", username, remoteIpAddress); } catch { _logger.LogWarning( "Failed login: User={User}, Attempts={Count}", username, loginAttempts); }

📦 Gestion des dépendances

60-80% des vulnérabilités viennent des dépendances, pas du code propriétaire.

Stratégie de gestion

🛡️ Processus de sécurisation

  1. Audit initial : Vérifier toutes les dépendances
    npm audit
composer audit
dotnet list package --vulnerable
  2. Correction : Update immédiat des CVE critiques
  3. CI/CD scanning : Bloquer les builds avec CVE
  4. Maintenance : Updates mensuelles minimum
  5. Monitoring : Alertes sur nouveaux CVE

Outils recommandés

Langage Natif Avancé
Node.js npm audit Snyk, Dependabot
.NET dotnet list package --vulnerable Snyk, Safety
PHP composer audit Snyk, Trivy

Bonnes pratiques

✅ À faire
  • Versions fixées (1.2.3)
  • Lock files en Git
  • Updates automatiques
  • Tests après update
  • Auditer indirectes
  • Supprimer inutiles
❌ À éviter
  • Wildcards (*)
  • Ignorer warnings
  • Jamais updater
  • Pas de tests
  • Sources inconnues
  • Code copié-collé

Zero Trust Architecture

"Never trust, always verify"

Principes :

  • Chaque requête = authentification
  • Vérifier à chaque accès
  • Segmentation granulaire
  • Logging et monitoring continu

✅ Checklist finale de sécurité

Avant chaque déploiement en production

🔐 Code

  • ✓ SAST : 0 vulnérabilité CRITIQUE
  • ✓ SCA : Dépendances à jour
  • ✓ Secrets : Aucun commité
  • ✓ Code review : 2+ approbations
  • ✓ Tests : Couverture >= 80%

🔑 Secrets & Données

  • ✓ Configuration depuis vault
  • ✓ Mots de passe chiffrés
  • ✓ Clés en variables d'env
  • ✓ DB credentials sécurisés
  • ✓ Pas de secrets en logs

✅ Entrées & Validation

  • ✓ Whitelists en place
  • ✓ Validation de taille
  • ✓ Validation de format
  • ✓ Prepared statements
  • ✓ Escaping des sorties

🔐 Authentification & Autorisation

  • ✓ HTTPS/TLS 1.2+ activé
  • ✓ Cookies sécurisés
  • ✓ MFA pour comptes sensibles
  • ✓ Vérifications d'autorisation
  • ✓ Audit trail complet

⚠️ Gestion d'erreurs & Logging

  • ✓ Pas de stack traces en prod
  • ✓ Messages génériques
  • ✓ Logging de sécurité actif
  • ✓ Alertes configurées
  • ✓ Rétention >= 1 an

Points critiques : Zéro tolérance

  • ⚠️ Secrets commités en Git
  • ⚠️ Mots de passe en clair
  • ⚠️ SQL Injection possible
  • ⚠️ XSS non protégé
  • ⚠️ CSRF tokens manquants
  • ⚠️ HTTP au lieu de HTTPS
  • ⚠️ Dépendances obsolètes avec CVE
  • ⚠️ Pas de MFA pour admins
