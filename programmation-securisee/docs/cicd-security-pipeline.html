Pipeline CI/CD Securise — DevSecOps

Integrer la cybersecurite dans chaque etape du pipeline de developpement

1. Introduction — Pourquoi DevSecOps ?

Le modele traditionnel de developpement logiciel separait strictement les equipes : les developpeurs ecrivaient le code, les equipes operations le deployaient, et la securite intervenait en fin de cycle — souvent trop tard pour corriger les problemes de maniere efficace et economique.

Modele traditionnel (Dev + Ops)

Developpeurs          Securite         Operations
     |                   |                  |
     |  Code termine     |                  |
     |-------------------+---> Audit ------>|
     |                   |  (trop tard!)    |
     |   Corrections     |                  |
     |<------------------+                  |
     |   (couteuses)     |                  |

La securite est un goulot d'etranglement en fin de cycle. Les corrections sont couteuses et retardent la livraison.

DevSecOps (Securite integree)

  Dev + Sec + Ops = Une seule equipe
         |
    +---------+
    | Commit  | --> Scan secrets
    +---------+     Lint securite
         |
    +---------+
    | Build   | --> SAST, SCA
    +---------+     Image scan
         |
    +---------+
    | Test    | --> DAST, Fuzzing
    +---------+     Pentest auto
         |
    +---------+
    | Deploy  | --> Security Gate
    +---------+     SBOM, Signing

La securite est automatisee et presente a chaque etape.

Shift Left Security

Le concept de "Shift Left" consiste a deplacer les controles de securite le plus tot possible dans le cycle de developpement. Plus une vulnerabilite est detectee tot, moins elle coute a corriger.

Cout de correction d'un bug selon la phase de detection :
Design
1x
Developpement
6.5x
Tests
15x
Production
100x

Source : IBM Systems Sciences Institute — Un bug detecte en production coute jusqu'a 100 fois plus a corriger que s'il avait ete detecte en phase de conception.

La boucle infinie DevSecOps

                    +-----------+
               +--->|   PLAN    |---+
               |    +-----------+   |
               |                    v
        +-----------+         +-----------+
        |  MONITOR  |         |   CODE    |
        +-----------+         +-----------+
               ^                    |
               |                    v
        +-----------+         +-----------+
        |  OPERATE  |         |   BUILD   |
        +-----------+         +-----------+
               ^                    |
               |                    v
        +-----------+         +-----------+
        |  DEPLOY   |<--------|   TEST    |
        +-----------+         +-----------+

        |<--- Ops ------->|<--- Dev ------->|
        |<---------- Sec (partout) -------->|

           ===  CONTINUOUS FEEDBACK  ===

Statistiques cles

84% des codebases contiennent au moins une vulnerabilite connue
158j temps moyen pour corriger une CVE critique
80-90% du code est compose de dependances open source
100x cout de correction en production vs conception

2. Pipeline CI/CD : Classique vs Securise

Pipeline classique (sans securite)

  +--------+     +--------+     +--------+     +--------+
  |  CODE  |---->| BUILD  |---->|  TEST  |---->| DEPLOY |
  +--------+     +--------+     +--------+     +--------+

  Aucune verification de securite automatisee.
  Les vulnerabilites passent directement en production.
Problemes : Pas de scan de secrets, pas d'analyse de vulnerabilites, pas de verification des dependances, pas de gate de securite avant le deploiement.

Pipeline securise (DevSecOps)

+=====================================================================+
|                    PIPELINE DevSecOps COMPLET                        |
+=====================================================================+
|                                                                     |
|  COMMIT              BUILD               TEST              DEPLOY   |
|    |                   |                   |                  |     |
|    v                   v                   v                  v     |
| +----------+     +----------+        +----------+      +----------+|
| | Secret   |     | SAST     |        | DAST     |      | Security ||
| | Scan     |     | (code)   |        | (runtime)|      | Gate     ||
| |----------|     |----------|        |----------|      |----------||
| | Lint     |     | SCA      |        | Pentest  |      | Artifact ||
| | securite |     | (deps)   |        | auto     |      | Sign     ||
| |----------|     |----------|        |----------|      |----------||
| | Pre-     |     | License  |        | Fuzzing  |      | SBOM     ||
| | commit   |     | Check    |        |          |      | Generate ||
| | hooks    |     |----------|        | API      |      |----------||
| |          |     | Image    |        | Security |      | Deploy   ||
| |          |     | Scan     |        | Test     |      | Canary   ||
| +----------+     +----------+        +----------+      +----------+|
|                                                                     |
|  <======== FEEDBACK CONTINU (Notifications, Dashboards) ========>  |

+=====================================================================+
Chaque etape du pipeline integre des controles de securite automatises. Le feedback est continu : les developpeurs sont alertes immediatement en cas de probleme.

Comparaison detaillee

Aspect Pipeline classique Pipeline DevSecOps

Analyse du code Lint basique SAST + Lint securite

3. SAST — Analyse Statique de Securite

Le SAST (Static Application Security Testing) analyse le code source sans l'executer pour detecter les vulnerabilites potentielles. Il intervient lors de la phase de build, idealement sur chaque commit ou pull request. 

    Code source
         |
         v
  +-------------+
  | Analyseur   |     Regles de securite
  | SAST        |<--- (OWASP, CWE, custom)
  +-------------+
         |
         v
  +-------------+
  | Rapport     |
  | - Critique  | ---> Bloque le pipeline
  | - Haute     | ---> Alerte equipe
  | - Moyenne   | ---> Ticket cree
  | - Basse     | ---> Info dans dashboard
  +-------------+

Vulnerabilites detectees par SAST

Categorie Exemples CWE
Injection SQL injection, OS command injection, LDAP injection CWE-89, CWE-78
XSS Reflected XSS, Stored XSS, DOM-based XSS CWE-79
Buffer Overflow Stack overflow, Heap overflow CWE-120
Deserialization Insecure deserialization, type confusion CWE-502
Secrets en dur Mots de passe, cles API, tokens dans le code CWE-798
Crypto faible MD5, SHA1, DES, cles trop courtes CWE-327
Path Traversal Acces fichiers non autorises via ../ CWE-22

Outils SAST — Comparaison

Outil Langages Open Source CI/CD Forces
SonarQube 30+ Community GitHub, GitLab, Azure Qualite + securite
Semgrep 30+ Oui Tous Regles personnalisables
Snyk Code 10+ Non Tous UX, suggestions de fix
CodeQL 10+ Queries GitHub Actions Profondeur d'analyse
Checkmarx 30+ Non Tous Entreprise, compliance
Fortify 25+ Non Tous Tres complet
Roslyn Analyzers C#/.NET Oui dotnet build Integre a .NET
Bandit Python Oui Tous Leger, rapide

Exemples d'integration CI

GitHub Actions — SAST avec Semgrep

# .github/workflows/sast.yml
name: SAST - Semgrep
on: [push, pull_request]

jobs:
  semgrep:
    runs-on: ubuntu-latest
    container:
      image: returntocorp/semgrep
    steps:
      - uses: actions/checkout@v4
      - run: semgrep ci
        env:
          SEMGREP_RULES: "p/owasp-top-ten p/cwe-top-25"

GitLab CI — SAST avec SonarQube

# .gitlab-ci.yml
sonarqube-sast:
  stage: test
  image: sonarsource/sonar-scanner-cli:latest
  variables:
    SONAR_HOST_URL: "https://sonarqube.example.com"
    SONAR_TOKEN: "$SONAR_TOKEN"
  script:
    - sonar-scanner
        -Dsonar.projectKey=my-project
        -Dsonar.sources=src/
        -Dsonar.qualitygate.wait=true
  allow_failure: false
  # Le pipeline echoue si le Quality Gate ne passe pas

Gestion des resultats SAST

Mauvaise pratique

  • Ignorer les faux positifs sans les documenter
  • Desactiver le scan quand il y a trop d'alertes
  • Ne pas prioriser les findings
  • Reporter indefiniment les corrections

Bonne pratique

  • Traiter chaque finding : corriger ou marquer comme faux positif avec justification
  • Prioriser par severite : Critique > Haute > Moyenne > Basse
  • Integrer dans le workflow : tickets Jira automatiques
  • Revue de securite lors des code reviews

4. SCA — Analyse des Dependances

Le SCA (Software Composition Analysis) verifie que les dependances (bibliotheques open source) utilisees par votre projet ne contiennent pas de vulnerabilites connues (CVE). Avec 80 a 90% du code des applications modernes provenant de l'open source, le SCA est essentiel. 

  Votre application
  +--------------------------------+
  |  Votre code (10-20%)           |
  |================================|
  |  Dependance A  v2.3.1          |  <-- CVE-2024-1234 (Critique!)
  |  Dependance B  v1.0.0          |  <-- OK
  |  Dependance C  v5.2.0          |  <-- CVE-2023-5678 (Haute)
  |    +-- Dep transitive D v1.1   |  <-- CVE-2024-9999 (Moyenne)
  |    +-- Dep transitive E v3.0   |  <-- OK
  |  Dependance F  v0.9.8          |  <-- Licence GPL! (contamination)
  +--------------------------------+

  Le SCA analyse TOUTES les dependances,
  y compris les dependances transitives.

SBOM — Software Bill of Materials

Un SBOM est un inventaire complet de tous les composants logiciels d'une application. C'est l'equivalent d'une liste d'ingredients pour un produit alimentaire. Requis par le decret executif americain 14028 pour les fournisseurs du gouvernement federal.

Format Organisation Format Adoption
CycloneDX OWASP JSON, XML Securite applicative, tres populaire
SPDX Linux Foundation JSON, RDF, YAML Conformite licence, standard ISO

Outils SCA — Comparaison

Outil Ecosystemes SBOM Licence Forces
Dependabot npm, NuGet, pip, etc. Non Non Integre GitHub, PRs automatiques
Snyk Tous Oui Oui Fix suggestions, monitoring continu
OWASP Dep-Check Java, .NET, Node Oui Non Gratuit, mature, reference
Trivy Tous + Docker Oui Non Rapide, polyvalent
Renovate Tous Non Non PRs auto, tres configurable
WhiteSource (Mend) Tous Oui Oui Entreprise, complet
npm audit / dotnet list npm / .NET Non Non Integres, zero configuration

5. DAST — Analyse Dynamique de Securite

Le DAST (Dynamic Application Security Testing) teste l'application en cours d'execution, depuis l'exterieur (approche "boite noire"). Il simule des attaques reelles contre l'application deployee dans un environnement de staging ou pre-production. 

                                    +---------------------+
                                    |  Application en     |
  +----------+    Requetes HTTP     |  cours d'execution  |
  | Scanner  | ------------------> |  (Staging)          |
  | DAST     | <------------------ |                     |
  +----------+    Reponses         +---------------------+
       |
       v
  +----------+
  | Rapport  |   Le scanner analyse les reponses pour
  | DAST     |   detecter : XSS, SQLi, CSRF, Headers
  +----------+   manquants, erreurs de configuration...

SAST vs DAST

CritereSASTDAST
ApprocheBoite blancheBoite noire
QuandBuild timeRuntime (staging)
Acces au codeOuiNon
Faux positifsPlus nombreuxMoins nombreux
CouvertureTout le codeEndpoints exposes
VitesseRapidePlus lent

Quoi utiliser ?

Les deux ! SAST et DAST sont complementaires :

  • SAST trouve les bugs dans le code source
  • DAST trouve les problemes de configuration et les vulnerabilites en runtime
  • IAST (Interactive) combine les deux avec un agent dans l'application
Conseil : Utilisez SAST sur chaque commit et DAST en pipeline de nuit ou sur les environnements de staging.

Outils DAST — Comparaison

Outil Type Open Source API Testing Forces
OWASP ZAP Proxy/Scanner Oui Oui Reference gratuite, communaute active
Burp Suite Proxy/Scanner Community Oui Le plus complet, standard de l'industrie
Nikto Scanner web Oui Non Rapide, simple, historique
Nuclei Scanner templates Oui Oui Templates communautaires, extensible
OWASP Amass Recon/Discovery Oui Non Reconnaissance de surface d'attaque

Exemple : OWASP ZAP dans GitHub Actions

# .github/workflows/dast.yml
name: DAST - OWASP ZAP
on:
  schedule:
    - cron: '0 2 * * 1-5'  # Chaque nuit, lundi-vendredi

jobs:
  zap-scan:
    runs-on: ubuntu-latest
    steps:
      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.12.0
        with:
          target: 'https://staging.example.com'
          rules_file_name: '.zap/rules.tsv'
          cmd_options: '-a'

      - name: ZAP Full Scan
        uses: zaproxy/action-full-scan@v0.10.0
        with:
          target: 'https://staging.example.com'

      - name: Upload Report
        uses: actions/upload-artifact@v4
        with:
          name: zap-report
          path: report_html.html

6. Detection et Gestion des Secrets

Les secrets (cles API, mots de passe, tokens, certificats) sont l'une des causes majeures de compromission. GitHub detecte des millions de secrets exposes dans les depots publics chaque annee.

Chiffre cle : En 2023, GitHub a detecte plus de 12 millions de secrets dans les commits de depots publics. Une cle API exposee peut etre exploitee en moins de 30 secondes par des bots qui scannent GitHub en continu. 
  Types de secrets exposes dans le code :

$ brew install gitleaks   # ou scoop install gitleaks sur Windows

  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0

      - id: gitleaks

# Lancer manuellement
$ gitleaks detect --source . --verbose

    RuleID: generic-api-key
    Entropy: 4.7
    File: src/config/settings.json
    Line: 12

Configuration .gitleaks.toml

# .gitleaks.toml
title = "Configuration GitLeaks personnalisee"

# Ajouter des regles personnalisees
[[rules]]
id = "custom-api-key"
description = "Cle API interne detectee"
regex = '''(?i)api[_-]?key\s*[:=]\s*['"][a-zA-Z0-9]{32,}['"]'''
tags = ["key", "api"]

# Exclure certains fichiers (faux positifs)
[allowlist]
paths = [
    '''tests/fixtures/''',
    '''docs/examples/''',
]

# Exclure certaines regles pour des fichiers specifiques
[[rules]]
id = "test-credentials"
description = "Credentials de test ignores"
regex = '''test_password\s*='''
[rules.allowlist]
paths = ['''tests/''']

Que faire quand un secret est expose ?

URGENT : Ne jamais simplement supprimer le commit ! Le secret reste dans l'historique git. Voici la procedure correcte : 
  Secret expose detecte !
         |
         v
  +------------------+
  | 1. REVOQUER      |  Revoquer immediatement le secret
  |    le secret     |  chez le fournisseur (AWS, GitHub, etc.)
  +------------------+
         |
         v
  +------------------+
  | 2. GENERER       |  Generer un nouveau secret et le
  |    un nouveau    |  stocker dans un gestionnaire securise
  +------------------+
         |
         v
  +------------------+
  | 3. DEPLOYER      |  Deployer la nouvelle configuration
  |    la rotation   |  avec le nouveau secret
  +------------------+
         |
         v
  +------------------+
  | 4. NETTOYER      |  Optionnel : git filter-branch ou
  |    l'historique   |  BFG Repo-Cleaner pour supprimer
  +------------------+  le secret de l'historique
         |
         v
  +------------------+

  |    et prevention |  les protections (pre-commit hooks)
  +------------------+

7. Scan de Conteneurs et Images Docker

Les images Docker sont construites a partir d'images de base contenant un systeme d'exploitation et des packages qui peuvent contenir des vulnerabilites connues. Le scan d'images est essentiel avant tout deploiement. 

  Image Docker : couches de vulnerabilites potentielles

  +========================================+
  |  Votre application (code)              |  <-- SAST
  +========================================+
  |  Dependances (npm, NuGet, pip)         |  <-- SCA
  +========================================+
  |  Runtime (.NET, Node.js, Python)       |  <-- Image Scan
  +========================================+
  |  OS packages (apt, apk)               |  <-- Image Scan
  +========================================+
  |  Image de base (ubuntu, alpine, etc.)  |  <-- Image Scan
  +========================================+

  Chaque couche peut introduire des CVE !
  Le scanner analyse TOUTES les couches.

Outils de scan d'images

Outil Registry CI/CD SBOM Forces
Trivy Oui Oui Oui Le plus populaire, rapide
Docker Scout Oui Oui Oui Integre Docker Desktop
Grype Oui Oui Oui Rapide, par Anchore
Snyk Container Oui Oui Oui Suggestions de fix, base image upgrade
Clair Oui Oui Non Open source, CoreOS/Red Hat

Exemple : Trivy scan d'image en pipeline

# GitHub Actions - Scan d'image Docker
- name: Build Docker image
  run: docker build -t myapp:${{ github.sha }} .

- name: Trivy image scan
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myapp:${{ github.sha }}'
    format: 'sarif'
    output: 'trivy-results.sarif'
    severity: 'CRITICAL,HIGH'
    exit-code: '1'  # Echoue si vulns critiques

Bonnes pratiques Dockerfile

Mauvais Dockerfile

# Image lourde avec plein de CVE
FROM ubuntu:latest

# Installation en root
RUN apt-get update && \
    apt-get install -y nodejs npm

# Copie de TOUT, y compris .env
COPY . .

# Secrets en dur dans l'image
ENV DB_PASSWORD=SuperSecret123

# Execution en root !
CMD ["node", "server.js"]

Bon Dockerfile

# Image minimale, version fixee
FROM node:20-alpine@sha256:abc...

# Utilisateur non-root
RUN addgroup -S app && adduser -S app -G app

WORKDIR /app

# Copie selective avec .dockerignore
COPY package*.json ./
RUN npm ci --only=production

COPY src/ ./src/

USER app
CMD ["node", "src/server.js"]
Conseil : Utilisez des images distroless (Google) ou alpine pour reduire drastiquement la surface d'attaque. Une image ubuntu:latest contient environ 100+ CVE, tandis qu'une image alpine en contient generalement moins de 5.

9. Quality Gates et Couverture

SonarQube Quality Gate

Un Quality Gate est un ensemble de conditions que le code doit remplir avant de pouvoir progresser dans le pipeline. Si le gate echoue, le pipeline est bloque. 

  Quality Gate SonarQube - Configuration par defaut ("Sonar way")

  +================================================================+
  |                    QUALITY GATE                                 |
  +================================================================+
  |                                                                |
  |  Condition                           Seuil      Statut        |
  |  ──────────────────────────────────  ─────────  ────────      |
  |  Couverture sur nouveau code         >= 80%     PASS/FAIL     |
  |  Duplications sur nouveau code       <= 3%      PASS/FAIL     |
  |  Fiabilite (bugs) nouveau code       A          PASS/FAIL     |
  |  Securite (vulns) nouveau code       A          PASS/FAIL     |
  |  Maintenabilite (code smells)        A          PASS/FAIL     |
  |  Security hotspots reviewed          100%       PASS/FAIL     |
  |                                                                |
  |  Resultat : PASS  --> Le code peut continuer                  |
  |             FAIL  --> Le pipeline est bloque !                |
  +================================================================+

Metriques de securite SonarQube

Metrique Description Impact pipeline
Vulnerabilities Failles de securite confirmees (CWE) Bloquant si > 0 (A)
Security Hotspots Code sensible necessitant une revue manuelle Doit etre revu a 100%
Bugs Bugs potentiels dans le code Bloquant si note < A
Code Smells Problemes de maintenabilite Objectif : note A
Coverage Couverture de tests unitaires Minimum 80% nouveau code
Duplications Code duplique Maximum 3% nouveau code

Signature d'artefacts

La signature d'artefacts garantit l'integrite et l'authenticite des binaires deployes. Personne n'a modifie l'artefact entre le build et le deploiement.

11. Exemples de Pipelines Complets

GitHub Actions — Pipeline DevSecOps complet

# .github/workflows/devsecops.yml
name: DevSecOps Pipeline
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  DOTNET_VERSION: '8.0.x'
  IMAGE_NAME: 'myapp'

jobs:
  # ────────────────────────────────────────────
  # ETAPE 1 : Lint et detection de secrets
  # ────────────────────────────────────────────
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: GitLeaks - Secret Scan
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  # ────────────────────────────────────────────
  # ETAPE 2 : Build et analyse statique
  # ────────────────────────────────────────────
  build-and-sast:
    runs-on: ubuntu-latest
    needs: secret-scan
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Restore & Build
        run: |
          dotnet restore
          dotnet build --no-restore

      - name: SAST - Semgrep
        uses: returntocorp/semgrep-action@v1
        with:
          config: "p/owasp-top-ten p/cwe-top-25"

      - name: SAST - CodeQL
        uses: github/codeql-action/analyze@v3

  # ────────────────────────────────────────────
  # ETAPE 3 : Analyse des dependances (SCA)
  # ────────────────────────────────────────────
  sca:
    runs-on: ubuntu-latest
    needs: secret-scan
    steps:
      - uses: actions/checkout@v4

      - name: SCA - Trivy (dependances)
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'

      - name: dotnet list vulnerable packages
        run: dotnet list package --vulnerable --include-transitive

  # ────────────────────────────────────────────
  # ETAPE 4 : Tests unitaires
  # ────────────────────────────────────────────
  tests:
    runs-on: ubuntu-latest
    needs: [build-and-sast, sca]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Run Tests with Coverage
        run: |
          dotnet test --collect:"XPlat Code Coverage" \
            --results-directory ./coverage

      - name: SonarQube Analysis
        uses: sonarsource/sonarqube-scan-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}

      - name: Quality Gate Check
        uses: sonarsource/sonarqube-quality-gate-action@master
        timeout-minutes: 5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  # ────────────────────────────────────────────
  # ETAPE 5 : Build image + scan conteneur
  # ────────────────────────────────────────────
  container-scan:
    runs-on: ubuntu-latest
    needs: tests
    steps:
      - uses: actions/checkout@v4

      - name: Build Docker Image
        run: docker build -t ${{ env.IMAGE_NAME }}:${{ github.sha }} .

      - name: Trivy Image Scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: '${{ env.IMAGE_NAME }}:${{ github.sha }}'
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
          exit-code: '1'

      - name: Generate SBOM
        run: |
          trivy image --format cyclonedx \
            --output sbom.json \
            ${{ env.IMAGE_NAME }}:${{ github.sha }}

      - name: Upload SBOM
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

  # ────────────────────────────────────────────
  # ETAPE 6 : DAST (sur staging)
  # ────────────────────────────────────────────
  dast:
    runs-on: ubuntu-latest
    needs: container-scan
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to Staging
        run: # Deployer sur staging...
          echo "Deploying to staging..."

      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.12.0
        with:
          target: 'https://staging.example.com'

  # ────────────────────────────────────────────
  # ETAPE 7 : Deploiement production
  # ────────────────────────────────────────────
  deploy:
    runs-on: ubuntu-latest
    needs: dast
    if: github.ref == 'refs/heads/main'
    environment: production
    steps:
      - name: Sign Image
        run: cosign sign --key env://COSIGN_KEY ${{ env.IMAGE_NAME }}:${{ github.sha }}
        env:
          COSIGN_KEY: ${{ secrets.COSIGN_KEY }}

      - name: Deploy to Production
        run: echo "Deploying to production..."

# .gitlab-ci.yml
stages:
  - secret-scan
  - build
  - sast
  - sca
  - test
  - container-scan
  - dast
  - deploy

variables:
  DOTNET_VERSION: "8.0"
  IMAGE_TAG: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"

# ──── Secret Scan ────
gitleaks:
  stage: secret-scan
  image: zricethezav/gitleaks:latest
  script:
    - gitleaks detect --source . --verbose --report-path gitleaks-report.json
  artifacts:
    paths:
      - gitleaks-report.json
    when: always

# ──── Build ────
build:
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet restore
    - dotnet build --no-restore --configuration Release
    - dotnet publish -c Release -o ./publish
  artifacts:
    paths:
      - publish/

# ──── SAST ────
semgrep:
  stage: sast
  image: returntocorp/semgrep
  script:
    - semgrep ci --config "p/owasp-top-ten" --config "p/cwe-top-25"
      --sarif --output semgrep-results.sarif
  artifacts:
    paths:
      - semgrep-results.sarif

# ──── SCA ────
trivy-sca:
  stage: sca
  image: aquasec/trivy:latest
  script:
    - trivy fs --scanners vuln --severity HIGH,CRITICAL
      --exit-code 1 --format json --output sca-report.json .
  artifacts:
    paths:
      - sca-report.json

# ──── Tests ────
unit-tests:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet test --collect:"XPlat Code Coverage"
      --results-directory ./coverage
  artifacts:
    paths:
      - coverage/
  coverage: '/Total\s*\|\s*(\d+\.?\d+)%/'

sonarqube:
  stage: test
  image: sonarsource/sonar-scanner-cli:latest
  variables:
    SONAR_HOST_URL: "$SONAR_URL"
    SONAR_TOKEN: "$SONAR_TOKEN"
  script:
    - sonar-scanner -Dsonar.qualitygate.wait=true
  allow_failure: false

# ──── Container Scan ────
container-scan:
  stage: container-scan
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker build -t $IMAGE_TAG .
    - docker run --rm
      -v /var/run/docker.sock:/var/run/docker.sock
      aquasec/trivy image --exit-code 1
      --severity CRITICAL,HIGH $IMAGE_TAG

# ──── DAST ────
zap-dast:
  stage: dast
  image: ghcr.io/zaproxy/zaproxy:stable
  script:
    - zap-baseline.py -t https://$STAGING_URL -r zap-report.html
  artifacts:
    paths:
      - zap-report.html
  only:
    - main

# ──── Deploy ────
deploy-production:
  stage: deploy
  script:
    - echo "Deploying $IMAGE_TAG to production..."
  environment:
    name: production
  when: manual
  only:
    - main

# azure-pipelines.yml
trigger:
  branches:
    include:
      - main
      - develop

pool:
  vmImage: 'ubuntu-latest'

variables:
  dotnetVersion: '8.0.x'
  imageName: 'myapp'

stages:
# ──── Stage 1 : Secret Scan ────
- stage: SecretScan
  jobs:
  - job: GitLeaks
    steps:
    - script: |
        docker run --rm -v $(Build.SourcesDirectory):/repo \
          zricethezav/gitleaks:latest detect \
          --source /repo --verbose
      displayName: 'Secret Scan - GitLeaks'

# ──── Stage 2 : Build + SAST + SCA ────
- stage: BuildAndAnalyze
  dependsOn: SecretScan
  jobs:
  - job: BuildSAST
    steps:
    - task: UseDotNet@2
      inputs:
        packageType: 'sdk'
        version: '$(dotnetVersion)'

    - script: dotnet restore && dotnet build --no-restore
      displayName: 'Restore & Build'

    - script: |
        dotnet list package --vulnerable --include-transitive
      displayName: 'SCA - Vulnerable Packages'

    - script: |
        docker run --rm -v $(Build.SourcesDirectory):/src \
          returntocorp/semgrep semgrep ci \
          --config "p/owasp-top-ten"
      displayName: 'SAST - Semgrep'

    - task: SonarQubePrepare@6
      inputs:
        SonarQube: 'SonarQubeConnection'
        scannerMode: 'MSBuild'
        projectKey: 'myapp'

    - task: SonarQubeAnalyze@6
    - task: SonarQubePublish@6

# ──── Stage 3 : Tests ────
- stage: Test
  dependsOn: BuildAndAnalyze
  jobs:
  - job: UnitTests
    steps:
    - task: DotNetCoreCLI@2
      inputs:
        command: 'test'
        arguments: '--collect:"XPlat Code Coverage"'
      displayName: 'Run Tests with Coverage'

    - task: PublishCodeCoverageResults@2
      inputs:
        summaryFileLocation: '**/coverage.cobertura.xml'

# ──── Stage 4 : Container Scan ────
- stage: ContainerScan
  dependsOn: Test
  jobs:
  - job: ScanImage
    steps:
    - script: docker build -t $(imageName):$(Build.BuildId) .
      displayName: 'Build Docker Image'

    - script: |
        docker run --rm \
          -v /var/run/docker.sock:/var/run/docker.sock \
          aquasec/trivy image --exit-code 1 \
          --severity CRITICAL,HIGH \
          $(imageName):$(Build.BuildId)
      displayName: 'Trivy Image Scan'

# ──── Stage 5 : DAST ────
- stage: DAST
  dependsOn: ContainerScan
  condition: eq(variables['Build.SourceBranch'], 'refs/heads/main')
  jobs:
  - job: ZAPScan
    steps:
    - script: |
        docker run --rm ghcr.io/zaproxy/zaproxy:stable \
          zap-baseline.py -t https://staging.example.com
      displayName: 'OWASP ZAP - DAST Scan'

# ──── Stage 6 : Deploy ────
- stage: Deploy
  dependsOn: DAST
  condition: eq(variables['Build.SourceBranch'], 'refs/heads/main')
  jobs:
  - deployment: Production
    environment: 'production'
    strategy:
      runOnce:
        deploy:
          steps:
          - script: echo "Deploying to production..."
            displayName: 'Deploy'

12. Bonnes Pratiques Recapitulatives

20 regles d'or pour un pipeline CI/CD securise.
  1. Shift Left : Integrer les controles de securite le plus tot possible. Un hook pre-commit est plus efficace qu'un scan en production.
  2. Automatiser tout : Chaque controle de securite doit etre automatise dans le pipeline. Aucune verification manuelle ne doit bloquer le flux.
  3. Scanner les secrets avant chaque commit : Utiliser des hooks pre-commit (GitLeaks, TruffleHog) pour empecher les secrets d'entrer dans l'historique git.
  4. SAST sur chaque PR : L'analyse statique doit s'executer sur chaque pull request/merge request et bloquer la fusion si des vulnerabilites critiques sont detectees.
  5. SCA automatise : Configurer Dependabot ou Renovate pour mettre a jour automatiquement les dependances vulnerables via des pull requests.
  6. DAST regulier : Executer des scans DAST (OWASP ZAP) sur les environnements de staging, au minimum chaque nuit.
  7. Quality Gate obligatoire : Configurer un Quality Gate SonarQube qui bloque le pipeline si le code ne respecte pas les seuils de securite et de qualite.
  8. Scanner les images Docker : Chaque image doit etre scannee (Trivy) avant d'etre poussee dans un registry. Bloquer les images avec des CVE critiques.
  9. Utiliser des images de base minimales : Preferer Alpine ou distroless plutot que Ubuntu/Debian pour reduire la surface d'attaque.
  10. Ne jamais executer en root : Les conteneurs et les processus doivent tourner avec un utilisateur non-root.
  11. Generer un SBOM : Produire un Software Bill of Materials (CycloneDX) pour chaque release pour la tracabilite et la conformite.
  12. Signer les artefacts : Utiliser cosign/Sigstore pour garantir l'integrite des images deployees.
  13. Gerer les secrets avec un vault : Utiliser Azure Key Vault, HashiCorp Vault ou AWS Secrets Manager. Jamais de secrets dans le code ou les variables d'environnement en clair.
  14. Rotation des secrets : Mettre en place une rotation automatique des secrets et revoquer immediatement tout secret expose.
  15. IaC scanning : Scanner les fichiers Terraform, Kubernetes, Dockerfiles avec Checkov ou tfsec pour detecter les misconfigurations.
  16. Deploiement progressif : Utiliser des strategies Canary ou Blue-Green pour limiter l'impact d'un probleme en production.
  17. Monitoring post-deploiement : Surveiller les metriques de securite (taux d'erreurs, comportements anormaux) apres chaque deploiement.
  18. Pipeline comme code : Les fichiers de pipeline (YAML) doivent etre versionnes dans git et revus comme du code applicatif.
  19. Principe du moindre privilege : Les service accounts du pipeline ne doivent avoir que les permissions strictement necessaires.
  20. Formation continue : Former regulierement les developpeurs aux pratiques de securite (OWASP Top 10, secure coding) et organiser des security champions dans chaque equipe.
