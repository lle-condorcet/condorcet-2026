Keycloak Authentication Lab

Authentification et autorisation centralisee avec OAuth 2.0, OpenID Connect et ASP.NET Core

Introduction : pourquoi Keycloak ?

Keycloak est un serveur d'identite et de gestion des acces (IAM) open source, developpe par Red Hat. Il permet de centraliser l'authentification et l'autorisation de toutes vos applications au sein d'un seul service.

Au lieu de reimplementer la gestion des mots de passe, des sessions, du MFA et des roles dans chaque application, Keycloak fournit ces fonctionnalites en tant que service, via les protocoles standards OAuth 2.0 et OpenID Connect (OIDC).

Avantage cle : Une seule source de verite pour les identites, les roles et les politiques d'acces. L'utilisateur se connecte une seule fois (SSO) et accede a toutes les applications autorisees.

Problemes resolus par Keycloak

  • Single Sign-On (SSO) : connexion unique pour toutes les applications
  • Gestion centralisee des utilisateurs : creation, desactivation, roles au meme endroit
  • Protocoles standards : OAuth 2.0, OIDC, SAML 2.0 — pas de solution proprietaire
  • MFA integre : TOTP, WebAuthn, SMS configurables par realm
  • Federation d'identites : integration avec LDAP, Active Directory, Google, GitHub
  • Audit : journalisation de tous les evenements d'authentification

Concepts cles

OAuth 2.0 — Les flux d'autorisation

OAuth 2.0 est un framework d'autorisation (pas d'authentification !). Il definit comment une application peut obtenir un acces delegue aux ressources d'un utilisateur sans connaitre son mot de passe.

FluxUsageDescription
Authorization Code Applications web serveur L'utilisateur est redirige vers Keycloak, s'authentifie, et un code temporaire est echange contre des tokens cote serveur
Authorization Code + PKCE SPA, applications mobiles Variante securisee pour les clients publics, avec un verifieur de code aleatoire
Client Credentials Communication machine-a-machine L'application s'authentifie elle-meme (pas d'utilisateur) avec son client_id et client_secret
Resource Owner Password Deconseille L'application collecte directement le mot de passe — a eviter sauf cas tres specifique

OpenID Connect (OIDC)

OIDC est une couche d'identite construite au-dessus d'OAuth 2.0. Elle ajoute :

  • ID Token : un JWT contenant l'identite de l'utilisateur (qui il est)
  • UserInfo Endpoint : un endpoint pour recuperer des informations supplementaires
  • Discovery : un document .well-known/openid-configuration decrivant les endpoints disponibles

JWT — JSON Web Token

Un JWT est compose de trois parties separees par des points : header.payload.signature. Chaque partie est encodee en Base64URL. 

// Structure d'un JWT
eyJhbGciOiJSUzI1NiJ9    // Header : algorithme de signature
.eyJzdWIiOiIxMjM0NTY3ODkwIiwiZW1haWwiOiJ1c2VyQGxhYi5sb2NhbCJ9    // Payload : donnees (claims)
.SflKxwRJSMeKKF2QT4fwp...    // Signature : verification d'integrite

Flux d'authentification (Authorization Code Flow)

  1. L'utilisateur clique sur "Se connecter" dans l'application .NET
  2. L'application redirige vers Keycloak (/realms/securite-lab/protocol/openid-connect/auth)
  3. L'utilisateur saisit ses identifiants sur la page de login Keycloak
  4. Keycloak redirige vers l'application avec un code d'autorisation
  5. L'application echange ce code contre un Access Token, un ID Token et un Refresh Token
  6. L'application cree une session cookie et stocke les tokens
  7. Les requetes suivantes utilisent le cookie de session (MVC) ou le Bearer token (API)

Prerequis

  • Docker Desktop installe et en cours d'execution
  • .NET 10 SDK (pour executer l'application en local sans Docker)
  • 8 Go de RAM minimum (Keycloak + PostgreSQL + App)
  • Un navigateur web moderne
  • curl ou Postman pour tester les API

Le realm securite-lab est importe automatiquement au demarrage de Keycloak grace au fichier realm-export.json. Voici comment reproduire cette configuration manuellement.

  2. Cliquez sur le menu deroulant en haut a gauche (affichant "master")
  3. Cliquez sur "Create Realm"
  4. Nom du realm : securite-lab
  5. Cliquez sur "Create"

2. Creer un client

  1. Dans le realm securite-lab, allez dans Clients > Create client
  2. Client ID : securite-lab-app
  3. Client type : OpenID Connect
  4. Activez Client authentication (client confidentiel)
  5. Activez Standard flow (Authorization Code) et Direct access grants
// Parametres du client

// URIs de redirection

  http://localhost:5000
  http://localhost:5001
Important : Le client_secret se trouve dans l'onglet Credentials du client. Copiez-le et configurez-le dans appsettings.json ou via variable d'environnement.

3. Creer les roles du realm

  1. Allez dans Realm roles > Create role
  2. Creez 4 roles : admin, manager, user, auditor

4. Creer les utilisateurs et assigner les roles

  1. Allez dans Users > Add user
  2. Renseignez le username, l'email, prenom et nom
  3. Dans l'onglet Credentials, definissez le mot de passe (decochez "Temporary")
  4. Dans l'onglet Role mapping, assignez le role du realm

5. Configurer les mappers de roles dans les tokens

Par defaut, Keycloak inclut les roles dans des structures imbriquees du token JWT. Pour que .NET puisse les lire, nous utilisons des protocol mappers :

  • realm_access.roles : roles globaux du realm
  • resource_access.securite-lab-app.roles : roles specifiques au client
// Structure des roles dans le JWT Keycloak
{
  "realm_access": {
    "roles": ["admin", "default-roles-securite-lab"]
  },
  "resource_access": {
    "securite-lab-app": {
      "roles": ["admin"]
    }
  }
}

Integration OpenID Connect dans ASP.NET Core

L'integration se fait via le middleware Microsoft.AspNetCore.Authentication.OpenIdConnect. La configuration est centralisee dans Program.cs.

Configuration de l'authentification

// Program.cs - Configuration de l'authentification
builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie(options =>
{
    options.Cookie.Name = "KeycloakLabAuth";
    options.Cookie.HttpOnly = true;           // Pas accessible via JavaScript
    options.Cookie.SecurePolicy = CookieSecurePolicy.SameAsRequest;
    options.Cookie.SameSite = SameSiteMode.Lax;
    options.ExpireTimeSpan = TimeSpan.FromMinutes(60);
    options.SlidingExpiration = true;
    options.AccessDeniedPath = "/Account/AccessDenied";
})
.AddOpenIdConnect(options =>
{
    // Serveur Keycloak
    options.Authority = "http://localhost:8080/realms/securite-lab";
    options.ClientId = "securite-lab-app";
    options.ClientSecret = "dev-secret-change-in-production";

    // Utiliser Authorization Code Flow
    options.ResponseType = OpenIdConnectResponseType.Code;
    options.SaveTokens = true;              // Stocker les tokens dans le cookie
    options.GetClaimsFromUserInfoEndpoint = true;
    options.RequireHttpsMetadata = false;    // Dev uniquement !

    // Scopes demandes
    options.Scope.Add("openid");
    options.Scope.Add("profile");
    options.Scope.Add("email");
    options.Scope.Add("roles");

    // Mapper les claims Keycloak
    options.ClaimActions.MapJsonKey("realm_access", "realm_access");
    options.ClaimActions.MapJsonKey("resource_access", "resource_access");
});
Attention production : RequireHttpsMetadata = false ne doit jamais etre utilise en production. En production, Keycloak doit etre accessible via HTTPS.

Configuration dans appsettings.json

{
  "Keycloak": {
    "Authority": "http://localhost:8080/realms/securite-lab",
    "ClientId": "securite-lab-app",
    "ClientSecret": "CHANGEZ-MOI-EN-PRODUCTION",
    "Realm": "securite-lab"
  }
}

JWT Bearer pour les API

En plus de l'authentification cookie pour le MVC, nous configurons un schema JWT Bearer pour securiser les endpoints API REST. Cela permet aux clients externes (SPA, applications mobiles, scripts) de s'authentifier avec un token Bearer. 

// Ajout du schema JWT Bearer dans Program.cs
.AddJwtBearer(options =>
{
    options.Authority = "http://localhost:8080/realms/securite-lab";
    options.Audience = "securite-lab-app";
    options.RequireHttpsMetadata = false;

    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidIssuer = "http://localhost:8080/realms/securite-lab",
        ValidateAudience = true,
        ValidAudiences = new[] { "securite-lab-app", "account" },
        ValidateLifetime = true,
        ClockSkew = TimeSpan.FromSeconds(30)  // Tolerance d'horloge reduite
    };
});

Utilisation dans les controleurs API

[ApiController]
[Route("api/[controller]")]
[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]
public class DocumentsApiController : ControllerBase
{
    // Tous les endpoints ici requierent un Bearer token valide

    [HttpGet]
    public async Task<IActionResult> GetDocuments()
    {
        var roles = User.Claims
            .Where(c => c.Type == ClaimTypes.Role)
            .Select(c => c.Value);

        var documents = await _documentService
            .GetAccessibleDocumentsAsync(GetUserId(), roles, GetIpAddress());

        return Ok(documents);
    }
}

Mapping des roles Keycloak vers .NET

Keycloak stocke les roles dans une structure JSON imbriquee a l'interieur du JWT (realm_access.roles et resource_access.{client}.roles). .NET attend des claims de type ClaimTypes.Role a plat. Il faut donc un ClaimsTransformation pour convertir.

Le probleme : structure des roles Keycloak

Format Keycloak (JWT brut)

{
  "realm_access": {
    "roles": ["admin"]
  },
  "resource_access": {
    "securite-lab-app": {
      "roles": ["admin"]
    }
  }
}
// .NET ne comprend pas
// cette structure nativement

Format .NET attendu (claims)

// Claims individuels de type Role
Type: ClaimTypes.Role
Value: "admin"

// Permet d'utiliser :
User.IsInRole("admin")
[Authorize(Roles = "admin")]

Solution : KeycloakRoleTransformer

public class KeycloakRoleTransformer : IClaimsTransformation
{
    public Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal)
    {
        var identity = principal.Identity as ClaimsIdentity;
        if (identity == null || !identity.IsAuthenticated)
            return Task.FromResult(principal);

        // Extraire realm_access.roles
        var realmAccessClaim = principal.FindFirst("realm_access");
        if (realmAccessClaim != null)
        {
            var realmAccess = JsonDocument.Parse(realmAccessClaim.Value);
            if (realmAccess.RootElement.TryGetProperty("roles", out var roles))
            {
                foreach (var role in roles.EnumerateArray())
                {
                    identity.AddClaim(new Claim(
                        ClaimTypes.Role,
                        role.GetString()!));
                }
            }
        }

        // Extraire resource_access.{clientId}.roles
        var resourceAccessClaim = principal.FindFirst("resource_access");
        // ... meme logique pour les roles du client

        return Task.FromResult(principal);
    }
}

Enregistrement du transformer

// Dans Program.cs
builder.Services.AddTransient<IClaimsTransformation, KeycloakRoleTransformer>();

Autorisation basee sur les roles

Une fois les roles mappes, nous pouvons utiliser le systeme d'autorisation standard d'ASP.NET Core : attributs [Authorize], politiques, et handlers personnalises.

Politiques d'autorisation

// Definition des politiques dans Program.cs
builder.Services.AddAuthorization(options =>
{
    // Politique simple par role
    options.AddPolicy("RequireAdmin", policy =>
        policy.RequireRole("admin"));

    // Politique acceptant plusieurs roles
    options.AddPolicy("RequireManager", policy =>
        policy.RequireRole("admin", "manager"));

    // Politique basee sur la classification de documents
    options.AddPolicy("ClassificationSecret", policy =>
        policy.Requirements.Add(
            new ClassificationRequirement(Classification.Secret)));
});

Utilisation dans les controleurs

// Acces restreint au role admin
[Authorize(Policy = "RequireAdmin")]
public class AdminController : Controller
{
    // Toutes les actions de ce controleur
    // requierent le role "admin"
}

// Acces restreint aux managers (et admins)
[Authorize(Policy = "RequireManager")]
public IActionResult Create()
{
    return View();
}

Handler d'autorisation personnalise : classification de documents

Le systeme de classification restreint l'acces aux documents en fonction du role de l'utilisateur :

RoleAcces maximumDocuments visibles
adminSecretPublic, Internal, Confidential, Secret
managerConfidentialPublic, Internal, Confidential
auditorConfidentialPublic, Internal, Confidential
userInternalPublic, Internal
(aucun role)PublicPublic uniquement
 
public class ClassificationHandler : AuthorizationHandler<ClassificationRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        ClassificationRequirement requirement)
    {
        var roles = context.User.Claims
            .Where(c => c.Type == ClaimTypes.Role)
            .Select(c => c.Value);

        var maxLevel = DocumentService.GetMaxClassificationForRoles(roles);

        if (maxLevel >= requirement.RequiredClassification)
        {
            context.Succeed(requirement);
        }
        // Si le role est insuffisant, le requirement echoue silencieusement
        // et l'acces est refuse (403)

        return Task.CompletedTask;
    }
}

Protection des API

Les endpoints API sont proteges par des tokens JWT Bearer. Pour les appeler, un client doit d'abord obtenir un token aupres de Keycloak, puis l'inclure dans l'en-tete Authorization: Bearer <token>.

Obtenir un token avec curl

# Obtenir un access token via Resource Owner Password Grant
curl -X POST "http://localhost:8080/realms/securite-lab/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password" \
  -d "client_id=securite-lab-app" \
  -d "client_secret=dev-secret-change-in-production" \
  -d "username=admin@lab.local" \
  -d "password=Admin123!"

Reponse de Keycloak

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6...",
  "expires_in": 300,
  "refresh_expires_in": 1800,
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6...",
  "token_type": "Bearer",
  "not-before-policy": 0,
  "session_state": "a1b2c3d4-...",
  "scope": "openid email profile roles"
}

Appeler l'API avec le token

# Stocker le token dans une variable
TOKEN="eyJhbGciOiJSUzI1NiIsInR5cCI6..."

# Appeler l'API des documents
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:5000/api/DocumentsApi"

# Appeler l'endpoint d'informations utilisateur

Deconnexion (Logout)

La deconnexion doit etre effectuee a la fois cote application et cote Keycloak :

// AccountController.cs - Deconnexion complete
[Authorize]
public async Task<IActionResult> Logout()
{
    // 1. Supprimer le cookie de session local
    await HttpContext.SignOutAsync(
        CookieAuthenticationDefaults.AuthenticationScheme);

    // 2. Rediriger vers le endpoint logout de Keycloak
    //    pour invalider la session SSO
    await HttpContext.SignOutAsync(
        OpenIdConnectDefaults.AuthenticationScheme);

    return RedirectToAction("Index", "Home");
}
Important : Si vous ne faites que supprimer le cookie local sans appeler le logout Keycloak, l'utilisateur sera automatiquement reconnecte lors de sa prochaine visite (car la session SSO est toujours active).

Configuration du timeout dans Keycloak

Dans la console d'administration Keycloak, allez dans Realm settings > Sessions pour configurer :

  • SSO Session Idle : duree d'inactivite avant expiration de la session SSO (par defaut : 30 minutes)
  • SSO Session Max : duree maximale d'une session SSO (par defaut : 10 heures)
  • Client Session Idle : duree d'inactivite specifique a un client
  • Access Token Lifespan : duree de vie de l'access token (dans Realm settings > Tokens)

Securisation avancee

PKCE (Proof Key for Code Exchange)

PKCE ajoute une couche de securite au flux Authorization Code pour prevenir les attaques d'interception de code. Le client genere un code_verifier aleatoire et envoie son hash (code_challenge) lors de la demande d'autorisation.

Bonne pratique : ASP.NET Core active PKCE automatiquement avec ResponseType = "code" dans les versions recentes du middleware OIDC.

// Configurer CORS pour les appels API depuis un front-end

Audit et tracabilite

La tracabilite est un pilier de la securite. Le laboratoire enregistre tous les acces (reussis et refuses) dans une table AccessLogs en base de donnees.

Service de journalisation

public class AccessLogService
{
    public async Task LogAsync(
        string userId,
        string action,
        string resource,
        string ipAddress,
        bool success,
        string details = "")
    {
        var log = new AccessLog
        {
            UserId = userId,
            Action = action,         // Ex: "VIEW_DOCUMENT", "LIST_DOCUMENTS"
            Resource = resource,     // Ex: "Document/3"
            IpAddress = ipAddress,
            Timestamp = DateTime.UtcNow,
            Success = success,       // true = autorise, false = refuse
            Details = details
        };

        _context.AccessLogs.Add(log);
        await _context.SaveChangesAsync();

        if (!success)
            _logger.LogWarning(
                "Access denied: User={UserId}, Resource={Resource}",
                userId, resource);
    }
}

Exemple d'utilisation dans le service de documents

// Quand un utilisateur tente d'acceder a un document protege
if (document.Classification > maxLevel)
{
    // Acces refuse — on enregistre la tentative
    await _accessLog.LogAsync(
        userId,
        "VIEW_DOCUMENT",
        $"Document/{id}",
        ipAddress,
        success: false,
        $"Classification {document.Classification} depasse le niveau {maxLevel}");

    return null;  // Le controleur redirige vers AccessDenied
}

// Acces autorise — on enregistre egalement
await _accessLog.LogAsync(
    userId, "VIEW_DOCUMENT", $"Document/{id}",
    ipAddress, success: true,
    $"Consulte: {document.Title}");

Anatomie d'un token JWT Keycloak

Voici un exemple de token JWT emis par Keycloak, decode pour en comprendre chaque partie.

Header

{
  "alg": "RS256",        // Algorithme de signature : RSA avec SHA-256
  "typ": "JWT",          // Type de token
  "kid": "abc123..."     // ID de la cle publique (pour la verification)
}

Payload (claims)

{
  "exp": 1711382400,            // Expiration (Unix timestamp)
  "iat": 1711382100,            // Emis le (Unix timestamp)
  "auth_time": 1711382100,      // Heure d'authentification
  "jti": "uuid-unique",        // Identifiant unique du token
  "iss": "http://localhost:8080/realms/securite-lab",  // Emetteur
  "aud": "account",             // Audience (destinataire)
  "sub": "user-uuid-...",       // Sujet (ID unique de l'utilisateur)
  "typ": "Bearer",              // Type de token
  "azp": "securite-lab-app",    // Client qui a demande le token
  "session_state": "...",      // ID de la session SSO
  "scope": "openid email profile roles",

  // Informations utilisateur
  "preferred_username": "admin@lab.local",
  "email": "admin@lab.local",
  "email_verified": true,
  "name": "Admin Systeme",
  "given_name": "Admin",
  "family_name": "Systeme",

  // Roles du realm (structure Keycloak specifique)
  "realm_access": {
    "roles": ["admin", "default-roles-securite-lab"]
  },

  // Roles specifiques au client
  "resource_access": {
    "securite-lab-app": {
      "roles": ["admin"]
    },
    "account": {
      "roles": ["manage-account"]
    }
  }
}

Signature

La signature est calculee avec la cle privee RSA de Keycloak. Pour la verifier, l'application .NET telecharge la cle publique depuis le JWKS endpoint (/realms/securite-lab/protocol/openid-connect/certs).

Ne jamais faire confiance a un JWT sans verifier la signature ! N'importe qui peut creer un JWT avec des claims arbitraires. Seule la verification cryptographique de la signature garantit que le token a ete emis par Keycloak.

Resolution des problemes courants

1. Erreur "Redirect URI Mismatch"

Symptome : Keycloak affiche "Invalid redirect_uri" lors de la connexion.

Cause : L'URL de redirection de l'application ne correspond pas aux URIs configurees dans le client Keycloak.

Solution :

  • Verifiez les Valid Redirect URIs dans la configuration du client Keycloak
  • Ajoutez http://localhost:5000/* (avec le wildcard /*)
  • Verifiez que le port correspond exactement

2. Erreur CORS

Symptome : Les appels API depuis un front-end echouent avec une erreur CORS.

Solution :

  • Ajoutez l'origine du front-end dans Web Origins du client Keycloak
  • Verifiez la configuration CORS dans Program.cs
  • Assurez-vous que AllowCredentials() est active si vous envoyez des cookies

3. Roles non mappes

Symptome : User.IsInRole("admin") retourne toujours false.

Solution :

  • Verifiez que le KeycloakRoleTransformer est enregistre dans Program.cs
  • Verifiez que les roles sont bien inclus dans le token (page Profile > Claims)
  • Verifiez les Client Scopes et Protocol Mappers dans Keycloak
  • Assurez-vous que realm_access et resource_access sont mappes via ClaimActions

4. Token expire

Symptome : L'API retourne 401 apres quelques minutes d'inactivite.

Solution :

  • L'access token expire apres 5 minutes par defaut
  • Utilisez le refresh token pour obtenir un nouveau token
  • Augmentez la duree de vie du token dans Realm settings > Tokens > Access Token Lifespan
  • Verifiez le ClockSkew dans TokenValidationParameters

5. Keycloak non accessible

Symptome : L'application .NET ne peut pas se connecter a Keycloak.

Solution :

  • Verifiez que Keycloak est bien demarre : docker compose ps
  • Verifiez les logs : docker compose logs keycloak
  • Si l'application est dans Docker, utilisez http://keycloak:8080 (nom du service) au lieu de http://localhost:8080
  • Si l'application est en local, utilisez http://localhost:8080

Exercices pratiques

Exercice 1 : Explorer les niveaux d'acces

Objectif : Observer les differences d'acces entre les roles.

  1. Demarrez la stack Docker et accedez a http://localhost:5000
  2. Connectez-vous avec user@lab.local / User123!
  3. Allez dans Documents et notez combien de documents sont visibles
  4. Deconnectez-vous, puis reconnectez-vous avec admin@lab.local / Admin123!
  5. Comparez le nombre de documents visibles
  6. Visitez la page Profil pour comparer les claims et roles entre les deux comptes
Questions : Combien de documents voit l'utilisateur "user" ? Et l'admin ? Quelle est la difference dans les claims du token ?

Exercice 2 : Ajouter un role "supervisor"

Objectif : Creer un nouveau role et implementer son controle d'acces.

  1. Dans la console Keycloak, creez un role supervisor dans le realm securite-lab
  2. Creez un utilisateur supervisor@lab.local et assignez-lui le role
  3. Modifiez DocumentService.GetMaxClassificationForRole() pour que le superviseur ait acces au niveau Secret
  4. Ajoutez une politique "RequireSupervisor" dans Program.cs
  5. Testez la connexion avec le nouveau compte
Indice : N'oubliez pas d'ajouter le role dans le client Keycloak egalement et de configurer les protocol mappers.

Exercice 3 : Appeler l'API avec curl/Postman

Objectif : Obtenir un token et appeler les endpoints API securises.

  1. Utilisez la commande curl ci-dessous pour obtenir un token :
curl -s -X POST \
  "http://localhost:8080/realms/securite-lab/protocol/openid-connect/token" \
  -d "grant_type=password&client_id=securite-lab-app&client_secret=dev-secret-change-in-production&username=manager@lab.local&password=Manager123!"
  1. Copiez le access_token de la reponse
  2. Appelez GET /api/AuthApi/userinfo avec le token
  3. Appelez GET /api/DocumentsApi et observez les documents retournes
  4. Essayez avec un token de l'utilisateur user@lab.local et comparez
  5. Essayez d'appeler sans token — quel code HTTP recevez-vous ?

Exercice 4 : Observer le cycle de vie du token

Objectif : Comprendre l'expiration et le rafraichissement des tokens.

  1. Obtenez un token avec curl (voir exercice 3)
  2. Notez la valeur de expires_in (en secondes)
  3. Attendez que le token expire (5 minutes par defaut)
  4. Essayez d'appeler l'API avec le token expire — observez l'erreur 401
  5. Utilisez le refresh_token pour obtenir un nouveau token :
curl -s -X POST \
  "http://localhost:8080/realms/securite-lab/protocol/openid-connect/token" \
  -d "grant_type=refresh_token&client_id=securite-lab-app&client_secret=dev-secret-change-in-production&refresh_token=VOTRE_REFRESH_TOKEN"
  1. Verifiez que le nouveau token fonctionne
  2. Bonus : Modifiez la duree de vie du token dans Keycloak (Realm settings > Tokens) et observez l'impact

Exercice 5 : Decoder et modifier un JWT

Objectif : Comprendre la verification de la signature JWT.

  1. Obtenez un token et copiez l'access_token
  2. Allez sur jwt.io et collez le token
  3. Observez le header, le payload et la signature
  4. Dans le payload, changez le role de "user" a "admin"
  5. Copiez le token modifie et essayez d'appeler l'API avec
  6. Observez que l'API refuse le token modifie (signature invalide)
Lecon : C'est exactement pour cela que la verification de la signature est essentielle. Sans elle, n'importe qui pourrait forger un token avec des privileges eleves.
