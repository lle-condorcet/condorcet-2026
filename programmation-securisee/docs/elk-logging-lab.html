ELK Logging Lab

Centralisation et analyse des logs avec Elasticsearch, Logstash et Kibana

Pourquoi centraliser les logs ?

Dans une architecture moderne, les applications generent des milliers de lignes de logs chaque minute. Sans centralisation, ces logs sont disperses sur differents serveurs, difficiles a correler et impossibles a analyser en temps reel. La centralisation des logs est un pilier fondamental de la securite informatique et de l'observabilite.

Les raisons principales de centraliser les logs :

  • Detection des intrusions — Identifier les tentatives d'attaque (injection SQL, XSS, brute force) en temps reel
  • Conformite reglementaire — RGPD, NIS2, PCI-DSS exigent la conservation et l'audit des logs
  • Diagnostic rapide — Correler les evenements entre plusieurs services pour trouver la cause racine
  • Monitoring de performance — Detecter les requetes lentes, les pics d'erreurs, les anomalies
  • Forensique — Reconstruire la chronologie d'un incident de securite

Qu'est-ce que la stack ELK ?

ELK est l'acronyme de trois projets open-source developpes par Elastic qui, ensemble, forment une plateforme complete de gestion des logs :

Composant Role Port par defaut
Elasticsearch Moteur de recherche et d'analyse distribue, stocke et indexe les logs 9200
Logstash Pipeline de traitement : recoit, transforme et envoie les logs vers Elasticsearch 5044, 5000
Kibana Interface web de visualisation : tableaux de bord, recherche, alertes 5601
Note : Dans notre lab, l'application .NET envoie les logs directement a Elasticsearch via le sink Serilog. Logstash est configure pour recevoir des logs supplementaires et les enrichir.

Configuration Serilog

Serilog est la bibliotheque de logging structuree la plus populaire pour .NET. Contrairement au logging standard qui produit du texte brut, Serilog genere des evenements structures en JSON, parfaitement adaptes a l'indexation par Elasticsearch.

Packages NuGet

<!-- Packages Serilog dans le .csproj -->
<PackageReference Include="Serilog.AspNetCore" Version="9.0.0" />
<PackageReference Include="Serilog.Sinks.Elasticsearch" Version="10.0.0" />
<PackageReference Include="Serilog.Enrichers.Environment" Version="3.0.1" />
<PackageReference Include="Serilog.Enrichers.Process" Version="3.0.0" />
<PackageReference Include="Serilog.Enrichers.Thread" Version="4.0.0" />

Configuration dans Program.cs

using Serilog;
using Serilog.Events;
using Serilog.Sinks.Elasticsearch;

Log.Logger = new LoggerConfiguration()
    // Niveau minimum global
    .MinimumLevel.Debug()

    // Surcharges par namespace (reduire le bruit)
    .MinimumLevel.Override("Microsoft", LogEventLevel.Information)
    .MinimumLevel.Override("Microsoft.AspNetCore", LogEventLevel.Warning)
    .MinimumLevel.Override("Microsoft.EntityFrameworkCore", LogEventLevel.Information)

    // Enrichisseurs : ajoutent du contexte a chaque log
    .Enrich.FromLogContext()
    .Enrich.WithMachineName()
    .Enrich.WithProcessId()
    .Enrich.WithThreadId()
    .Enrich.WithEnvironmentName()
    .Enrich.WithProperty("Application", "ElkLoggingLabApp")

    // Sink Console (developpement local)
    .WriteTo.Console(outputTemplate:
        "[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj} {Properties:j}{NewLine}{Exception}")

    // Sink Elasticsearch (centralisation)
    .WriteTo.Elasticsearch(new ElasticsearchSinkOptions(
        new Uri("http://localhost:9200"))
    {
        AutoRegisterTemplate = true,
        IndexFormat = "elklab-logs-{0:yyyy.MM.dd}",
        NumberOfShards = 1,
        NumberOfReplicas = 0,
    })
    .CreateLogger();

Les enrichisseurs expliques

Enrichisseur Champ ajoute Utilite
WithMachineName MachineName Identifier le serveur source dans un cluster
WithProcessId ProcessId Distinguer les instances de l'application
WithThreadId ThreadId Diagnostiquer les problemes de concurrence
WithEnvironmentName EnvironmentName Distinguer les environnements (Dev, Staging, Prod)
FromLogContext Proprietes dynamiques Ajouter du contexte specifique a chaque requete

Logging des requetes HTTP

Le RequestLoggingMiddleware intercepte chaque requete HTTP entrante et genere des logs structures contenant toutes les informations necessaires au monitoring et au debugging.

Informations capturees

  • Methode HTTP — GET, POST, PUT, DELETE, etc.
  • Chemin et query string — URL complete de la requete
  • Code de statut — 200, 404, 500, etc.
  • Duree — Temps de traitement en millisecondes
  • Adresse IP client — Pour le suivi et le rate limiting
  • User Agent — Navigateur ou client HTTP utilise
  • Taille requete/reponse — En octets
  • Correlation ID — Identifiant unique pour tracer la requete

Implementation du middleware

public async Task InvokeAsync(HttpContext context)
{
    // Generer ou recuperer le Correlation ID
    var correlationId = context.Request.Headers["X-Correlation-ID"]
        .FirstOrDefault() ?? Guid.NewGuid().ToString("N");
    context.Items["CorrelationId"] = correlationId;
    context.Response.Headers["X-Correlation-ID"] = correlationId;

    var stopwatch = Stopwatch.StartNew();

    // Log de debut de requete
    _logger.LogInformation(
        "HTTP {Method} {Path} started | IP: {ClientIp} | CorrelationId: {CorrelationId}",
        method, path, clientIp, correlationId);

    await _next(context);
    stopwatch.Stop();

    // Niveau de log adapte au code de statut
    var logLevel = statusCode >= 500 ? LogLevel.Error
        : statusCode >= 400 ? LogLevel.Warning
        : LogLevel.Information;

    // Detection des requetes lentes
    if (duration > 500)
        _logger.LogWarning("SLOW REQUEST: {Method} {Path} took {Duration}ms",
            method, path, duration);
}
Astuce : Le niveau de log est automatiquement ajuste en fonction du code de statut HTTP. Les erreurs 5xx generent des logs Error, les 4xx des Warning, et les 2xx des Information.

Detection des requetes EF Core lentes

Les requetes de base de donnees lentes sont l'une des causes les plus frequentes de degradation de performance. Notre application configure Entity Framework Core pour mesurer le temps d'execution de chaque requete SQL et generer des alertes selon des seuils configurables.

Seuils de detection

Duree Niveau de log Action
< 100ms Normal Pas de log supplementaire
100ms - 500ms Warning Log d'avertissement avec la requete SQL
> 500ms Error Log d'erreur + visible dans le dashboard Kibana

Configuration dans Program.cs

builder.Services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlite(connectionString);

    options.LogTo(
        (eventId, level) => eventId.Id ==
            RelationalEventId.CommandExecuted.Id,
        eventData =>
        {
            if (eventData is CommandExecutedEventData cmdData)
            {
                var duration = cmdData.Duration.TotalMilliseconds;

                if (duration > 500)
                    Log.Error(
                        "EF SLOW QUERY ({Duration}ms): {Command}",
                        duration, cmdData.Command.CommandText);
                else if (duration > 100)
                    Log.Warning(
                        "EF MODERATE QUERY ({Duration}ms): {Command}",
                        duration, cmdData.Command.CommandText);
            }
        });
});

Audit de securite

Le SecurityAuditMiddleware analyse chaque requete entrante pour detecter des patterns d'attaque courants. C'est une couche de defense en profondeur qui ne bloque pas les requetes mais les signale pour investigation.

Patterns detectes

Injection SQL

  • Mots-cles SQL : SELECT, UNION, DROP
  • Caracteres speciaux : --, ;, '
  • Tautologies : OR 1=1, AND 1=1

Cross-Site Scripting (XSS)

  • Balises script : <script>
  • Protocoles : javascript:
  • Handlers : onerror=, onload=
  • Iframes malveillants

Detection des methodes HTTP suspectes

private static readonly HashSet<string> SuspiciousMethods = new()
{
    "TRACE", "TRACK", "CONNECT", "OPTIONS"
};

if (SuspiciousMethods.Contains(context.Request.Method))
{
    _logger.LogWarning(
        "SECURITY: Suspicious HTTP method {Method} from {ClientIp}",
        context.Request.Method, clientIp);
}

Rate limiting basique

Le middleware suit le nombre de requetes par adresse IP et genere un avertissement lorsqu'un client depasse 50 requetes par minute :

// Verifier le taux de requetes par IP
if (requestCount > 50)
{
    _logger.LogWarning(
        "SECURITY: Rate limit exceeded for {ClientIp} | Requests: {Count}",
        clientIp, requestCount);
}

Alertes et notifications

Kibana permet de configurer des regles d'alerte qui declenchent des notifications lorsque certaines conditions sont remplies.

Creer une alerte de securite

1
Dans Kibana, aller dans Stack Management → Rules and Connectors
2
Creer une nouvelle regle de type Elasticsearch query
3
Configurer la requete pour detecter les evenements de securite :
{
  "query": {
    "bool": {
      "must": [
        { "match": { "level": "Fatal" } },
        { "wildcard": { "message": "*SECURITY*" } }
      ],
      "filter": [
        { "range": { "@timestamp": { "gte": "now-5m" } } }
      ]
    }
  }
}

Correlation des logs

La correlation des logs est la capacite a relier tous les evenements generes par une meme requete HTTP. C'est essentiel pour le debugging et l'investigation d'incidents.

Fonctionnement du Correlation ID

// Le middleware genere un ID unique pour chaque requete
var correlationId = context.Request.Headers["X-Correlation-ID"]
    .FirstOrDefault() ?? Guid.NewGuid().ToString("N");

// L'ID est propage dans la reponse HTTP
context.Response.Headers["X-Correlation-ID"] = correlationId;

// Et inclus dans chaque message de log
_logger.LogInformation(
    "... | CorrelationId: {CorrelationId}", correlationId);

Recherche par Correlation ID dans Kibana

Pour retrouver tous les logs d'une requete specifique :

# Dans la barre de recherche Kibana (KQL) :
fields.CorrelationId: "a1b2c3d4e5f6"

Cela affiche chronologiquement :

  1. Le log de debut de requete (methode, path, IP)
  2. Les logs de traitement (service, requetes SQL)
  3. Les eventuels avertissements de securite
  4. Le log de fin de requete (statut, duree)
Bonne pratique : Si votre architecture comporte plusieurs microservices, propagez le X-Correlation-ID entre les appels HTTP. Ainsi, vous pouvez tracer une requete utilisateur a travers tout le systeme.

Bonnes pratiques de logging

Ce qu'il faut logger

A faire

  • Requetes HTTP entrantes (methode, path, duree, statut)
  • Erreurs et exceptions avec stack trace
  • Tentatives d'authentification (succes et echecs)
  • Operations CRUD sur les donnees sensibles
  • Modifications de configuration
  • Requetes de base de donnees lentes
  • Evenements de securite (tentatives d'injection, rate limiting)
  • Correlation IDs pour le tracage distribue

A ne JAMAIS logger

  • Mots de passe — Ni en clair, ni hashes
  • Tokens d'authentification — JWT, API keys, session tokens
  • Donnees personnelles sensibles — Numeros de carte bancaire, IBAN
  • Donnees de sante — Informations medicales (RGPD/HIPAA)
  • Cles de chiffrement — Cles privees, secrets cryptographiques
  • Corps de requete complet — Peut contenir des donnees sensibles

Niveaux de log et leur usage

Niveau Usage Exemple
Trace Details tres fins, rarement active en production Entree/sortie de methodes internes
Debug Informations utiles au developpement Valeur d'une variable, chemin d'execution
Information Flux normal de l'application Requete traitee, commande creee
Warning Situation anormale mais non bloquante Requete lente, tentative de rate limiting
Error Erreur qui empeche une operation Exception non geree, echec d'appel externe
Fatal Erreur critique, arret de l'application Base de donnees inaccessible, configuration manquante

Retention des logs

En production, configurez des politiques de retention dans Elasticsearch via ILM (Index Lifecycle Management) :

  • Hot — 7 jours : index actifs, recherche rapide
  • Warm — 30 jours : index en lecture seule, moins de resources
  • Cold — 90 jours : archivage, recherche lente acceptable
  • Delete — Apres 90 jours (sauf obligation reglementaire)
Conformite : Verifiez les obligations de retention de votre secteur. PCI-DSS exige 1 an minimum, NIS2 impose des durees specifiques selon le type de donnees.
