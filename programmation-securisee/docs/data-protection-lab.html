Data Protection Lab

Protection des secrets de configuration et chiffrement des donnees sensibles avec .NET

Objectifs du laboratoire

  • Comprendre pourquoi stocker des secrets dans appsettings.json est dangereux
  • Apprendre a utiliser User Secrets pour le developpement local
  • Maitriser l'API Data Protection pour chiffrer/dechiffrer des donnees
  • Comparer les approches vulnerables et securisees

Prerequis

  • .NET 10 SDK installe
  • Un editeur de code (VS Code, Visual Studio, Rider)
  • Connaissances de base en ASP.NET MVC

Lancer le laboratoire

# Cloner le depot et naviguer vers le projet
cd DataProtectionLabApp
dotnet run

L'application demarre sur http://localhost:5400.

User Secrets : le probleme

De nombreux developpeurs stockent leurs secrets (mots de passe, cles API, chaines de connexion) directement dans appsettings.json. Ce fichier est commite dans Git et visible par tous les contributeurs du projet.

Risque : Meme apres suppression, les secrets restent dans l'historique Git. Des outils comme git log, truffleHog ou git-secrets peuvent les retrouver.

Demo : secrets en clair

Dans le labo, la page Secrets Vulnerable montre :

  • Les secrets lus depuis appsettings.json via IConfiguration
  • Le contenu brut du fichier de configuration
  • Une simulation d'historique Git revelant les secrets

appsettings.json (dangereux)

{
  "ConnectionStrings": {
    "DefaultConnection": "Server=prod;Password=Secret123!"
  },
  "ApiKeys": {
    "PaymentGateway": "sk_live_4242..."
  }
}

appsettings.json (securise)

{
  "ConnectionStrings": {
    "DefaultConnection": ""
  },
  "ApiKeys": {
    "PaymentGateway": ""
  }
}
// Vrais secrets dans User Secrets

Solution : User Secrets

User Secrets est un mecanisme integre a .NET qui stocke les secrets en dehors du projet, dans le profil utilisateur. Ces secrets ne sont jamais commites dans Git.

Ou sont stockes les secrets ?

Systeme Chemin
Windows %APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json
Linux / macOS ~/.microsoft/usersecrets/<UserSecretsId>/secrets.json

Commandes CLI

# Initialiser User Secrets dans le projet
dotnet user-secrets init

# Ajouter un secret
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=localhost;Database=DevDB"

# Lister les secrets
dotnet user-secrets list

# Supprimer un secret
dotnet user-secrets remove "ApiKeys:PaymentGateway"

# Supprimer tous les secrets
dotnet user-secrets clear

Data Protection API : le probleme

Meme avec des secrets bien geres, les donnees sensibles (numeros de carte, IBAN, mots de passe) sont souvent stockees en clair dans la base de donnees. En cas de compromission, toutes les donnees sont directement exploitables.

Demo : donnees en clair

La page Chiffrement Vulnerable simule une base de donnees contenant :

  • Numeros de cartes bancaires
  • IBAN
  • Mots de passe
  • Numeros nationaux

Toutes ces donnees sont stockees et affichees en clair.

Solution : Data Protection API

L'API Data Protection de .NET fournit un mecanisme de chiffrement simple et securise.

Configuration

// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDataProtection(); // Enregistrer le service

Utilisation dans un controleur

public class EncryptionController : Controller
{
    private readonly IDataProtector _protector;

    public EncryptionController(IDataProtectionProvider provider)
    {
        _protector = provider.CreateProtector("MonApp.Purpose");
    }

    public string Chiffrer(string data)
    {
        return _protector.Protect(data);
    }

    public string Dechiffrer(string cipher)
    {
        return _protector.Unprotect(cipher);
    }
}
Note : Le parametre purpose dans CreateProtector("purpose") isole les cles. Un protecteur cree avec un purpose different ne peut pas dechiffrer les donnees d'un autre.

Chiffrement a expiration

L'API permet de creer des jetons chiffres avec une duree de vie limitee, utile pour les tokens de reinitialisation de mot de passe ou les liens temporaires. 

var timeLimited = _protector.ToTimeLimitedDataProtector();

// Chiffrer avec expiration de 30 minutes
var cipher = timeLimited.Protect(data, TimeSpan.FromMinutes(30));

// Dechiffrer (echoue si expire)
try
{
    var plain = timeLimited.Unprotect(cipher);
}
catch (CryptographicException)
{
    // Le jeton a expire !
}

Hierarchie de configuration .NET

Priorite Source Usage
1 (basse) appsettings.json Valeurs par defaut (pas de secrets)
2 appsettings.{Env}.json Surcharges par environnement
3 User Secrets Developpement local
4 Variables d'environnement Production (Azure, Docker)
5 (haute) Arguments CLI Surcharges ponctuelles

Bonnes pratiques

  • Jamais de secrets dans le code source — utiliser User Secrets ou des variables d'environnement
  • Ajouter appsettings.*.json au .gitignore si necessaire
  • Utiliser un coffre-fort de secrets en production — Azure Key Vault, AWS Secrets Manager, HashiCorp Vault
  • Chiffrer les donnees sensibles au repos — Data Protection API, chiffrement de colonne SQL
  • Rotation reguliere des secrets — changer les cles API et mots de passe periodiquement
  • Principe du moindre privilege — chaque service n'accede qu'aux secrets dont il a besoin
  • Scanner l'historique Git — utiliser des outils comme truffleHog ou git-secrets
