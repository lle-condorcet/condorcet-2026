Chiffrement en Base de Donnees

PostgreSQL & EF Core — Du stockage en clair au chiffrement avance

Dans une architecture moderne, la base de donnees est souvent la cible principale d'un attaquant. Elle contient les donnees les plus sensibles : numeros de securite sociale, salaires, coordonnees bancaires, donnees medicales. La defense en profondeur exige de proteger ces donnees meme si un attaquant parvient a acceder au serveur de base de donnees.

RGPD (Article 32) — Le reglement europeen impose la mise en oeuvre de mesures techniques appropriees, dont le chiffrement, pour garantir la securite des donnees personnelles.

Ce laboratoire presente 5 patterns progressifs de protection des donnees en base :

  1. Stockage en clair — le probleme a resoudre
  2. Value Converters + Data Protection API — chiffrement applicatif simple
  3. AES-256-CBC + HMAC-SHA256 — chiffrement applicatif avance
  4. pgcrypto — chiffrement cote serveur natif PostgreSQL
  5. TDE / Chiffrement au niveau du disque — chiffrement au repos

Pattern 1 : Stockage en Clair (Vulnerable)

Le premier reflexe de nombreux developpeurs est de stocker les donnees telles quelles dans la base. C'est rapide, simple, et catastrophiquement dangereux pour les donnees sensibles.

Le modele (EmployeClair)

public class Patient
{
    public int Id { get; set; }
    public string Nom { get; set; } = "";
    public string NumeroSecu { get; set; } = "";     // Numero de securite sociale
    public string Diagnostic { get; set; } = "";    // Donnee medicale sensible
    public string IBAN { get; set; } = "";          // Coordonnees bancaires
    public decimal Salaire { get; set; }              // Remuneration
}

Ce que voit un attaquant dans la base

id nom numero_secu diagnostic iban salaire
1 Jean Dupont 1 85 12 75 108 234 56 Diabete type 2 FR76 1234 5678 9012 3456 3200.00
2 Marie Martin 2 91 03 69 042 567 89 Hypertension FR76 9876 5432 1098 7654 4100.00
Toutes les donnees sont lisibles ! Un simple SELECT * FROM patients; expose l'integralite des informations sensibles.

Scenarios d'attaque

  • Vol de backup — Les fichiers pg_dump contiennent les donnees en clair. Un disque dur vole = toutes les donnees exposees.
  • Injection SQL — Un attaquant qui exploite une faille SQL Injection peut lire directement toutes les colonnes.
  • DBA malveillant — Un administrateur de base de donnees a un acces complet et non audite aux donnees.
  • Compromission du serveur — Si le serveur PostgreSQL est compromis, aucune couche de protection supplementaire n'existe.

Le DbContext basique (aucune protection)

public class ClearTextDbContext : DbContext
{
    public DbSet<Patient> Patients { get; set; }

    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {
        options.UseNpgsql(
            "Host=localhost;Database=EncryptionLab;Username=postgres;Password=secret"
        );
    }

    // Aucune protection - les donnees sont stockees telles quelles
    // C'est le comportement par defaut d'EF Core
}

Pattern 2 : Value Converters + Data Protection API

La premiere solution consiste a utiliser le systeme de Data Protection integre a ASP.NET Core, combine avec les Value Converters d'EF Core pour chiffrer/dechiffrer automatiquement les donnees lors de la lecture et de l'ecriture.

Qu'est-ce que la Data Protection API ?

La Data Protection API est un framework de chiffrement integre a ASP.NET Core. Elle gere automatiquement les cles de chiffrement, leur rotation, et fournit une API simple basee sur le concept de purpose strings (chaines de contexte).

  • Purpose string : identifie le contexte de chiffrement (ex: "PatientData.NumeroSecu"). Deux purpose strings differentes produisent des cles differentes.
  • Gestion des cles : les cles sont stockees par defaut dans ~/.aspnet/DataProtection-Keys (Linux) ou %LOCALAPPDATA%\ASP.NET\DataProtection-Keys (Windows).
  • Rotation automatique : les cles sont automatiquement renouvelees tous les 90 jours.

Creation du ValueConverter

public static class EncryptedConverter
{
    public static ValueConverter<string, string> Create(
        IDataProtectionProvider provider,
        string purpose)
    {
        var protector = provider.CreateProtector(purpose);

        return new ValueConverter<string, string>(
            v => protector.Protect(v),        // Ecriture : chiffre
            v => protector.Unprotect(v)      // Lecture : dechiffre
        );
    }
}

Application dans OnModelCreating

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    var converter = EncryptedConverter.Create(
        _provider, "PatientData");

    modelBuilder.Entity<Patient>(entity =>
    {
        entity.Property(e => e.NumeroSecu)
              .HasConversion(converter)
              .HasMaxLength(500);  // Le texte chiffre est plus long

        entity.Property(e => e.Diagnostic)
              .HasConversion(converter)
              .HasMaxLength(500);

        entity.Property(e => e.IBAN)
              .HasConversion(converter)
              .HasMaxLength(500);
    });
}

Limitations importantes

Attention : Les Value Converters chiffrent les donnees cote application. Cela implique des limitations significatives.
  • Pas de clause WHERE — Impossible de faire WHERE numero_secu = '...' car la valeur chiffree change a chaque chiffrement (IV aleatoire cote DPAPI).
  • Pas d'indexation — Les index sur les colonnes chiffrees sont inutiles.
  • Dependance aux cles — Si les cles de Data Protection sont perdues, les donnees sont irrecuperables.
  • Tri impossible — ORDER BY sur les colonnes chiffrees donne des resultats incoherents.

    public DbSet<Patient> Patients { get; set; }

    }
}

Pattern 3 : AES-256-CBC + HMAC-SHA256

Pour un controle total sur le chiffrement, on peut implementer manuellement un service utilisant AES-256 en mode CBC avec un HMAC-SHA256 pour garantir l'integrite. C'est le pattern Encrypt-then-MAC, considere comme la reference en cryptographie symetrique.

Pourquoi un chiffrement manuel ?

  • Portabilite — Fonctionne avec n'importe quelle base de donnees (PostgreSQL, SQL Server, MySQL, SQLite, etc.)
  • Controle des cles — Vous decidez ou et comment stocker les cles
  • Audit — Le code est inspectable et verifiable par un auditeur de securite
  • Independance — Pas de dependance a un framework specifique

Flux de chiffrement

┌─────────────────────────────────────────────────────────────────┐
│                    ENCRYPT-THEN-MAC FLOW                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Texte clair                                                    │
│      │                                                          │
│      ▼                                                          │
│  ┌──────────────────────┐                                       │
│  │  AES-256-CBC(key, IV)│  ◄── IV aleatoire (16 bytes)         │
│  └──────────┬───────────┘                                       │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────┐                                       │
│  │  IV + Ciphertext     │                                       │
│  └──────────┬───────────┘                                       │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────────────┐                               │
│  │  HMAC-SHA256(hmac_key,      │  ◄── Cle HMAC separee         │
│  │            IV + Ciphertext) │                                │
│  └──────────┬───────────────────┘                               │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────────────┐                               │
│  │  Base64(IV + Ciphertext     │                                │
│  │         + HMAC tag)         │  → Stocke en base              │
│  └──────────────────────────────┘                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Le pattern Encrypt-then-MAC

Il existe trois facons de combiner chiffrement et MAC :

Methode Ordre Securite
MAC-then-Encrypt HMAC(clair) puis Encrypt(clair + MAC) Vulnerable (padding oracle)
Encrypt-and-MAC Encrypt(clair) + HMAC(clair) Fuite potentielle via MAC
Encrypt-then-MAC Encrypt(clair) puis HMAC(chiffre) Recommande (prouve sur)

Protection contre les attaques temporelles : FixedTimeEquals

Lors de la verification du HMAC, il est crucial d'utiliser une comparaison a temps constant. Une comparaison classique (==) s'arrete au premier octet different, ce qui permet a un attaquant de deviner le HMAC octet par octet en mesurant le temps de reponse.

Comparaison classique (vulnerable)

// DANGEREUX : timing attack possible
if (computedMac.SequenceEqual(storedMac))
{
    // S'arrete au 1er octet different
    // → fuite d'information temporelle
}

Comparaison a temps constant (sure)

// SUR : temps constant quel que soit
// le nombre d'octets corrects
if (CryptographicOperations
    .FixedTimeEquals(computedMac, storedMac))
{
    // Compare TOUS les octets
}

Service AesEncryptionService complet

public class AesEncryptionService
{
    private readonly byte[] _encryptionKey; // 32 bytes = AES-256
    private readonly byte[] _hmacKey;       // 32 bytes pour HMAC-SHA256

    public AesEncryptionService(string encKey, string hmacKey)
    {
        _encryptionKey = Convert.FromBase64String(encKey);
        _hmacKey = Convert.FromBase64String(hmacKey);

        if (_encryptionKey.Length != 32)
            throw new ArgumentException("La cle AES doit faire 256 bits (32 octets)");
        if (_hmacKey.Length != 32)
            throw new ArgumentException("La cle HMAC doit faire 256 bits (32 octets)");
    }

    public string Encrypt(string plainText)
    {
        using var aes = Aes.Create();
        aes.Key = _encryptionKey;
        aes.Mode = CipherMode.CBC;
        aes.Padding = PaddingMode.PKCS7;
        aes.GenerateIV();  // IV aleatoire a chaque chiffrement

        using var encryptor = aes.CreateEncryptor();
        var plainBytes = Encoding.UTF8.GetBytes(plainText);
        var cipherBytes = encryptor.TransformFinalBlock(
            plainBytes, 0, plainBytes.Length);

        // Concatener IV + Ciphertext
        var ivAndCipher = new byte[aes.IV.Length + cipherBytes.Length];
        Buffer.BlockCopy(aes.IV, 0, ivAndCipher, 0, aes.IV.Length);
        Buffer.BlockCopy(cipherBytes, 0, ivAndCipher, aes.IV.Length, cipherBytes.Length);

        // Calculer HMAC sur IV + Ciphertext (Encrypt-then-MAC)
        using var hmac = new HMACSHA256(_hmacKey);
        var mac = hmac.ComputeHash(ivAndCipher);

        // Resultat final : IV + Ciphertext + MAC
        var result = new byte[ivAndCipher.Length + mac.Length];
        Buffer.BlockCopy(ivAndCipher, 0, result, 0, ivAndCipher.Length);
        Buffer.BlockCopy(mac, 0, result, ivAndCipher.Length, mac.Length);

        return Convert.ToBase64String(result);
    }

    public string Decrypt(string cipherText)
    {
        var fullBytes = Convert.FromBase64String(cipherText);

        // Separer les composants : IV(16) + Ciphertext(N) + MAC(32)
        const int ivLength = 16;
        const int macLength = 32;
        var ivAndCipherLength = fullBytes.Length - macLength;

        var ivAndCipher = fullBytes[..ivAndCipherLength];
        var storedMac = fullBytes[ivAndCipherLength..];

        // Verifier le HMAC AVANT de dechiffrer (crucial !)
        using var hmac = new HMACSHA256(_hmacKey);
        var computedMac = hmac.ComputeHash(ivAndCipher);

        if (!CryptographicOperations.FixedTimeEquals(computedMac, storedMac))
            throw new CryptographicException("Integrite compromise : HMAC invalide");

        // Extraire IV et Ciphertext
        var iv = ivAndCipher[..ivLength];
        var cipherBytes = ivAndCipher[ivLength..];

        using var aes = Aes.Create();
        aes.Key = _encryptionKey;
        aes.IV = iv;
        aes.Mode = CipherMode.CBC;
        aes.Padding = PaddingMode.PKCS7;

        using var decryptor = aes.CreateDecryptor();
        var plainBytes = decryptor.TransformFinalBlock(
            cipherBytes, 0, cipherBytes.Length);

        return Encoding.UTF8.GetString(plainBytes);
    }
}

Integration avec EF Core via ValueConverter

{

    );

Pattern 4 : pgcrypto (PostgreSQL)

pgcrypto est une extension native de PostgreSQL qui fournit des fonctions cryptographiques directement dans le moteur de base de donnees. Contrairement aux patterns precedents (chiffrement cote application), pgcrypto effectue le chiffrement et le dechiffrement cote serveur SQL.

Activer l'extension pgcrypto

-- Activer l'extension (une seule fois par base de donnees)
CREATE EXTENSION IF NOT EXISTS pgcrypto;
Note : L'extension pgcrypto est incluse dans les distributions standard de PostgreSQL. Aucune installation supplementaire n'est necessaire sur la plupart des systemes.

Fonctions principales de pgcrypto

Fonction Usage Type
pgp_sym_encrypt() Chiffrement symetrique (mot de passe) AES-128/256
pgp_sym_decrypt() Dechiffrement symetrique AES-128/256
pgp_pub_encrypt() Chiffrement asymetrique (cle publique) RSA/DSA
pgp_pub_decrypt() Dechiffrement asymetrique (cle privee) RSA/DSA
crypt() Hachage de mots de passe bcrypt, md5, etc.
gen_salt() Generation de sel pour crypt() Aleatoire
gen_random_bytes() Generation d'octets aleatoires CSPRNG

Architecture

┌────────────────────────┐        ┌─────────────────────────┐
│    APPLICATION         │        │    POSTGRESQL            │
│                        │        │                          │
│  Envoie les donnees    │        │  pgcrypto chiffre/       │
│  en clair + la cle     │        │  dechiffre les donnees   │
│  ┌──────────────────┐  │        │  ┌────────────────────┐  │
│  │ "Jean Dupont"    │  │        │  │ \x7f3a...9b2e      │  │
│  │ "1 85 12 75..."  │  │  ───►  │  │ (BYTEA chiffre)    │  │
│  └──────────────────┘  │        │  └────────────────────┘  │
│                        │        │                          │
│  SQL avec appels       │        │  Les donnees chiffrees   │
│  pgp_sym_encrypt()     │        │  sont stockees en BYTEA  │
│                        │        │                          │
└────────────────────────┘        └─────────────────────────┘
Attention : Avec pgcrypto, la cle de chiffrement transite dans les requetes SQL. Il est imperatif d'utiliser une connexion TLS (SSL) entre l'application et PostgreSQL pour proteger la cle en transit.

Creer la table avec colonnes BYTEA

-- Les colonnes chiffrees utilisent le type BYTEA
CREATE TABLE patients_pgcrypto (
    id SERIAL PRIMARY KEY,
    nom VARCHAR(100),
    numero_secu BYTEA,       -- Chiffre avec pgp_sym_encrypt
    diagnostic BYTEA,        -- Chiffre avec pgp_sym_encrypt
    iban BYTEA,              -- Chiffre avec pgp_sym_encrypt
    salaire NUMERIC(10,2)
);

Chiffrement symetrique avec pgp_sym_encrypt

-- Insertion avec chiffrement symetrique
INSERT INTO patients_pgcrypto (nom, numero_secu, diagnostic, iban, salaire)
VALUES (
    'Jean Dupont',
    pgp_sym_encrypt('1 85 12 75 108 234 56', 'ma_cle_secrete'),
    pgp_sym_encrypt('Diabete type 2', 'ma_cle_secrete'),
    pgp_sym_encrypt('FR76 1234 5678 9012 3456', 'ma_cle_secrete'),
    3200.00
);

-- Lecture avec dechiffrement
SELECT
    nom,
    pgp_sym_decrypt(numero_secu, 'ma_cle_secrete') AS numero_secu,
    pgp_sym_decrypt(diagnostic, 'ma_cle_secrete') AS diagnostic,
    pgp_sym_decrypt(iban, 'ma_cle_secrete') AS iban,
    salaire
FROM patients_pgcrypto;

Chiffrement asymetrique avec pgp_pub_encrypt

-- Generer une paire de cles GPG (en ligne de commande)
-- gpg --gen-key
-- gpg --export -a "MonIdentite" > public.key
-- gpg --export-secret-keys -a "MonIdentite" > private.key

-- Chiffrement avec la cle publique
INSERT INTO patients_pgcrypto (nom, numero_secu)
VALUES (
    'Marie Martin',
    pgp_pub_encrypt(
        '2 91 03 69 042 567 89',
        dearmor('-----BEGIN PGP PUBLIC KEY BLOCK-----
...contenu de la cle publique...
-----END PGP PUBLIC KEY BLOCK-----')
    )
);

-- Dechiffrement avec la cle privee
SELECT nom,
    pgp_pub_decrypt(
        numero_secu,
        dearmor('-----BEGIN PGP PRIVATE KEY BLOCK-----
...contenu de la cle privee...
-----END PGP PRIVATE KEY BLOCK-----')
    ) AS numero_secu
FROM patients_pgcrypto;

Hachage de mots de passe avec crypt() et gen_salt()

-- Creer une table d'utilisateurs avec mots de passe haches
CREATE TABLE utilisateurs (
    id SERIAL PRIMARY KEY,
    login VARCHAR(50) UNIQUE NOT NULL,
    mot_de_passe TEXT NOT NULL
);

-- Insertion avec hachage bcrypt
INSERT INTO utilisateurs (login, mot_de_passe)
VALUES (
    'admin',
    crypt('MonMotDePasse123!', gen_salt('bf', 12))
);

-- Verification d'un mot de passe
SELECT id, login
FROM utilisateurs
WHERE login = 'admin'
  AND mot_de_passe = crypt('MonMotDePasse123!', mot_de_passe);
bcrypt est recommande : L'algorithme 'bf' (bcrypt) est le plus sur pour le hachage de mots de passe. Le parametre de cout (ici 12) controle le nombre d'iterations : plus il est eleve, plus le hachage est lent et resistant aux attaques par force brute.

Generation d'octets aleatoires

-- Generer 32 octets aleatoires (pour une cle AES-256)
SELECT encode(gen_random_bytes(32), 'hex') AS cle_aleatoire;

-- Generer un UUID v4 aleatoire
SELECT gen_random_uuid();

-- Generer un token base64
SELECT encode(gen_random_bytes(48), 'base64') AS token;

Limitations de pgcrypto

  • Cle dans les requetes — La cle de chiffrement apparait dans les requetes SQL et dans les logs si log_statement = 'all'. Desactivez la journalisation des requetes sensibles.
  • Pas de gestion de cles integree — Contrairement a Always Encrypted (SQL Server), il n'y a pas de hierarchie de cles automatique.
  • Pas de recherche sur les colonnes chiffrees — Impossible de faire un WHERE sur une colonne chiffree sans la dechiffrer d'abord (impact performance).
  • Le serveur voit la cle — Le chiffrement est cote serveur, donc un DBA avec acces aux logs peut intercepter la cle.

Pattern 5 : TDE / Chiffrement au niveau du disque

Contrairement a SQL Server qui propose nativement le TDE (Transparent Data Encryption), PostgreSQL communautaire ne dispose pas de TDE integre. Plusieurs approches existent pour obtenir un chiffrement au repos equivalent.

Option A : pg_tde (extension)

L'extension pg_tde (developpee par Percona et d'autres contributeurs) ajoute le chiffrement transparent des donnees au repos pour PostgreSQL. Elle chiffre les fichiers de donnees (tablespaces) de maniere transparente. 

-- Installer et activer pg_tde (necessite une compilation ou un package)
CREATE EXTENSION pg_tde;

-- Configurer la cle de chiffrement principale
SELECT pg_tde_add_key_provider_file(
    'local_keyfile',
    '/etc/postgresql/tde_keyfile.json'
);

-- Definir la cle principale
SELECT pg_tde_set_principal_key(
    'master_key',
    'local_keyfile'
);

-- Creer une table chiffree avec l'access method tde_heap
CREATE TABLE patients_tde (
    id SERIAL PRIMARY KEY,
    nom VARCHAR(100),
    numero_secu VARCHAR(50),
    diagnostic VARCHAR(500)
) USING tde_heap;
Note : pg_tde est une extension relativement recente. Pour les environnements de production, evaluez soigneusement sa maturite et son support avant de l'adopter.

Option B : LUKS (Linux Unified Key Setup)

LUKS est le standard de chiffrement de partitions sous Linux. Il permet de chiffrer le volume entier ou PostgreSQL stocke ses donnees (/var/lib/postgresql/data). 

# Etape 1 : Creer une partition chiffree LUKS
cryptsetup luksFormat /dev/sdb1

# Etape 2 : Ouvrir la partition
cryptsetup luksOpen /dev/sdb1 pg_encrypted

# Etape 3 : Creer le systeme de fichiers
mkfs.ext4 /dev/mapper/pg_encrypted

# Etape 4 : Monter le volume
mount /dev/mapper/pg_encrypted /var/lib/postgresql/data

# Etape 5 : Initialiser PostgreSQL sur le volume chiffre
pg_ctl initdb -D /var/lib/postgresql/data

# Verification du chiffrement
cryptsetup status pg_encrypted

Option C : Chiffrement complet du disque (Full-Disk Encryption)

Pour les environnements cloud ou virtualises, le chiffrement complet du disque est souvent la solution la plus simple :

  • AWS — EBS Encryption (AES-256, gere par AWS KMS)
  • Azure — Azure Disk Encryption (BitLocker / dm-crypt)
  • GCP — Persistent Disk Encryption (active par defaut)
  • On-premise — BitLocker (Windows), dm-crypt/LUKS (Linux)

Ce que le chiffrement au repos protege

  • Les fichiers de donnees PostgreSQL (base/, WAL, etc.)
  • Les sauvegardes (pg_dump, pg_basebackup)
  • Les fichiers temporaires
  • Les snapshots et replicas physiques

Ce que le chiffrement au repos ne protege PAS

Attention : Le chiffrement au repos ne protege pas contre un DBA malveillant. Toute personne avec un acces SELECT voit les donnees en clair, car le dechiffrement est transparent et automatique une fois le volume monte.
  • Les donnees en memoire (elles sont en clair dans shared_buffers)
  • Les donnees transmises sur le reseau (utilisez TLS/SSL pour ca)
  • Les acces SQL (un SELECT retourne les donnees en clair)
  • Les exports de donnees (pg_dump, COPY, etc.)
Sauvegardez les cles LUKS ! Sans la cle LUKS ou la passphrase, un volume chiffre est irrecuperable. Sauvegardez toujours les en-tetes LUKS et les passphrases dans un emplacement securise. 
# Sauvegarder l'en-tete LUKS (CRITIQUE !)
cryptsetup luksHeaderBackup /dev/sdb1 \
    --header-backup-file /secure/luks_header_backup.bin

# Ajouter une cle de recuperation supplementaire
cryptsetup luksAddKey /dev/sdb1

Quand utiliser le chiffrement au repos ?

  • Conformite reglementaire exigeant le chiffrement au repos
  • Protection contre le vol physique de disques ou de backups
  • En complement d'autres mecanismes (pgcrypto, chiffrement applicatif)
  • Quand vous ne pouvez pas modifier le code applicatif

Reference et Bonnes Pratiques

Gestion des cles

La securite du chiffrement repose entierement sur la protection des cles. Une cle compromise rend tout le chiffrement inutile.

  • HashiCorp Vault — Solution open-source de gestion de secrets avec journalisation des acces, rotation automatique, et integration avec PostgreSQL.
  • AWS KMS / Azure Key Vault / GCP KMS — Services cloud de gestion de cles avec audit et rotation.
  • HSM (Hardware Security Module) — Pour les environnements les plus sensibles, les cles ne quittent jamais le materiel dedie.
  • Rotation des cles — Definissez une politique de rotation (ex: tous les 90 jours pour les cles applicatives, annuelle pour les cles de chiffrement disque).
  • Separation des responsabilites — L'equipe qui gere les cles ne devrait pas etre la meme que celle qui gere la base de donnees.
  • Sauvegarde des cles — Toujours maintenir une copie securisee des cles hors site (disaster recovery).

Defense en profondeur

Le chiffrement n'est qu'une couche de la strategie de securite. Pour une protection complete, combinez plusieurs mecanismes :

  1. LUKS / Cloud KMS — Chiffrement au repos (fichiers et backups)
  2. pgcrypto — Chiffrement par colonne pour les donnees les plus sensibles
  3. Chiffrement applicatif (AES + HMAC) — Protection contre le DBA et le serveur compromis
  4. RLS (Row-Level Security) — Chaque utilisateur ne voit que ses propres donnees
  5. TLS 1.3 — Chiffrement des donnees en transit (sslmode=verify-full dans la chaine de connexion)
  6. pgAudit — Extension d'audit pour journaliser tous les acces aux donnees sensibles

Configuration TLS pour PostgreSQL

# Dans postgresql.conf
ssl = on
ssl_cert_file = '/etc/ssl/certs/server.crt'
ssl_key_file = '/etc/ssl/private/server.key'
ssl_min_protocol_version = 'TLSv1.3'

# Dans pg_hba.conf (forcer SSL)
hostssl  all  all  0.0.0.0/0  scram-sha-256

# Chaine de connexion cote application
"Host=db.example.com;Database=EncryptionLab;Username=app;Password=***;SslMode=VerifyFull;Root Certificate=/path/to/ca.crt"

Implications RGPD

Article 32 du RGPD : Le chiffrement est explicitement cite comme mesure technique appropriee. En cas de violation de donnees, les donnees chiffrees sont considerees comme non compromises si les cles n'ont pas ete exposees (Article 34 — exemption de notification).
  • Pseudonymisation — Le chiffrement des identifiants est une forme de pseudonymisation acceptee par le RGPD.
  • Droit a l'effacement — La destruction de la cle de chiffrement peut constituer un effacement cryptographique (crypto-shredding).
  • Notification de violation — Si les donnees chiffrees sont volees mais que les cles sont sures, l'obligation de notification aux personnes concernees peut etre levee.

Desactiver la journalisation des cles dans PostgreSQL

Critique : Si vous utilisez pgcrypto, assurez-vous que les requetes contenant des cles ne sont pas enregistrees dans les logs PostgreSQL. 
# Dans postgresql.conf
# Eviter de logger les requetes contenant des cles
log_statement = 'ddl'          -- Ne logger que les DDL, pas les DML
log_min_duration_statement = -1 -- Desactiver le log des requetes lentes

# Ou utiliser pg_stat_statements avec prudence
# Les requetes normalisees remplacent les parametres par $1, $2, etc.
# ce qui masque les cles dans les statistiques
