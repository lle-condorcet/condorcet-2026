Chiffrement en Base de Donnees

Oracle Database & EF Core — Du stockage en clair au chiffrement de niveau entreprise

Dans une architecture moderne, la base de donnees est souvent la cible principale d'un attaquant. Elle contient les donnees les plus sensibles : numeros de securite sociale, salaires, coordonnees bancaires, donnees medicales. La defense en profondeur exige de proteger ces donnees meme si un attaquant parvient a acceder au serveur de base de donnees.

RGPD (Article 32) — Le reglement europeen impose la mise en oeuvre de mesures techniques appropriees, dont le chiffrement, pour garantir la securite des donnees personnelles.

Ce laboratoire presente 5 patterns progressifs de protection des donnees en base :

  1. Stockage en clair — le probleme a resoudre
  2. Value Converters + Data Protection API — chiffrement applicatif simple
  3. AES-256-CBC + HMAC-SHA256 — chiffrement applicatif avance
  4. TDE + DBMS_CRYPTO — chiffrement natif Oracle (colonne et tablespace)
  5. Oracle Data Redaction — masquage dynamique base sur des politiques

Pattern 1 : Stockage en Clair (Vulnerable)

Le premier reflexe de nombreux developpeurs est de stocker les donnees telles quelles dans la base. C'est rapide, simple, et catastrophiquement dangereux pour les donnees sensibles.

Le modele (Patient)

public class Patient
{
    public int Id { get; set; }
    public string Nom { get; set; } = "";
    public string NumeroSecu { get; set; } = "";     // Numero de securite sociale
    public string Diagnostic { get; set; } = "";    // Donnee medicale sensible
    public string IBAN { get; set; } = "";          // Coordonnees bancaires
    public decimal Salaire { get; set; }              // Remuneration
}

Ce que voit un attaquant dans la base

ID NOM NUMERO_SECU DIAGNOSTIC IBAN SALAIRE
1 Jean Dupont 1 85 12 75 108 234 56 Diabete type 2 FR76 1234 5678 9012 3456 3200.00
2 Marie Martin 2 91 03 69 042 567 89 Hypertension FR76 9876 5432 1098 7654 4100.00
Toutes les donnees sont lisibles ! Un simple SELECT * FROM PATIENTS expose l'integralite des informations sensibles.

Scenarios d'attaque

  • Vol de backup — Les fichiers de datafile (.dbf) et les exports Data Pump contiennent les donnees en clair. Un disque dur vole = toutes les donnees exposees.
  • Injection SQL — Un attaquant qui exploite une faille SQL Injection peut lire directement toutes les colonnes.
  • DBA malveillant — Un administrateur de base de donnees a un acces complet et non audite aux donnees.
  • Compromission du serveur — Si le serveur Oracle est compromis, aucune couche de protection supplementaire n'existe.

Le DbContext basique (aucune protection)

public class ClearTextDbContext : DbContext
{
    public DbSet<Patient> Patients { get; set; }

    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {
        options.UseOracle(
            @"User Id=lab_user;Password=lab_password;Data Source=localhost:1521/FREEPDB1"
        );
    }

    // Aucune protection - les donnees sont stockees telles quelles
    // C'est le comportement par defaut d'EF Core
}

Pattern 2 : Value Converters + Data Protection API

La premiere solution consiste a utiliser le systeme de Data Protection integre a ASP.NET Core, combine avec les Value Converters d'EF Core pour chiffrer/dechiffrer automatiquement les donnees lors de la lecture et de l'ecriture.

Qu'est-ce que la Data Protection API ?

La Data Protection API est un framework de chiffrement integre a ASP.NET Core. Elle gere automatiquement les cles de chiffrement, leur rotation, et fournit une API simple basee sur le concept de purpose strings (chaines de contexte).

  • Purpose string : identifie le contexte de chiffrement (ex: "PatientData.NumeroSecu"). Deux purpose strings differentes produisent des cles differentes.
  • Gestion des cles : les cles sont stockees par defaut dans %LOCALAPPDATA%\ASP.NET\DataProtection-Keys.
  • Rotation automatique : les cles sont automatiquement renouvelees tous les 90 jours.

Creation du ValueConverter

public static class EncryptedConverter
{
    public static ValueConverter<string, string> Create(
        IDataProtectionProvider provider,
        string purpose)
    {
        var protector = provider.CreateProtector(purpose);

        return new ValueConverter<string, string>(
            v => protector.Protect(v),        // Ecriture : chiffre
            v => protector.Unprotect(v)      // Lecture : dechiffre
        );
    }
}

Application dans OnModelCreating

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    var converter = EncryptedConverter.Create(
        _provider, "PatientData");

    modelBuilder.Entity<Patient>(entity =>
    {
        entity.Property(e => e.NumeroSecu)
              .HasConversion(converter)
              .HasMaxLength(500);  // Le texte chiffre est plus long

        entity.Property(e => e.Diagnostic)
              .HasConversion(converter)
              .HasMaxLength(500);

        entity.Property(e => e.IBAN)
              .HasConversion(converter)
              .HasMaxLength(500);
    });
}

Limitations importantes

Attention : Les Value Converters chiffrent les donnees cote application. Cela implique des limitations significatives.
  • Pas de clause WHERE — Impossible de faire WHERE NUMERO_SECU = '...' car la valeur chiffree change a chaque chiffrement (IV aleatoire cote DPAPI).
  • Pas d'indexation — Les index sur les colonnes chiffrees sont inutiles.
  • Dependance aux cles — Si les cles de Data Protection sont perdues, les donnees sont irrecuperables.
  • Tri impossible — ORDER BY sur les colonnes chiffrees donne des resultats incoherents.

Pattern 3 : AES-256-CBC + HMAC-SHA256

Pour un controle total sur le chiffrement, on peut implementer manuellement un service utilisant AES-256 en mode CBC avec un HMAC-SHA256 pour garantir l'integrite. C'est le pattern Encrypt-then-MAC, considere comme la reference en cryptographie symetrique.

Pourquoi un chiffrement manuel ?

  • Portabilite — Fonctionne avec n'importe quelle base de donnees (Oracle, PostgreSQL, MySQL, SQLite, etc.)
  • Controle des cles — Vous decidez ou et comment stocker les cles
  • Audit — Le code est inspectable et verifiable par un auditeur de securite
  • Independance — Pas de dependance a un framework specifique

Flux de chiffrement

┌─────────────────────────────────────────────────────────────────┐
│                    ENCRYPT-THEN-MAC FLOW                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Texte clair                                                    │
│      │                                                          │
│      ▼                                                          │
│  ┌──────────────────────┐                                       │
│  │  AES-256-CBC(key, IV)│  ◄── IV aleatoire (16 bytes)         │
│  └──────────┬───────────┘                                       │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────┐                                       │
│  │  IV + Ciphertext     │                                       │
│  └──────────┬───────────┘                                       │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────────────┐                               │
│  │  HMAC-SHA256(hmac_key,      │  ◄── Cle HMAC separee         │
│  │            IV + Ciphertext) │                                │
│  └──────────┬───────────────────┘                               │
│             │                                                   │
│             ▼                                                   │
│  ┌──────────────────────────────┐                               │
│  │  Base64(IV + Ciphertext     │                                │
│  │         + HMAC tag)         │  → Stocke en base              │
│  └──────────────────────────────┘                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Le pattern Encrypt-then-MAC

Il existe trois facons de combiner chiffrement et MAC :

Methode Ordre Securite
MAC-then-Encrypt HMAC(clair) puis Encrypt(clair + MAC) Vulnerable (padding oracle)
Encrypt-and-MAC Encrypt(clair) + HMAC(clair) Fuite potentielle via MAC
Encrypt-then-MAC Encrypt(clair) puis HMAC(chiffre) Recommande (prouve sur)

Protection contre les attaques temporelles : FixedTimeEquals

Lors de la verification du HMAC, il est crucial d'utiliser une comparaison a temps constant. Une comparaison classique (==) s'arrete au premier octet different, ce qui permet a un attaquant de deviner le HMAC octet par octet en mesurant le temps de reponse.

Comparaison classique (vulnerable)

// DANGEREUX : timing attack possible
if (computedMac.SequenceEqual(storedMac))
{
    // S'arrete au 1er octet different
    // → fuite d'information temporelle
}

Comparaison a temps constant (sure)

// SUR : temps constant quel que soit
// le nombre d'octets corrects
if (CryptographicOperations
    .FixedTimeEquals(computedMac, storedMac))
{
    // Compare TOUS les octets
}

Service AesEncryptionService complet

public class AesEncryptionService
{
    private readonly byte[] _encryptionKey; // 32 bytes = AES-256
    private readonly byte[] _hmacKey;       // 32 bytes pour HMAC-SHA256

    public AesEncryptionService(string encKey, string hmacKey)
    {
        _encryptionKey = Convert.FromBase64String(encKey);
        _hmacKey = Convert.FromBase64String(hmacKey);

        if (_encryptionKey.Length != 32)
            throw new ArgumentException("La cle AES doit faire 256 bits (32 octets)");
        if (_hmacKey.Length != 32)
            throw new ArgumentException("La cle HMAC doit faire 256 bits (32 octets)");
    }

    public string Encrypt(string plainText)
    {
        using var aes = Aes.Create();
        aes.Key = _encryptionKey;
        aes.Mode = CipherMode.CBC;
        aes.Padding = PaddingMode.PKCS7;
        aes.GenerateIV();  // IV aleatoire a chaque chiffrement

        using var encryptor = aes.CreateEncryptor();
        var plainBytes = Encoding.UTF8.GetBytes(plainText);
        var cipherBytes = encryptor.TransformFinalBlock(
            plainBytes, 0, plainBytes.Length);

        // Concatener IV + Ciphertext
        var ivAndCipher = new byte[aes.IV.Length + cipherBytes.Length];
        Buffer.BlockCopy(aes.IV, 0, ivAndCipher, 0, aes.IV.Length);
        Buffer.BlockCopy(cipherBytes, 0, ivAndCipher, aes.IV.Length, cipherBytes.Length);

        // Calculer HMAC sur IV + Ciphertext (Encrypt-then-MAC)
        using var hmac = new HMACSHA256(_hmacKey);
        var mac = hmac.ComputeHash(ivAndCipher);

        // Resultat final : IV + Ciphertext + MAC
        var result = new byte[ivAndCipher.Length + mac.Length];
        Buffer.BlockCopy(ivAndCipher, 0, result, 0, ivAndCipher.Length);
        Buffer.BlockCopy(mac, 0, result, ivAndCipher.Length, mac.Length);

        return Convert.ToBase64String(result);
    }

    public string Decrypt(string cipherText)
    {
        var fullBytes = Convert.FromBase64String(cipherText);

        // Separer les composants : IV(16) + Ciphertext(N) + MAC(32)
        const int ivLength = 16;
        const int macLength = 32;
        var ivAndCipherLength = fullBytes.Length - macLength;

        var ivAndCipher = fullBytes[..ivAndCipherLength];
        var storedMac = fullBytes[ivAndCipherLength..];

        // Verifier le HMAC AVANT de dechiffrer (crucial !)
        using var hmac = new HMACSHA256(_hmacKey);
        var computedMac = hmac.ComputeHash(ivAndCipher);

        if (!CryptographicOperations.FixedTimeEquals(computedMac, storedMac))
            throw new CryptographicException("Integrite compromise : HMAC invalide");

        // Extraire IV et Ciphertext
        var iv = ivAndCipher[..ivLength];
        var cipherBytes = ivAndCipher[ivLength..];

        using var aes = Aes.Create();
        aes.Key = _encryptionKey;
        aes.IV = iv;
        aes.Mode = CipherMode.CBC;
        aes.Padding = PaddingMode.PKCS7;

        using var decryptor = aes.CreateDecryptor();
        var plainBytes = decryptor.TransformFinalBlock(
            cipherBytes, 0, cipherBytes.Length);

        return Encoding.UTF8.GetString(plainBytes);
    }
}

Pattern 4 : TDE + DBMS_CRYPTO (Oracle)

Oracle propose deux mecanismes natifs de chiffrement complementaires : TDE (Transparent Data Encryption) pour le chiffrement au repos, et DBMS_CRYPTO pour le chiffrement programmatique cote serveur. Combines, ils offrent une protection de niveau entreprise.

Architecture : Hierarchie des cles Oracle TDE

┌─────────────────────────────────────────────────────────────────┐
│                 ORACLE TDE - HIERARCHIE DES CLES                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌───────────────────────────────┐                              │
│  │  Oracle Wallet / OKV          │  Stockage securise           │
│  │  (fichier .p12 ou HSM)        │  de la Master Key            │
│  └──────────────┬────────────────┘                              │
│                 │                                                │
│                 ▼                                                │
│  ┌───────────────────────────────┐                              │
│  │  Master Encryption Key (MEK)  │  Cle maitre unique           │
│  │  (1 par base de donnees)      │  par PDB/CDB                 │
│  └──────────────┬────────────────┘                              │
│                 │  chiffre                                       │
│                 ▼                                                │
│  ┌───────────────────────────────┐                              │
│  │  Table Key / Column Key       │  Cle specifique              │
│  │  (1 par table ou colonne)     │  par objet chiffre           │
│  └──────────────┬────────────────┘                              │
│                 │  chiffre                                       │
│                 ▼                                                │
│  ┌───────────────────────────────┐                              │
│  │  Donnees (colonne ou          │  Donnees chiffrees           │
│  │  tablespace entier)           │  sur disque                  │
│  └───────────────────────────────┘                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Etape 1 : Configurer le Wallet (Keystore)

-- Creer le repertoire du wallet
-- mkdir -p /opt/oracle/admin/FREE/wallet

-- Creer le keystore (wallet) avec un mot de passe
ALTER SYSTEM SET ENCRYPTION WALLET OPEN
    IDENTIFIED BY "MonMotDePasseWallet!123";

-- Ou avec la syntaxe ADMINISTER KEY MANAGEMENT (12c+)
ADMINISTER KEY MANAGEMENT
    CREATE KEYSTORE '/opt/oracle/admin/FREE/wallet'
    IDENTIFIED BY "MonMotDePasseWallet!123";

-- Ouvrir le keystore
ADMINISTER KEY MANAGEMENT
    SET KEYSTORE OPEN
    IDENTIFIED BY "MonMotDePasseWallet!123";

-- Creer la Master Encryption Key
ADMINISTER KEY MANAGEMENT
    SET KEY
    IDENTIFIED BY "MonMotDePasseWallet!123"
    WITH BACKUP;

Etape 2 : TDE au niveau colonne (Column-level)

-- Creer une table avec des colonnes chiffrees par TDE
CREATE TABLE PATIENTS_TDE (
    ID          NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    NOM         VARCHAR2(100),
    NUMERO_SECU VARCHAR2(50)  ENCRYPT,
    DIAGNOSTIC  VARCHAR2(500) ENCRYPT,
    IBAN        VARCHAR2(50)  ENCRYPT,
    SALAIRE     NUMBER(10,2)  ENCRYPT
);

-- Ou chiffrer une colonne existante
ALTER TABLE PATIENTS
    MODIFY (NUMERO_SECU ENCRYPT);

-- Specifier l'algorithme (AES256 par defaut)
ALTER TABLE PATIENTS
    MODIFY (DIAGNOSTIC ENCRYPT USING 'AES256');

-- Ajouter un salt (valeur aleatoire) pour plus de securite
ALTER TABLE PATIENTS
    MODIFY (IBAN ENCRYPT USING 'AES256' SALT);

Etape 3 : TDE au niveau tablespace (Tablespace-level)

-- Creer un tablespace entierement chiffre
CREATE TABLESPACE TS_ENCRYPTED
    DATAFILE '/opt/oracle/oradata/FREE/ts_encrypted01.dbf'
    SIZE 100M
    AUTOEXTEND ON
    ENCRYPTION USING 'AES256'
    DEFAULT STORAGE (ENCRYPT);

-- Toutes les tables creees dans ce tablespace seront chiffrees
CREATE TABLE PATIENTS_SECURE (
    ID          NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    NOM         VARCHAR2(100),
    NUMERO_SECU VARCHAR2(50),
    DIAGNOSTIC  VARCHAR2(500)
) TABLESPACE TS_ENCRYPTED;

Column-level TDE vs Tablespace-level TDE

TDE au niveau colonne

  • + Granularite fine : chiffrement selectif
  • + Moins d'impact sur les performances
  • + Compatible avec les index (sans SALT)
  • - Limite aux types scalaires (pas de LOB)
  • - Maximum 2 colonnes par table avec SALT
  • - Pas de chiffrement des index eux-memes

Usage : quelques colonnes sensibles a proteger

TDE au niveau tablespace

  • + Tout est chiffre automatiquement
  • + Supporte tous les types (LOB inclus)
  • + Index et donnees temporaires chiffres
  • + Meilleure performance (bulk encryption)
  • - Pas de granularite (tout ou rien)
  • - Espace disque supplementaire

Usage : protection globale de toutes les donnees

DBMS_CRYPTO : Chiffrement programmatique

Le package DBMS_CRYPTO permet de chiffrer et dechiffrer des donnees directement dans du code PL/SQL. Il offre un controle total sur les algorithmes et les cles utilises. 

-- Fonctions principales de DBMS_CRYPTO

-- ENCRYPT : chiffrement symetrique
DECLARE
    l_clair     VARCHAR2(200) := '1 85 12 75 108 234 56';
    l_cle       RAW(32);       -- Cle AES-256 (32 octets)
    l_iv        RAW(16);       -- Vecteur d'initialisation
    l_chiffre   RAW(2000);
    l_dechiffre RAW(2000);
    l_algo      PLS_INTEGER;
BEGIN
    -- Definir l'algorithme : AES256 + CBC + PKCS5
    l_algo := DBMS_CRYPTO.ENCRYPT_AES256
            + DBMS_CRYPTO.CHAIN_CBC
            + DBMS_CRYPTO.PAD_PKCS5;

    -- Generer une cle aleatoire
    l_cle := DBMS_CRYPTO.RANDOMBYTES(32);
    l_iv  := DBMS_CRYPTO.RANDOMBYTES(16);

    -- Chiffrer
    l_chiffre := DBMS_CRYPTO.ENCRYPT(
        src => UTL_I18N.STRING_TO_RAW(l_clair, 'AL32UTF8'),
        typ => l_algo,
        key => l_cle,
        iv  => l_iv
    );

    -- Dechiffrer
    l_dechiffre := DBMS_CRYPTO.DECRYPT(
        src => l_chiffre,
        typ => l_algo,
        key => l_cle,
        iv  => l_iv
    );

    DBMS_OUTPUT.PUT_LINE('Clair    : ' || l_clair);
    DBMS_OUTPUT.PUT_LINE('Chiffre  : ' || RAWTOHEX(l_chiffre));
    DBMS_OUTPUT.PUT_LINE('Dechiffre: ' ||
        UTL_I18N.RAW_TO_CHAR(l_dechiffre, 'AL32UTF8'));
END;
/

DBMS_CRYPTO : HASH et MAC

-- Fonctions de hachage et MAC disponibles

DECLARE
    l_donnee RAW(2000);
    l_cle    RAW(32);
    l_hash   RAW(64);
    l_mac    RAW(64);
BEGIN
    l_donnee := UTL_I18N.STRING_TO_RAW('Donnee sensible', 'AL32UTF8');
    l_cle    := DBMS_CRYPTO.RANDOMBYTES(32);

    -- Hachage SHA-256
    l_hash := DBMS_CRYPTO.HASH(
        src => l_donnee,
        typ => DBMS_CRYPTO.HASH_SH256
    );

    -- MAC (Message Authentication Code) HMAC-SHA256
    l_mac := DBMS_CRYPTO.MAC(
        src => l_donnee,
        typ => DBMS_CRYPTO.HMAC_SH256,
        key => l_cle
    );

    DBMS_OUTPUT.PUT_LINE('Hash SHA-256  : ' || RAWTOHEX(l_hash));
    DBMS_OUTPUT.PUT_LINE('HMAC-SHA256   : ' || RAWTOHEX(l_mac));
END;
/

EF Core avec Oracle : TDE est transparent

Transparence totale : Avec TDE active, le DbContext et les modeles EF Core n'ont aucune modification. Le chiffrement est gere automatiquement par Oracle au niveau du stockage. Vos requetes LINQ restent identiques. 
// Ce code fonctionne tel quel avec TDE actif
var patient = new Patient
{
    Nom = "Jean Dupont",
    NumeroSecu = "1 85 12 75 108 234 56",
    Diagnostic = "Diabete type 2",
    IBAN = "FR76 1234 5678 9012 3456"
};

_context.Patients.Add(patient);
await _context.SaveChangesAsync();

// Requete avec filtre (fonctionne normalement, TDE est transparent)
var found = await _context.Patients
    .Where(p => p.NumeroSecu == "1 85 12 75 108 234 56")
    .FirstOrDefaultAsync();

Verification de l'etat TDE

-- Verifier quelles colonnes sont chiffrees
SELECT TABLE_NAME, COLUMN_NAME, ENCRYPTION_ALG, SALT
FROM DBA_ENCRYPTED_COLUMNS
WHERE OWNER = 'LAB_USER';

-- Verifier les tablespaces chiffres
SELECT TABLESPACE_NAME, ENCRYPTED
FROM DBA_TABLESPACES
WHERE ENCRYPTED = 'YES';

-- Verifier l'etat du wallet/keystore
SELECT WRL_TYPE, STATUS, WALLET_TYPE
FROM V$ENCRYPTION_WALLET;

Limitations

  • Oracle uniquement — TDE et DBMS_CRYPTO sont specifiques a Oracle Database.
  • Editions requises — TDE necessite l'Advanced Security Option (Enterprise Edition) ou Oracle Database 23ai Free.
  • Wallet obligatoire — Le wallet doit etre ouvert au demarrage de la base. S'il est ferme, les donnees chiffrees sont inaccessibles.
  • Pas de protection contre le DBA — Un DBA connecte voit les donnees en clair (TDE est transparent pour les requetes SQL).
  • DBMS_CRYPTO cote serveur — Les cles transitent par le serveur, contrairement a Always Encrypted (SQL Server) ou le chiffrement est cote client.

Pattern 5 : Oracle Data Redaction (DBMS_REDACT)

Oracle Data Redaction est une fonctionnalite de masquage dynamique des donnees. Contrairement au chiffrement, les donnees sont stockees en clair mais masquees a la volee lors de la lecture, en fonction de politiques definies par l'administrateur. C'est un complement ideal au chiffrement TDE.

Types de redaction

Type Description Exemple
Full Redaction Remplacement total de la valeur '1 85 12 75...' → ' ' (vide)
Partial Redaction Masquage partiel (debut, milieu ou fin) 'FR76 1234 5678' → 'FR76 XXXX XXXX'
Random Redaction Remplacement par une valeur aleatoire 'Jean Dupont' → 'Kx9mPqR'
Regex Redaction Masquage base sur une expression reguliere 'jean@mail.fr' → 'xxxx@mail.fr'
No Redaction Aucun masquage (pour tests) 'Jean Dupont' → 'Jean Dupont'

Creer une politique de redaction complete

-- Full Redaction sur le numero de securite sociale
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema  => 'LAB_USER',
        object_name    => 'PATIENTS',
        column_name    => 'NUMERO_SECU',
        policy_name    => 'REDACT_SECU',
        function_type  => DBMS_REDACT.FULL,
        expression     => 'SYS_CONTEXT(''USERENV'',''SESSION_USER'') != ''LAB_ADMIN'''
    );
END;
/

-- Partial Redaction sur l'IBAN (masquer les 12 derniers caracteres)
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema       => 'LAB_USER',
        object_name         => 'PATIENTS',
        column_name         => 'IBAN',
        policy_name         => 'REDACT_IBAN',
        function_type       => DBMS_REDACT.PARTIAL,
        function_parameters => 'VVVVVVVVVVVVVVFFFFFFFFFFFF,VVVVVVVVVVVVVVFFFFFFFFFFFF,X,5,12',
        expression          => 'SYS_CONTEXT(''USERENV'',''SESSION_USER'') != ''LAB_ADMIN'''
    );
END;
/

-- Random Redaction sur le diagnostic
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema  => 'LAB_USER',
        object_name    => 'PATIENTS',
        column_name    => 'DIAGNOSTIC',
        policy_name    => 'REDACT_DIAG',
        function_type  => DBMS_REDACT.RANDOM,
        expression     => 'SYS_CONTEXT(''USERENV'',''SESSION_USER'') != ''LAB_ADMIN'''
    );
END;
/

Ce que Data Redaction protege (et ne protege pas)

Attention : Data Redaction n'est pas du chiffrement. Les donnees restent en clair sur le disque. Un DBA avec des privileges eleves ou un acces direct aux fichiers de donnees peut contourner la redaction.
  • Protege : requetes SELECT standard des utilisateurs non privilegies
  • Protege : acces via des applications connectees avec un utilisateur restreint
  • Ne protege pas : acces DBA (SYSDBA, EXEMPT REDACTION POLICY)
  • Ne protege pas : donnees sur disque (utiliser TDE en complement)
  • Ne protege pas : exports Data Pump par un utilisateur privilegie

Quand utiliser Data Redaction ?

  • Masquer les donnees sensibles pour les developpeurs et testeurs
  • Conformite reglementaire (affichage restreint des donnees PII)
  • Applications multi-tenants avec differents niveaux d'acces
  • En complement de TDE pour une defense en profondeur

Reference et Bonnes Pratiques

Gestion des cles

La securite du chiffrement repose entierement sur la protection des cles. Une cle compromise rend tout le chiffrement inutile.

  • Oracle Wallet — Fichier PKCS#12 protege par mot de passe, stockant les cles maitres TDE. Peut etre configure en auto-login pour un demarrage automatique.
  • Oracle Key Vault (OKV) — Solution centralisee de gestion de cles pour les environnements multi-bases. Supporte la rotation automatique et l'audit complet.
  • HSM (Hardware Security Module) — Pour les environnements les plus sensibles, les cles ne quittent jamais le materiel dedie. Oracle TDE supporte les HSM via PKCS#11.
  • Rotation des cles — Utilisez ADMINISTER KEY MANAGEMENT SET KEY pour effectuer une rotation de la Master Key sans interruption de service.
  • Separation des responsabilites — L'equipe qui gere le Wallet ne devrait pas etre la meme que celle qui gere la base de donnees.
  • Sauvegarde du Wallet — Toujours maintenir une copie securisee du fichier Wallet hors site (disaster recovery).

Defense en profondeur

Le chiffrement n'est qu'une couche de la strategie de securite. Pour une protection complete, combinez plusieurs mecanismes Oracle :

  1. TDE — Chiffrement au repos (fichiers de donnees et backups RMAN)
  2. DBMS_CRYPTO — Chiffrement programmatique pour les donnees critiques
  3. VPD (Virtual Private Database) — Chaque utilisateur ne voit que ses propres donnees via des predicats automatiques
  4. Oracle Net Encryption / TLS 1.3 — Chiffrement des donnees en transit
  5. Oracle Audit Vault — Journalisation de tous les acces aux donnees sensibles
  6. Data Redaction — Masquage dynamique des donnees pour les utilisateurs non autorises
  7. Database Vault — Restriction des acces DBA aux donnees applicatives

Implications RGPD

Article 32 du RGPD : Le chiffrement est explicitement cite comme mesure technique appropriee. En cas de violation de donnees, les donnees chiffrees sont considerees comme non compromises si les cles n'ont pas ete exposees (Article 34 — exemption de notification).
  • Pseudonymisation — Le chiffrement des identifiants est une forme de pseudonymisation acceptee par le RGPD.
  • Droit a l'effacement — La destruction de la cle de chiffrement peut constituer un effacement cryptographique (crypto-shredding). Avec Oracle TDE, supprimer la Master Key rend les donnees definitivement inaccessibles.
  • Notification de violation — Si les donnees chiffrees sont volees mais que les cles (Wallet) sont sures, l'obligation de notification aux personnes concernees peut etre levee.
