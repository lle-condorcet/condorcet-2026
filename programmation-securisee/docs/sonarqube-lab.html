SonarQube

Analyse statique de code et detection de vulnerabilites de securite

Objectifs du labo Installer SonarQube avec Docker, analyser un projet .NET, identifier et corriger les vulnerabilites de securite detectees par l'analyse statique.

SonarQube est une plateforme open-source d'analyse statique de code (SAST — Static Application Security Testing). Elle inspecte le code source sans l'executer pour detecter des bugs, des vulnerabilites de securite, du code duplique et des mauvaises pratiques.

Pourquoi l'analyse statique ?

L'analyse statique est un pilier fondamental de la securite applicative. Elle permet de detecter des failles avant meme que le code ne soit deploye, ce qui est infiniment moins couteux que de corriger une faille en production.

AvantageDescription
Detection precoce Les failles sont trouvees des la phase de developpement, avant les tests manuels
Couverture exhaustive Chaque ligne de code est analysee, meme les chemins rarement executes
Automatisation Integrable dans le pipeline CI/CD pour un controle continu et systematique
Education Les developpeurs apprennent les bonnes pratiques grace aux explications des regles
Conformite Aide a respecter les normes OWASP, SANS Top 25, CWE
Limites de l'analyse statique L'analyse statique ne detecte pas tout. Elle ne peut pas trouver les failles liees a la configuration du serveur, aux erreurs de logique metier complexes, ou aux vulnerabilites dans les dependances (pour cela, on utilise des outils SCA comme dotnet list package --vulnerable). Elle doit etre combinee avec d'autres approches : DAST, tests de penetration, revue de code.

Architecture

SonarQube est compose de trois elements principaux qui interagissent ensemble :

SonarQube Scanner
→
SonarQube Server
→
PostgreSQL


Le scanner analyse le code → envoie les resultats au serveur → qui les stocke en base de donnees
ComposantRoleTechnologie
SonarQube Server Interface web, moteur de regles, API REST, calcul des metriques et Quality Gates Java (Elasticsearch integre pour la recherche)
PostgreSQL Stockage persistant des projets, resultats d'analyse, configurations, historique PostgreSQL 16
SonarScanner Analyse le code source localement et envoie les resultats au serveur via l'API dotnet-sonarscanner pour les projets .NET

Flux d'une analyse

  1. Le developpeur lance dotnet sonarscanner begin pour initialiser l'analyse
  2. Le projet est compile avec dotnet build (necessaire pour l'analyse du code .NET)
  3. dotnet sonarscanner end collecte les resultats et les envoie au serveur SonarQube
  4. Le serveur traite les resultats, applique les regles et calcule les metriques
  5. Les resultats sont visibles dans l'interface web avec des recommandations de correction

# Verifier la valeur actuelle

sudo sysctl -w vm.max_map_count=262144

# Configurer (permanent)

Docker Desktop sur Windows Sur Windows avec Docker Desktop recent, cette configuration est souvent geree automatiquement. Si SonarQube ne demarre pas, verifiez les logs avec docker compose logs sonarqube et recherchez l'erreur max virtual memory areas vm.max_map_count is too low.

  sonarqube:

    container_name: sonarqube
    depends_on:
      db:
        condition: service_healthy
    environment:
      SONAR_JDBC_URL: jdbc:postgresql://db:5432/sonarqube
      SONAR_JDBC_USERNAME: sonar
      SONAR_JDBC_PASSWORD: sonar_password_change_me

      - sonarqube_logs:/opt/sonarqube/logs
    ports:
      - "9000:9000"
    ulimits:                   # Requis par Elasticsearch
      memlock:
        soft: -1
        hard: -1
      nofile:
        soft: 65536
        hard: 65536
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:9000/api/system/status || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 10
      start_period: 120s
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    container_name: sonarqube-db
    environment:
      POSTGRES_USER: sonar
      POSTGRES_PASSWORD: sonar_password_change_me
      POSTGRES_DB: sonarqube
    volumes:
      - postgresql_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U sonar -d sonarqube"]
      interval: 10s
      retries: 5
    restart: unless-stopped
Points importants
  • depends_on avec condition: service_healthy — SonarQube ne demarre que quand PostgreSQL est pret

  • healthcheck — Verification automatique de l'etat de chaque service
  • volumes — Donnees persistantes, survivent au redemarrage des conteneurs

Analyse d'un projet .NET

Installer le scanner .NET

Pour les projets .NET, on utilise dotnet-sonarscanner, un outil global .NET qui s'integre au processus de build : 

# Installer le scanner globalement
dotnet tool install --global dotnet-sonarscanner

# Verifier l'installation
dotnet sonarscanner --version

Lancer une analyse

L'analyse d'un projet .NET se fait en 3 etapes :

# Etape 1 : Initialiser l'analyse
dotnet sonarscanner begin \
    /k:"my-dotnet-project" \
    /d:sonar.host.url="http://localhost:9000" \
    /d:sonar.token="sqp_votre_token"

# Etape 2 : Compiler le projet
dotnet build --no-incremental

# Etape 3 : Finaliser et envoyer les resultats
dotnet sonarscanner end \
    /d:sonar.token="sqp_votre_token"
Pourquoi 3 etapes ? Contrairement a d'autres langages, le scanner .NET doit s'integrer au processus de compilation. L'etape begin configure les hooks MSBuild, build compile et collecte les donnees, et end envoie tout au serveur SonarQube.

Utiliser les scripts fournis

Windows (PowerShell)

# Definir le token
$env:SONAR_TOKEN = "sqp_xxx"

# Lancer l'analyse
.\scripts\scan.ps1 -ProjectPath "..\SqlInjectionLabApp"

Linux / macOS / Git Bash

# Definir le token
export SONAR_TOKEN="sqp_xxx"

# Lancer l'analyse
./scripts/scan.sh ../SqlInjectionLabApp

Fichier sonar-project.properties

Ce fichier configure les parametres de l'analyse. Il est place a la racine du projet a analyser :

# Cle unique du projet
sonar.projectKey=my-dotnet-project

# Nom affiche dans l'interface
sonar.projectName=Mon Projet .NET

# URL du serveur SonarQube
sonar.host.url=http://localhost:9000

# Exclusions (fichiers a ignorer)
sonar.exclusions=**/bin/**,**/obj/**,**/Migrations/**

# Encodage
sonar.sourceEncoding=UTF-8

Consulter les resultats

Apres l'analyse, ouvrez http://localhost:9000/dashboard?id=my-dotnet-project. Vous verrez :

  • Bugs — Problemes de fiabilite (code qui ne fonctionne pas comme prevu)
  • Vulnerabilities — Failles de securite (injection, XSS, etc.)
  • Security Hotspots — Code qui necessite une revue manuelle de securite
  • Code Smells — Problemes de maintenabilite (code complexe, duplique, etc.)
  • Coverage — Pourcentage de code couvert par les tests unitaires

Regles de securite

SonarQube integre des centaines de regles de securite basees sur les standards OWASP Top 10, CWE et SANS Top 25. Voici les plus importantes pour le developpement .NET :

1. Injection SQL (CWE-89)

Vulnerable

// Concatenation directe = injection SQL
var sql = $"SELECT * FROM Users WHERE Name = '{input}'";
var cmd = new SqlCommand(sql, connection);
var reader = cmd.ExecuteReader();

Securise

// Requete parametree = pas d'injection
var sql = "SELECT * FROM Users WHERE Name = @name";
var cmd = new SqlCommand(sql, connection);
cmd.Parameters.AddWithValue("@name", input);
var reader = cmd.ExecuteReader();

2. Cross-Site Scripting - XSS (CWE-79)

Vulnerable

// Injection de HTML brut dans la page
@Html.Raw(Model.UserComment)

// Ou via JavaScript
<script>
  document.getElementById("name").innerHTML =
    "@Model.UserName";
</script>

Securise

// Razor encode automatiquement
@Model.UserComment

// Encodage explicite si necessaire
@Html.Encode(Model.UserComment)

// En JavaScript, utiliser textContent
<script>
  document.getElementById("name").textContent =
    "@Html.JavaScriptStringEncode(Model.UserName)";
</script>

3. Credentials codees en dur (CWE-798)

Vulnerable

// Mot de passe dans le code source !
var password = "SuperSecret123!";
var connectionString =
  $"Server=db;Password={password}";

// Cle API dans le code
var apiKey = "sk-abc123xyz789";

Securise

// Variables d'environnement
var password = Environment
  .GetEnvironmentVariable("DB_PASSWORD");

// Ou appsettings.json + User Secrets
var connStr = configuration
  .GetConnectionString("Default");

// Azure Key Vault, AWS Secrets, etc.
var apiKey = vault.GetSecret("api-key");

4. Cryptographie faible (CWE-327)

Vulnerable

// Algorithmes obsoletes et casses
var md5 = MD5.Create();
var sha1 = SHA1.Create();
var des = DES.Create();

// Hash de mot de passe sans sel
var hash = SHA256.HashData(
  Encoding.UTF8.GetBytes(password));

Securise

// Algorithmes modernes et surs
var sha256 = SHA256.Create();
var aes = Aes.Create();

// Pour les mots de passe : bcrypt/PBKDF2
var hasher = new PasswordHasher<User>();
var hash = hasher.HashPassword(
  user, password);
// Utilise PBKDF2 avec sel automatique

5. CSRF - Cross-Site Request Forgery (CWE-352)

Vulnerable

// Pas de validation anti-CSRF
[HttpPost]
[IgnoreAntiforgeryToken]
public IActionResult TransferMoney(
    decimal amount, string to)
{
    // Un attaquant peut forger cette requete
    _bank.Transfer(amount, to);
    return Ok();
}

Securise

// Token anti-CSRF valide automatiquement
[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult TransferMoney(
    decimal amount, string to)
{
    _bank.Transfer(amount, to);
    return Ok();
}
// Dans le formulaire Razor :
// @Html.AntiForgeryToken()

6. Path Traversal (CWE-22)

Vulnerable

// L'utilisateur controle le chemin
[HttpGet]
public IActionResult Download(string file)
{
    var path = Path.Combine(
      "uploads", file);
    // file = "../../etc/passwd" !
    return PhysicalFile(path, "application/octet-stream");
}

Securise

// Valider et normaliser le chemin
[HttpGet]
public IActionResult Download(string file)
{
    var basePath = Path.GetFullPath("uploads");
    var fullPath = Path.GetFullPath(
      Path.Combine("uploads", file));
    if (!fullPath.StartsWith(basePath))
        return Forbid();
    return PhysicalFile(fullPath, "application/octet-stream");
}

Piege : quand SonarQube ne detecte pas une injection SQL

Cas reel observe sur le projet SqlInjectionLabApp L'analyse SonarQube du projet n'a pas remonte les injections SQL comme vulnerabilites, alors que le code contient des concatenations directes de chaines dans des requetes SQL. Cette section explique pourquoi et comment eviter ce piege.

Le probleme

Le projet SqlInjectionLabApp contient du code clairement vulnerable :

// Services/DatabaseService.cs — Recherche vulnerable
var sql = $"SELECT * FROM Persons WHERE LastName LIKE '%{searchTerm}%'";
using var cmd = _connection.CreateCommand();
cmd.CommandText = sql;
var reader = cmd.ExecuteReader();

// Services/DatabaseService.cs — Login vulnerable
var sql = $"SELECT * FROM Users WHERE Username = '{username}' AND Password = '{password}'";

// Controllers/EfDemoController.cs — FromSqlRaw vulnerable
var sql = $"SELECT * FROM EfPersons WHERE LastName LIKE '%{q}%'";
model.Results = _context.Persons.FromSqlRaw(sql).ToList();

Pourtant, SonarQube n'a signale aucune vulnerabilite d'injection SQL. Il a uniquement emis 3 Security Hotspots de type Warning.

Deux regles, deux comportements

SonarQube dispose de deux regles distinctes pour les requetes SQL dynamiques. Comprendre leur difference est essentiel :

Regle Type Comportement Statut dans notre analyse
S2077 Hotspot Signale les requetes SQL formattees dynamiquement et demande une revue manuelle : "Make sure using a dynamically formatted SQL query is safe here." Active — 3 occurrences detectees
S3649 Vulnerabilite Effectue une analyse de flux de donnees (taint analysis) : trace le chemin d'une entree utilisateur jusqu'a l'execution SQL et confirme la vulnerabilite Absente du ruleset

S2077 — Hotspot (ce qui etait active)

  • Detecte les string interpolations dans du SQL
  • Classe le resultat comme Security Hotspot
  • Demande une revue manuelle
  • Ne fait pas echouer le Quality Gate
  • Pas d'analyse de flux de donnees

S3649 — Vulnerabilite (ce qui manquait)

  • Analyse le flux : entree utilisateur → variable → requete SQL
  • Classe le resultat comme Vulnerability confirmee
  • Severite Blocker ou Critical
  • Fait echouer le Quality Gate
  • Analyse de type taint analysis

Pourquoi la regle S3649 etait absente

L'analyse a utilise un Quality Profile personnalise qui contenait 467 regles C#, mais la regle S3649 n'en faisait pas partie. Cela peut arriver dans plusieurs cas :

  • Quality Profile personnalise — Cree a partir d'un sous-ensemble de regles, sans inclure les regles de taint analysis
  • Edition Community — Certaines regles de taint analysis (dont S3649) ne sont disponibles que dans les editions Developer, Enterprise ou Data Center de SonarQube
  • Profil non mis a jour — Un profil copie puis jamais resynchronise avec les nouvelles regles
Point d'attention Dans l'edition Community (gratuite) de SonarQube, la regle S3649 peut ne pas etre disponible car les analyses de type taint analysis sont une fonctionnalite des editions payantes. La regle S2077 (hotspot) reste disponible mais ne remonte qu'un avertissement necessitant une revue manuelle.

Ce que SonarQube a reellement detecte

Sur les 27 problemes remontes lors de l'analyse du SqlInjectionLabApp, voici les resultats lies a la securite SQL :

Fichier Ligne Regle Type Message
DatabaseService.cs 163 S2077 Hotspot Make sure using a dynamically formatted SQL query is safe here.
DatabaseService.cs 217 S2077 Hotspot Make sure using a dynamically formatted SQL query is safe here.
EfDemoController.cs 46 S2077 Hotspot Make sure using a dynamically formatted SQL query is safe here.

Les autres problemes detectes concernaient les credentials codees en dur (S2068), l'absence de validation ModelState.IsValid (S6967) et des problemes d'IDisposable (S3881) — mais aucune vulnerabilite SQL confirmee.

Comment corriger la configuration

1 Verifier l'edition SonarQube

# Verifier la version et l'edition
curl http://localhost:9000/api/system/status
# Reponse : { "status": "UP", "version": "10.x", "edition": "community" }

Si vous etes sur l'edition Community, les regles de taint analysis (S3649, S5131, S5144, S5145, S5146, S5167) ne sont pas disponibles. Vous devrez vous appuyer sur les Security Hotspots (S2077) et les traiter comme des vulnerabilites dans votre processus de revue.

2 Activer S3649 (editions Developer+)

Si vous disposez d'une edition Developer, Enterprise ou Data Center :

  1. Aller dans Quality Profiles → profil C# actif
  2. Cliquer sur Activate More Rules
  3. Chercher S3649 ou "SQL Injection"
  4. Activer la regle avec la severite Blocker
  5. Relancer l'analyse du projet
# Ou via l'API SonarQube :
curl -u admin:votreMotDePasse -X POST \
  "http://localhost:9000/api/qualityprofiles/activate_rule" \
  -d "key=votre-profil-csharp" \
  -d "rule=csharpsquid:S3649" \
  -d "severity=BLOCKER"

3 Utiliser le profil Sonar way

Le profil Sonar way (profil par defaut) inclut toutes les regles de securite disponibles dans votre edition. Si vous utilisez un profil personnalise, verifiez qu'il herite de Sonar way ou qu'il inclut les regles de securite critiques :

# Lister les regles de securite actives dans votre profil
curl -u admin:votreMotDePasse \
  "http://localhost:9000/api/rules/search?qprofile=votre-profil&types=VULNERABILITY&languages=cs"

# Verifier si S3649 est presente
curl -u admin:votreMotDePasse \
  "http://localhost:9000/api/rules/show?key=csharpsquid:S3649"

4 Adapter le Quality Gate (edition Community)

Si S3649 n'est pas disponible, renforcez votre Quality Gate pour inclure les Security Hotspots :

  • Ajouter la condition : Security Hotspots Reviewed ≥ 100%
  • Cela force la revue manuelle de chaque hotspot S2077 avant de valider l'analyse
  • Traiter tout hotspot SQL non justifie comme un echec

Lecon a retenir

Un outil d'analyse statique n'est pas une garantie de securite SonarQube ne detecte que ce que ses regles actives couvrent. Un code peut passer une analyse SonarQube avec 0 vulnerabilite et contenir malgre tout des failles critiques. C'est pourquoi il est essentiel de :
  • Verifier le Quality Profile — S'assurer que les regles de securite critiques sont activees
  • Revoir les Security Hotspots — Ne pas les ignorer sous pretexte que ce ne sont "que" des hotspots
  • Combiner les approches — Analyse statique (SAST) + tests de penetration (DAST) + revue de code manuelle
  • Connaitre les limites de son edition — L'edition Community ne dispose pas de taint analysis

Quality Gates

Un Quality Gate est un ensemble de conditions que le code doit respecter pour etre considere comme acceptable. C'est un gardien automatique qui bloque le code de mauvaise qualite avant qu'il n'atteigne la production.

Quality Gate par defaut ("Sonar way")

SonarQube fournit un Quality Gate preconfigure avec ces conditions :

ConditionSeuilMesure
Nouvelles vulnerabilites 0 Aucune nouvelle faille de securite toleree
Nouveaux bugs 0 Aucun nouveau bug tolere
Nouveaux Security Hotspots revus 100% Tous les hotspots doivent etre revus
Couverture sur le nouveau code ≥ 80% Le nouveau code doit etre teste
Duplication sur le nouveau code ≤ 3% Peu de code duplique dans les ajouts

Creer un Quality Gate personnalise

  1. Allez dans Quality Gates (menu du haut)
  2. Cliquez sur "Create"
  3. Nommez-le (ex: Security-First)
  4. Ajoutez des conditions axees securite :
Conditions recommandees pour un gate axe securite :

Security Rating        is worse than  A
New Vulnerabilities    is greater than  0
New Security Hotspots  reviewed is less than  100%
New Bugs               is greater than  0
New Code Smells        is greater than  10
Coverage               is less than  70%
Bonne pratique Appliquez le principe du "Clean as You Code" : concentrez-vous sur la qualite du nouveau code uniquement. C'est plus realiste que de vouloir corriger tout le code existant d'un coup. SonarQube appelle cela la "New Code Period".

Resultat du Quality Gate

Apres chaque analyse, le Quality Gate retourne un statut :

  • PASSED — Toutes les conditions sont respectees
  • FAILED — Au moins une condition n'est pas respectee

Ce statut peut etre utilise dans un pipeline CI/CD pour bloquer un merge ou empecher un deploiement si le code ne respecte pas les criteres de qualite.

Integration CI/CD

L'integration de SonarQube dans un pipeline CI/CD permet d'analyser automatiquement chaque commit ou pull request. Voici un exemple avec GitHub Actions :

GitHub Actions - Workflow complet

# .github/workflows/sonarqube.yml
name: SonarQube Analysis

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  sonarqube:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v4
      with:
        fetch-depth: 0  # Historique complet pour l'analyse

    - name: Setup .NET
      uses: actions/setup-dotnet@v4
      with:
        dotnet-version: '8.0.x'

    - name: Setup Java (requis par le scanner)
      uses: actions/setup-java@v4
      with:
        distribution: 'temurin'
        java-version: '17'

    - name: Install SonarScanner
      run: dotnet tool install --global dotnet-sonarscanner

    - name: Begin SonarQube Analysis
      run: |
        dotnet sonarscanner begin \
          /k:"${{ secrets.SONAR_PROJECT_KEY }}" \
          /d:sonar.host.url="${{ secrets.SONAR_HOST_URL }}" \
          /d:sonar.token="${{ secrets.SONAR_TOKEN }}"

    - name: Build
      run: dotnet build --no-incremental

    - name: End SonarQube Analysis
      run: |
        dotnet sonarscanner end \
          /d:sonar.token="${{ secrets.SONAR_TOKEN }}"

Secrets GitHub a configurer

SecretValeur
SONAR_TOKEN Token genere dans SonarQube
SONAR_HOST_URL URL du serveur SonarQube (ex: https://sonar.mondomaine.com)
SONAR_PROJECT_KEY Cle du projet (ex: my-dotnet-project)
SonarQube en CI/CD Pour un usage en CI/CD, le serveur SonarQube doit etre accessible depuis le runner GitHub Actions. Cela signifie soit un SonarQube heberge sur un serveur public, soit l'utilisation de SonarCloud (version SaaS gratuite pour les projets open-source).

Bloquer un merge si le Quality Gate echoue

Ajoutez une etape supplementaire au workflow pour verifier le Quality Gate :

    - name: Check Quality Gate
      run: |
        STATUS=$(curl -s -u "${{ secrets.SONAR_TOKEN }}:" \
          "${{ secrets.SONAR_HOST_URL }}/api/qualitygates/project_status?projectKey=${{ secrets.SONAR_PROJECT_KEY }}" \
          | jq -r '.projectStatus.status')
        echo "Quality Gate: $STATUS"
        if [ "$STATUS" != "OK" ]; then
          echo "Quality Gate FAILED!"
          exit 1
        fi

ProblemeCauseSolution
max virtual memory areas vm.max_map_count is too low Elasticsearch requiert au minimum 262144 Linux : sudo sysctl -w vm.max_map_count=262144
Windows : wsl -d docker-desktop sh -c "sysctl -w vm.max_map_count=262144"
SonarQube ne demarre pas (restart en boucle) Memoire insuffisante Augmentez la RAM de Docker Desktop a minimum 4 Go (Settings → Resources)
Port 9000 already in use Un autre service utilise le port 9000 Changez le port dans .env : SONAR_WEB_PORT=9001
Cannot connect to database PostgreSQL non pret ou credentials incorrectes Verifiez que les credentials dans .env sont coherentes entre les deux services
Le scanner ne trouve pas dotnet sonarscanner Outil global non installe ou PATH non configure dotnet tool install --global dotnet-sonarscanner puis redemarrer le terminal
Not authorized. Please check the token Token invalide ou expire Generez un nouveau token dans SonarQube (Mon Compte → Securite)

java.lang.OutOfMemoryError Elasticsearch manque de memoire Augmentez les limites Docker ou ajoutez SONAR_SEARCH_JAVAOPTS=-Xmx512m

Logs importants a verifier

Les logs de SonarQube se trouvent dans le volume Docker. Les fichiers cles :

  • sonar.log — Log principal du serveur
  • web.log — Log du serveur web (interface et API)
  • ce.log — Log du Compute Engine (traitement des analyses)
  • es.log — Log d'Elasticsearch (recherche et indexation)
# Acceder aux logs dans le conteneur
docker exec sonarqube ls /opt/sonarqube/logs/
docker exec sonarqube cat /opt/sonarqube/logs/sonar.log | tail -50

Exercices pratiques

Exercice 1 : Installation et premiere analyse

Objectif : Installer SonarQube et analyser un projet existant du cours.

  1. Demarrez SonarQube avec docker compose up -d depuis SonarQubeLabApp/
  2. Connectez-vous a http://localhost:9000 et changez le mot de passe admin
  3. Creez un projet avec la cle sql-injection-lab
  4. Generez un token d'authentification
  5. Analysez le projet SqlInjectionLabApp avec dotnet-sonarscanner
  6. Consultez les resultats dans l'interface web

Questions :

  • Combien de vulnerabilites de securite SonarQube a-t-il detectees ?
  • Quel est le Security Rating du projet (A, B, C, D ou E) ?
  • Quelles sont les 3 vulnerabilites les plus critiques ?

Exercice 2 : Corriger les vulnerabilites

Objectif : Corriger les failles detectees et relancer l'analyse pour voir l'amelioration.

  1. Dans les resultats de l'exercice 1, selectionnez 3 vulnerabilites detectees
  2. Pour chaque vulnerabilite, lisez l'explication et la regle SonarQube associee
  3. Corrigez le code en suivant les recommendations de SonarQube
  4. Relancez l'analyse avec dotnet-sonarscanner
  5. Verifiez que les vulnerabilites corrigees ont disparu

Livrable : Un rapport (capture d'ecran avant/apres) montrant les vulnerabilites corrigees.

Exercice 3 : Quality Gate personnalise

Objectif : Creer et appliquer un Quality Gate axe securite.

  1. Allez dans Quality Gates dans SonarQube
  2. Creez un nouveau Quality Gate nomme Security-First
  3. Ajoutez les conditions suivantes :
    • Security Rating meilleur que A
    • 0 nouvelle vulnerabilite
    • 100% des Security Hotspots revus
    • Couverture ≥ 50% sur le nouveau code
  4. Appliquez ce Quality Gate au projet sql-injection-lab
  5. Relancez l'analyse et observez le resultat du Quality Gate

Questions :

  • Le Quality Gate passe-t-il ou echoue-t-il ? Pourquoi ?
  • Quelles conditions ne sont pas respectees ?

Exercice 4 : Analyse multi-projets

Objectif : Analyser plusieurs projets du cours et comparer les resultats.

  1. Analysez les projets suivants avec SonarQube :
    • SqlInjectionLabApp
    • XssLabApp
    • CspDemoApp
  2. Comparez les metriques de securite entre les projets
  3. Identifiez quel projet a le plus de vulnerabilites
  4. Creez un tableau comparatif avec :
    • Nombre de vulnerabilites par projet
    • Security Rating par projet
    • Types de vulnerabilites les plus frequents

Livrable : Un tableau comparatif et une analyse ecrite (5-10 lignes) des resultats.

Conseil Pour chaque exercice, prenez des captures d'ecran des resultats dans SonarQube. Cela vous servira pour le rapport final. Portez une attention particuliere aux Security Hotspots : contrairement aux vulnerabilites, ils necessitent une revue manuelle pour determiner s'il s'agit d'un vrai probleme ou d'un faux positif.
