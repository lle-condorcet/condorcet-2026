Sécurisation des Bases de Données — Comparatif

SQL Server vs PostgreSQL vs Oracle — Guide complet des mécanismes de protection

1. Pourquoi sécuriser une base de données ?

La base de données est le cœur d'un système d'information. Elle contient les données métier, les informations personnelles des utilisateurs, les secrets commerciaux et bien souvent les identifiants d'accès à d'autres systèmes. Une compromission de la base de données peut avoir des conséquences catastrophiques : perte financière, atteinte à la réputation, sanctions réglementaires (RGPD, PCI-DSS, HIPAA) et responsabilité juridique.

La sécurisation de la base de données s'inscrit dans une stratégie de défense en profondeur (defense in depth). Même si le pare-feu, le WAF et l'application sont correctement configurés, la base de données doit disposer de ses propres mécanismes de protection. Un attaquant qui parvient à contourner les couches supérieures doit encore faire face à des contrôles au niveau des données elles-mêmes.

Statistique alarmante : Selon le rapport IBM Cost of a Data Breach 2024, le coût moyen d'une violation de données est de 4,88 millions USD. Les violations impliquant des bases de données non chiffrées sont parmi les plus coûteuses, car elles ne bénéficient pas de l'exemption de notification prévue par le RGPD.

Modèle de menaces

Pour concevoir une architecture de sécurité efficace, il faut d'abord identifier les menaces :

Menace Description Contre-mesure principale
DBA malveillant Un administrateur abuse de ses privilèges pour accéder ou exfiltrer des données sensibles Chiffrement client-side (Always Encrypted), séparation des rôles, audit
Backup volé Un fichier de sauvegarde est dérobé et restauré sur un autre serveur TDE (Transparent Data Encryption), chiffrement des backups
SQL Injection Un attaquant injecte du SQL via l'application pour extraire ou modifier des données Requêtes paramétrées, moindre privilège, RLS, WAF
Man-in-the-Middle Interception du trafic réseau entre l'application et la base de données TLS/SSL obligatoire, vérification des certificats
Accès physique Vol ou accès non autorisé aux disques/serveurs physiques TDE, chiffrement disque (BitLocker, LUKS), contrôle d'accès physique
Insider threat Un employé autorisé accède à des données au-delà de son besoin légitime RLS, Dynamic Data Masking, moindre privilège, audit
Escalade de privilèges Un utilisateur exploite une faille pour obtenir des droits administrateur Hardening, patches, séparation des rôles, audit

Les 3 piliers de la sécurité (CIA Triad)

Confidentialité

Seules les personnes autorisées peuvent accéder aux données. Mécanismes : chiffrement, contrôle d'accès, masking.

Intégrité

Les données ne peuvent pas être modifiées de manière non autorisée. Mécanismes : contraintes, audit, hachage, signatures.

Disponibilité

Les données restent accessibles aux utilisateurs autorisés. Mécanismes : haute disponibilité, backups, réplication.

2. Chiffrement au repos — Transparent Data Encryption (TDE)

Le chiffrement au repos (encryption at rest) protège les données lorsqu'elles sont stockées sur disque : fichiers de données, journaux de transactions, sauvegardes. Si un attaquant obtient un accès physique au disque ou vole un fichier de backup, les données restent illisibles sans la clé de chiffrement.

Transparent : Le mot « transparent » signifie que les applications existantes n'ont pas besoin d'être modifiées. Le chiffrement/déchiffrement est effectué automatiquement par le moteur de base de données au niveau des pages d'I/O.

SQL Server — TDE

SQL Server propose TDE depuis la version 2008, disponible uniquement dans les éditions Enterprise et Developer (et Azure SQL Database pour toutes les éditions). Le mécanisme repose sur une hiérarchie de clés :

  • Service Master Key (SMK) — protégée par DPAPI, générée automatiquement
  • Database Master Key (DMK) — protégée par le SMK
  • Certificate — contient la clé asymétrique
  • Database Encryption Key (DEK) — clé symétrique AES-256 qui chiffre réellement les données
-- 1. Créer la master key dans master
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'P@ssw0rd!Str0ng';

-- 2. Créer le certificat serveur
CREATE CERTIFICATE TDE_Cert
    WITH SUBJECT = 'TDE Certificate';

-- 3. Créer la clé de chiffrement dans la base cible
USE MaBaseDeDonnees;
CREATE DATABASE ENCRYPTION KEY
    WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE TDE_Cert;

-- 4. Activer TDE
ALTER DATABASE MaBaseDeDonnees
    SET ENCRYPTION ON;

Points importants :

  • Les fichiers .mdf, .ldf et les backups sont chiffrés
  • tempdb est automatiquement chiffré dès qu'une base TDE existe sur l'instance
  • Impact sur les performances : environ 3-5% d'overhead I/O
  • Le certificat doit être sauvegardé — sans lui, les backups sont irrécupérables
  • TDE ne protège pas les données en mémoire ni contre un DBA connecté

PostgreSQL — Chiffrement au repos

PostgreSQL n'offre historiquement pas de TDE natif au niveau du moteur. Cependant, plusieurs solutions existent :

  • pg_tde (Percona) — Extension relativement récente qui fournit un TDE au niveau des colonnes et des tablespaces. En développement actif.
  • Chiffrement au niveau du système de fichiers — LUKS/dm-crypt sous Linux, BitLocker sous Windows, FileVault sous macOS. Protège l'intégralité du volume.
  • Services cloud managés — AWS RDS chiffre automatiquement au repos avec KMS, Azure Database for PostgreSQL offre le chiffrement via des clés gérées par Azure.
  • pgcrypto — Chiffrement applicatif (au niveau des colonnes), mais ce n'est pas du TDE au sens strict.
-- Chiffrement au niveau du système de fichiers (Linux)
-- Créer un volume chiffré LUKS
$ sudo cryptsetup luksFormat /dev/sdb1
$ sudo cryptsetup luksOpen /dev/sdb1 pg_encrypted
$ sudo mkfs.ext4 /dev/mapper/pg_encrypted
$ sudo mount /dev/mapper/pg_encrypted /var/lib/postgresql/data

-- pg_tde (Percona) — activation
CREATE EXTENSION pg_tde;
SELECT pg_tde_set_master_key('master-key', 'file');
CREATE TABLE secrets (
    id serial,
    data text
) USING tde_heap;
Attention : Le chiffrement au niveau du filesystem (LUKS, BitLocker) ne protège pas contre un DBA connecté ni contre le vol d'un backup non chiffré. Il protège uniquement contre le vol physique du disque.

Oracle — TDE

Oracle possède l'implémentation TDE la plus mature du marché, disponible depuis Oracle 10g R2 (2005). Initialement réservée à l'option Advanced Security (coût supplémentaire), TDE est incluse dans toutes les éditions depuis Oracle 21c.

Oracle TDE offre deux niveaux de chiffrement :

  • Column-level TDE — chiffrement sélectif de colonnes individuelles
  • Tablespace-level TDE — chiffrement de l'intégralité d'un tablespace (recommandé pour les performances)
-- Configuration du Wallet (Oracle 19c+)
ADMINISTER KEY MANAGEMENT
    CREATE KEYSTORE '/opt/oracle/wallet'
    IDENTIFIED BY "WalletP@ss123";

ADMINISTER KEY MANAGEMENT
    SET KEYSTORE OPEN
    IDENTIFIED BY "WalletP@ss123";

ADMINISTER KEY MANAGEMENT
    SET KEY
    IDENTIFIED BY "WalletP@ss123"
    WITH BACKUP;

-- TDE au niveau colonne
ALTER TABLE employes
    MODIFY (salaire ENCRYPT);

-- TDE au niveau tablespace
CREATE TABLESPACE ts_secure
    DATAFILE '/opt/oracle/data/ts_secure.dbf'
    SIZE 100M
    ENCRYPTION USING 'AES256'
    DEFAULT STORAGE (ENCRYPT);

Oracle utilise un Oracle Wallet (fichier PKCS#12) ou Oracle Key Vault (OKV) pour le stockage centralisé des clés dans les environnements multi-serveurs. L'auto-login wallet permet d'ouvrir automatiquement le keystore au démarrage de l'instance.

3. Chiffrement en transit — TLS/SSL

Le chiffrement en transit protège les données qui circulent entre l'application et le serveur de base de données. Sans TLS, un attaquant sur le réseau peut intercepter les requêtes SQL, les résultats, les identifiants de connexion et les données sensibles en clair. L'attaque man-in-the-middle (MITM) est triviale sur un réseau local non sécurisé.

SQL Server — TLS

  • Support TLS 1.2 et TLS 1.3 (depuis SQL Server 2022)
  • Configuration via SQL Server Configuration Manager : onglet « Force Encryption »
  • Certificat installé dans le magasin de certificats Windows
  • Chaîne de connexion côté client : Encrypt=True;TrustServerCertificate=False
  • Depuis SQL Server 2022, Encrypt=True est le comportement par défaut pour les nouveaux drivers
// Chaîne de connexion .NET — TLS activé
"Server=sql-prod;Database=AppDB;User Id=app;Password=***;Encrypt=True;TrustServerCertificate=False;"

PostgreSQL — TLS

  • Configuration dans postgresql.conf :
# postgresql.conf
ssl = on
ssl_cert_file = '/etc/ssl/certs/server.crt'
ssl_key_file = '/etc/ssl/private/server.key'
ssl_ca_file = '/etc/ssl/certs/ca.crt'
ssl_min_protocol_version = 'TLSv1.2'
  • Contrôle d'accès dans pg_hba.conf avec hostssl pour forcer TLS
  • Côté client : sslmode=verify-full (le plus sécurisé — vérifie le certificat et le hostname)
  • Modes sslmode disponibles : disable, allow, prefer, require, verify-ca, verify-full
  • Authentification par mot de passe : SCRAM-SHA-256 recommandé (défaut depuis PostgreSQL 14)
# pg_hba.conf — forcer SSL pour toutes les connexions distantes
hostssl  all  all  0.0.0.0/0  scram-sha-256

Oracle — Chiffrement réseau

Oracle offre deux mécanismes de chiffrement réseau, configurables via sqlnet.ora :

  • Oracle Native Network Encryption — chiffrement AES256 sans certificat TLS, intégré dans Oracle Net Services. Simple à configurer.
  • TLS standard — avec certificats x.509, via Oracle Wallet
# sqlnet.ora — chiffrement natif Oracle
SQLNET.ENCRYPTION_SERVER = REQUIRED
SQLNET.ENCRYPTION_TYPES_SERVER = (AES256, AES192)
SQLNET.CRYPTO_CHECKSUM_SERVER = REQUIRED
SQLNET.CRYPTO_CHECKSUM_TYPES_SERVER = (SHA256)

# sqlnet.ora — TLS avec certificats
WALLET_LOCATION =
  (SOURCE =
    (METHOD = FILE)
    (METHOD_DATA =
      (DIRECTORY = /opt/oracle/wallet)))
SSL_CLIENT_AUTHENTICATION = TRUE
SSL_VERSION = 1.2
Particularité Oracle : Le chiffrement natif Oracle Net est plus simple à déployer que TLS (pas de PKI à gérer), mais il n'est pas basé sur un standard ouvert. Pour la conformité et l'interopérabilité, TLS est recommandé.

4. Chiffrement applicatif (dans le code)

Le chiffrement applicatif (application-level encryption) permet de chiffrer les données avant qu'elles n'atteignent la base de données, ou de les chiffrer au sein du moteur SQL avec des fonctions dédiées. Contrairement au TDE, ce type de chiffrement peut protéger contre un DBA malveillant — à condition que les clés soient gérées côté client.

SQL Server — Always Encrypted

Always Encrypted est la solution phare de SQL Server pour le chiffrement côté client. Les données sont chiffrées et déchiffrées par le driver ADO.NET / ODBC / JDBC, jamais par le moteur SQL Server lui-même. Le DBA ne voit que des données chiffrées.

  • Column Master Key (CMK) — stockée dans le magasin de certificats Windows, Azure Key Vault ou un HSM. Jamais accessible au serveur SQL.
  • Column Encryption Key (CEK) — chiffre les données, elle-même protégée par la CMK
  • Chiffrement déterministe — même texte en clair = même texte chiffré. Permet l'égalité (WHERE, JOIN, GROUP BY) mais pas LIKE.
  • Chiffrement aléatoire — plus sécurisé, mais aucune opération côté serveur possible
-- Créer une CMK
CREATE COLUMN MASTER KEY CMK_Auto
WITH (
    KEY_STORE_PROVIDER_NAME = 'MSSQL_CERTIFICATE_STORE',
    KEY_PATH = 'CurrentUser/My/AB123...'
);

-- Créer une CEK
CREATE COLUMN ENCRYPTION KEY CEK_Auto
WITH VALUES (
    COLUMN_MASTER_KEY = CMK_Auto,
    ALGORITHM = 'RSA_OAEP',
    ENCRYPTED_VALUE = 0x01700...
);

-- Utiliser dans une table
CREATE TABLE Patients (
    Id int PRIMARY KEY,
    Nom nvarchar(100),
    NumeroSecu char(15)
        ENCRYPTED WITH (
            COLUMN_ENCRYPTION_KEY = CEK_Auto,
            ENCRYPTION_TYPE = DETERMINISTIC,
            ALGORITHM = 'AEAD_AES_256_CBC_HMAC_SHA_256'
        )
);

Always Encrypted with Secure Enclaves (SQL Server 2019+) permet d'effectuer des opérations sur les données chiffrées (LIKE, comparaisons de plage) dans un enclave sécurisé (Intel SGX ou VBS) côté serveur, sans exposer les clés au DBA.

SQL Server propose aussi des fonctions T-SQL de chiffrement côté serveur :

-- Chiffrement symétrique côté serveur (moins sécurisé : le DBA voit les clés)
OPEN SYMMETRIC KEY SK_Data DECRYPTION BY CERTIFICATE Cert_Data;

INSERT INTO Secrets (EncryptedValue)
VALUES (EncryptByKey(Key_GUID('SK_Data'), 'donnée sensible'));

SELECT CONVERT(varchar, DecryptByKey(EncryptedValue)) FROM Secrets;

PostgreSQL — pgcrypto

PostgreSQL utilise l'extension pgcrypto pour le chiffrement applicatif. Toutes les opérations s'effectuent côté serveur — les clés sont visibles par le moteur (et donc par le DBA). C'est moins sécurisé que le modèle client-side d'Always Encrypted. 

-- Activer l'extension
CREATE EXTENSION pgcrypto;

-- Chiffrement symétrique PGP
INSERT INTO secrets (data)
VALUES (pgp_sym_encrypt('donnée sensible', 'ma_cle_secrete'));

SELECT pgp_sym_decrypt(data, 'ma_cle_secrete') FROM secrets;

-- Chiffrement asymétrique PGP
SELECT pgp_pub_encrypt('secret', dearmor('-----BEGIN PGP PUBLIC KEY...'));
SELECT pgp_pub_decrypt(data, dearmor('-----BEGIN PGP PRIVATE KEY...'));

-- Hachage de mots de passe (bcrypt)
INSERT INTO users (password_hash)
VALUES (crypt('mon_mot_de_passe', gen_salt('bf', 12)));

-- Vérification du mot de passe
SELECT * FROM users
WHERE password_hash = crypt('tentative', password_hash);

-- Fonctions utilitaires
SELECT gen_random_bytes(32);        -- 32 octets aléatoires
SELECT digest('data', 'sha256');  -- hash SHA-256
SELECT hmac('data', 'key', 'sha256');  -- HMAC

Oracle — DBMS_CRYPTO

Oracle propose le package PL/SQL DBMS_CRYPTO pour le chiffrement applicatif. Comme pgcrypto, les opérations s'effectuent côté serveur et les clés sont accessibles au DBA. 

DECLARE
    l_key      RAW(32) := UTL_RAW.CAST_TO_RAW('CleSecrete32Caracteres!!');
    l_data     RAW(2000);
    l_encrypted RAW(2000);
    l_decrypted RAW(2000);
BEGIN
    l_data := UTL_RAW.CAST_TO_RAW('Donnée sensible');

    -- Chiffrement AES-256 CBC PKCS5
    l_encrypted := DBMS_CRYPTO.ENCRYPT(
        src => l_data,
        typ => DBMS_CRYPTO.ENCRYPT_AES256
              + DBMS_CRYPTO.CHAIN_CBC
              + DBMS_CRYPTO.PAD_PKCS5,
        key => l_key
    );

    -- Déchiffrement
    l_decrypted := DBMS_CRYPTO.DECRYPT(
        src => l_encrypted,
        typ => DBMS_CRYPTO.ENCRYPT_AES256
              + DBMS_CRYPTO.CHAIN_CBC
              + DBMS_CRYPTO.PAD_PKCS5,
        key => l_key
    );

    -- Hachage
    l_data := DBMS_CRYPTO.HASH(
        UTL_RAW.CAST_TO_RAW('password'),
        DBMS_CRYPTO.HASH_SH256
    );

    -- HMAC
    l_data := DBMS_CRYPTO.MAC(
        UTL_RAW.CAST_TO_RAW('message'),
        DBMS_CRYPTO.HMAC_SH256,
        l_key
    );
END;

5. Authentification

L'authentification est la première ligne de défense : vérifier l'identité de l'utilisateur ou de l'application qui se connecte à la base de données. Chaque SGBD propose différents mécanismes, du simple mot de passe à l'authentification Kerberos intégrée.

SQL Server

  • Windows Authentication (Kerberos/NTLM) — recommandé en environnement Active Directory. Pas de mot de passe à gérer dans la chaîne de connexion.
  • SQL Server Authentication — login/mot de passe stocké dans SQL Server. Nécessaire pour les accès hors domaine.
  • Azure Active Directory (Entra ID) — pour Azure SQL et SQL Server 2022+
  • Contained Database Users — utilisateurs portables, pas de dépendance aux logins serveur
  • Politique de mot de passe : CHECK_POLICY = ON, CHECK_EXPIRATION = ON (utilise la politique Windows)
-- Créer un login avec politique de mot de passe
CREATE LOGIN app_user
    WITH PASSWORD = 'C0mplexP@ss!',
    CHECK_POLICY = ON,
    CHECK_EXPIRATION = ON;

-- Créer un utilisateur contained
USE MaBase;
CREATE USER app_user WITH PASSWORD = 'C0mplexP@ss!';

PostgreSQL

  • SCRAM-SHA-256 — méthode recommandée, défaut depuis PostgreSQL 14. Authentification par challenge-response, le mot de passe n'est jamais envoyé en clair.
  • md5 — méthode historique, considérée comme faible. À éviter.
  • cert — authentification par certificat client TLS
  • LDAP — délégation à un annuaire LDAP/Active Directory
  • GSSAPI/Kerberos — authentification Kerberos
  • RADIUS — délégation à un serveur RADIUS
  • PAM — authentification via les modules PAM du système
  • peer — correspondance utilisateur Unix (connexions locales via socket)
  • Configuration granulaire dans pg_hba.conf : par base, utilisateur, adresse IP
# pg_hba.conf — exemples de configuration
# TYPE   DATABASE   USER       ADDRESS        METHOD
local    all        postgres                  peer
hostssl  all        all        10.0.0.0/8     scram-sha-256
hostssl  all        all        192.168.0.0/16 scram-sha-256
host     all        all        0.0.0.0/0      reject

# postgresql.conf
password_encryption = 'scram-sha-256'

Oracle

  • Database Authentication — mot de passe stocké dans la base, haché avec un algorithme propriétaire (verifier-based depuis 12c)
  • OS Authentication — l'utilisateur du système d'exploitation est mappé à un utilisateur de la base
  • Kerberos — via Oracle Advanced Security
  • LDAP — intégration avec un annuaire LDAP
  • RADIUS — délégation à un serveur RADIUS
  • Oracle Internet Directory (OID) — annuaire LDAP Oracle
  • Profiles — politique de mot de passe très granulaire
-- Créer un profil de sécurité pour les mots de passe
CREATE PROFILE secure_profile LIMIT
    FAILED_LOGIN_ATTEMPTS 5
    PASSWORD_LIFE_TIME 90
    PASSWORD_REUSE_TIME 365
    PASSWORD_REUSE_MAX 12
    PASSWORD_LOCK_TIME 1
    PASSWORD_GRACE_TIME 7
    PASSWORD_VERIFY_FUNCTION ora12c_verify_function;

-- Assigner le profil à un utilisateur
ALTER USER app_user PROFILE secure_profile;

6. Autorisation et contrôle d'accès

L'autorisation détermine ce que peut faire un utilisateur authentifié. Le principe fondamental est celui du moindre privilège : chaque utilisateur ou application ne doit disposer que des droits strictement nécessaires à son fonctionnement.

SQL Server

  • Modèle hiérarchique : Server roles → Database roles → Schema → Object
  • Rôles serveur prédéfinis : sysadmin, securityadmin, dbcreator, etc.
  • Rôles de base prédéfinis : db_owner, db_datareader, db_datawriter, etc.
  • Rôles personnalisés, permissions granulaires avec GRANT / DENY / REVOKE
  • Schémas pour l'isolation logique des objets

PostgreSQL

  • Modèle basé sur les rôles (pas de distinction user/group)
  • GRANT / REVOKE sur bases, schémas, tables, colonnes, fonctions
  • Privilèges par défaut (ALTER DEFAULT PRIVILEGES) pour les nouveaux objets
  • pg_read_all_data, pg_write_all_data (PG 14+)
  • La flexibilité des rôles PostgreSQL permet des architectures très fines

Oracle

  • Modèle riche : System privileges, Object privileges, Roles
  • Rôles prédéfinis : DBA, CONNECT, RESOURCE, etc.
  • Separation of Duties : SYSDBA, SYSOPER, SYSBACKUP, SYSDG, SYSKM
  • Database Vault — empêche même le DBA d'accéder à certains schémas. Réalms, command rules et facteurs de sécurité.
  • Analyse de privilèges (DBMS_PRIVILEGE_CAPTURE) pour identifier les droits inutilisés
Bonne pratique : Utilisez DBMS_PRIVILEGE_CAPTURE (Oracle) ou des requêtes d'audit pour identifier les privilèges accordés mais jamais utilisés, puis révoquez-les. C'est l'application concrète du principe de moindre privilège.

7. Row-Level Security (RLS)

La sécurité au niveau des lignes (Row-Level Security) permet de filtrer automatiquement les lignes visibles par un utilisateur, de manière transparente pour l'application. Chaque utilisateur ne voit que les données qui lui sont destinées, même s'il exécute SELECT * FROM table.

SQL Server — Security Policy

-- 1. Créer la fonction de filtrage
CREATE FUNCTION dbo.fn_SecurityPredicate(@TenantId int)
RETURNS TABLE
WITH SCHEMABINDING
AS
    RETURN
        SELECT 1 AS result
        WHERE @TenantId = CAST(SESSION_CONTEXT(N'TenantId') AS int);

-- 2. Créer la politique de sécurité
CREATE SECURITY POLICY TenantFilter
    ADD FILTER PREDICATE dbo.fn_SecurityPredicate(TenantId)
        ON dbo.Commandes,
    ADD BLOCK PREDICATE dbo.fn_SecurityPredicate(TenantId)
        ON dbo.Commandes AFTER INSERT
    WITH (STATE = ON);

-- 3. Définir le contexte de session
EXEC sp_set_session_context 'TenantId', 42;
  • Filter predicate : filtre silencieusement les lignes (SELECT, UPDATE, DELETE)
  • Block predicate : empêche l'insertion/modification de lignes non autorisées
  • Contexte via SESSION_CONTEXT() ou SUSER_SNAME()

PostgreSQL — Row-Level Security

-- 1. Activer RLS sur la table
ALTER TABLE commandes ENABLE ROW LEVEL SECURITY;

-- 2. Créer une politique
CREATE POLICY tenant_isolation ON commandes
    FOR ALL
    USING (tenant_id = current_setting('app.tenant_id')::int)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::int);

-- 3. Politique basée sur le rôle PostgreSQL
CREATE POLICY user_data ON documents
    FOR SELECT
    USING (owner = current_user);

-- 4. Définir le contexte applicatif
SET app.tenant_id = '42';

-- Forcer RLS même pour le propriétaire de la table
ALTER TABLE commandes FORCE ROW LEVEL SECURITY;
  • L'implémentation PostgreSQL est considérée comme la plus flexible
  • Politiques multiples combinables (OR entre les politiques du même type)
  • USING : filtre les lignes visibles (SELECT, UPDATE, DELETE)
  • WITH CHECK : vérifie les lignes écrites (INSERT, UPDATE)
  • Support des rôles, de current_user et de variables de session personnalisées

Oracle — Virtual Private Database (VPD)

-- 1. Créer la fonction de politique
CREATE OR REPLACE FUNCTION tenant_policy(
    p_schema IN VARCHAR2,
    p_table  IN VARCHAR2
) RETURN VARCHAR2
AS
BEGIN
    RETURN 'tenant_id = SYS_CONTEXT(''APP_CTX'', ''TENANT_ID'')';
END;
/

-- 2. Appliquer la politique VPD
BEGIN
    DBMS_RLS.ADD_POLICY(
        object_schema   => 'APP',
        object_name     => 'COMMANDES',
        policy_name     => 'TENANT_POLICY',
        function_schema => 'SEC',
        policy_function => 'TENANT_POLICY',
        statement_types => 'SELECT, INSERT, UPDATE, DELETE'
    );
END;
/

-- 3. Définir le contexte applicatif
CREATE OR REPLACE CONTEXT app_ctx USING set_context_pkg;

CREATE OR REPLACE PACKAGE BODY set_context_pkg AS
    PROCEDURE set_tenant(p_id NUMBER) IS
    BEGIN
        DBMS_SESSION.SET_CONTEXT('APP_CTX', 'TENANT_ID', p_id);
    END;
END;
/
  • Oracle Label Security (OLS) — niveau supérieur : classification des données (Confidentiel, Secret, Top Secret) avec des labels sur chaque ligne
  • VPD modifie dynamiquement la clause WHERE des requêtes SQL
  • Contexte via SYS_CONTEXT() et application contexts
  • Très puissant mais plus complexe à configurer que les implémentations SQL Server/PostgreSQL

8. Dynamic Data Masking

Le masquage dynamique des données (Dynamic Data Masking) permet de masquer automatiquement les données sensibles dans les résultats de requête pour les utilisateurs non autorisés. Contrairement au chiffrement, les données sont stockées en clair — seul l'affichage est modifié. C'est utile pour les environnements de développement, les rapports ou les accès en lecture seule limités.

SQL Server — Dynamic Data Masking (natif)

-- Créer une table avec masquage
CREATE TABLE Clients (
    Id int PRIMARY KEY,
    Nom nvarchar(100),
    Email nvarchar(100)
        MASKED WITH (FUNCTION = 'email()'),
    Telephone varchar(15)
        MASKED WITH (FUNCTION = 'partial(0, "XXX-XXX-", 4)'),
    NumeroSecu char(15)
        MASKED WITH (FUNCTION = 'default()'),
    Salaire decimal(10,2)
        MASKED WITH (FUNCTION = 'random(1000, 9999)')
);

-- Accorder le droit de voir les vraies données
GRANT UNMASK TO admin_user;

-- Révoquer le droit
REVOKE UNMASK TO report_user;

Fonctions de masquage disponibles :

  • default() — remplace par « XXXX » (strings), 0 (nombres), 01-01-1900 (dates)
  • email() — « aXXX@XXXX.com »
  • partial(prefix, padding, suffix) — masquage partiel personnalisable
  • random(start, end) — valeur aléatoire dans une plage

PostgreSQL — Pas de masquage natif

PostgreSQL ne dispose pas de Dynamic Data Masking intégré. Plusieurs approches alternatives existent :

  • Vues avec CASE — créer des vues qui masquent conditionnellement les données
  • postgresql_anonymizer (Anon) — extension de masquage et d'anonymisation
  • pgMask — extension tierce pour le masquage dynamique
-- Approche manuelle avec une vue
CREATE VIEW v_clients_masked AS
SELECT
    id,
    nom,
    CASE WHEN current_user = 'admin'
        THEN email
        ELSE LEFT(email, 1) || '***@***.com'
    END AS email,
    CASE WHEN current_user = 'admin'
        THEN telephone
        ELSE 'XXX-XXX-' || RIGHT(telephone, 4)
    END AS telephone
FROM clients;

-- Avec l'extension postgresql_anonymizer
CREATE EXTENSION anon CASCADE;
SELECT anon.init();

SECURITY LABEL FOR anon ON COLUMN clients.email
    IS 'MASKED WITH FUNCTION anon.partial_email(email)';

SECURITY LABEL FOR anon ON COLUMN clients.telephone
    IS 'MASKED WITH FUNCTION anon.partial(telephone, 2, $$XXX-XXX-$$, 4)';

Oracle — Data Redaction (DBMS_REDACT)

-- Masquage complet d'une colonne
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema  => 'APP',
        object_name    => 'CLIENTS',
        column_name    => 'NUMERO_SECU',
        policy_name    => 'MASK_SSN',
        function_type  => DBMS_REDACT.FULL,
        expression     => 'SYS_CONTEXT(''USERENV'', ''SESSION_USER'') != ''ADMIN'''
    );
END;
/

-- Masquage partiel (garder les 4 derniers chiffres)
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema       => 'APP',
        object_name         => 'CLIENTS',
        column_name         => 'CARTE_CREDIT',
        policy_name         => 'MASK_CC',
        function_type       => DBMS_REDACT.PARTIAL,
        function_parameters => DBMS_REDACT.REDACT_NUM_US_PHONE_TYPE,
        expression          => '1=1'
    );
END;
/

-- Masquage par expression régulière
BEGIN
    DBMS_REDACT.ADD_POLICY(
        object_schema  => 'APP',
        object_name    => 'CLIENTS',
        column_name    => 'EMAIL',
        policy_name    => 'MASK_EMAIL',
        function_type  => DBMS_REDACT.REGEXP,
        regexp_pattern => '([A-Za-z0-9._%+-]+)(@.*)',
        regexp_replace_string => 'xxxx\2',
        expression     => '1=1'
    );
END;
/

Oracle Data Redaction est appliqué au moment de la requête (query time) — les données ne sont jamais modifiées sur disque. C'est très performant car le masquage est effectué juste avant le retour des résultats.

9. Audit et journalisation

L'audit est essentiel pour la détection des intrusions, la conformité réglementaire et l'investigation post-incident. Un bon système d'audit enregistre qui a fait quoi, quand et sur quelles données.

SQL Server — SQL Server Audit

-- 1. Créer un audit serveur (destination : fichier)
CREATE SERVER AUDIT MainAudit
    TO FILE (FILEPATH = 'C:\AuditLogs\', MAXSIZE = 100 MB)
    WITH (ON_FAILURE = CONTINUE);

ALTER SERVER AUDIT MainAudit WITH (STATE = ON);

-- 2. Spécification d'audit au niveau serveur
CREATE SERVER AUDIT SPECIFICATION ServerAuditSpec
    FOR SERVER AUDIT MainAudit
    ADD (FAILED_LOGIN_GROUP),
    ADD (LOGIN_CHANGE_PASSWORD_GROUP),
    ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP)
    WITH (STATE = ON);

-- 3. Spécification d'audit au niveau base de données
USE MaBase;
CREATE DATABASE AUDIT SPECIFICATION DbAuditSpec
    FOR SERVER AUDIT MainAudit
    ADD (SELECT, INSERT, UPDATE, DELETE
        ON SCHEMA::dbo BY PUBLIC),
    ADD (SCHEMA_OBJECT_CHANGE_GROUP)
    WITH (STATE = ON);

-- Lire les logs d'audit
SELECT * FROM sys.fn_get_audit_file('C:\AuditLogs\*.sqlaudit', NULL, NULL);

Autres mécanismes SQL Server :

  • Change Data Capture (CDC) — capture les modifications de données (INSERT, UPDATE, DELETE) dans des tables de suivi
  • Temporal Tables — tables versionnées avec historique automatique des modifications
  • SQL Server Profiler / Extended Events — capture détaillée des requêtes pour le diagnostic

PostgreSQL — pgaudit

# postgresql.conf — configuration de pgaudit
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'read, write, ddl, role'
pgaudit.log_catalog = off
pgaudit.log_relation = on
pgaudit.log_statement_once = on

# Logging basique (sans pgaudit)
log_statement = 'all'          -- none, ddl, mod, all
log_connections = on
log_disconnections = on
log_line_prefix = '%t [%p] %u@%d '

-- Audit par objet avec pgaudit
SET pgaudit.role = 'auditor';

-- Accorder les droits pour déclencher l'audit
GRANT SELECT ON clients TO auditor;
-- Maintenant tous les SELECT sur clients seront audités

-- Statistiques de requêtes
CREATE EXTENSION pg_stat_statements;
SELECT query, calls, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY calls DESC LIMIT 20;
  • pgaudit — l'extension standard pour l'audit de conformité
  • pg_stat_statements — statistiques sur les requêtes exécutées
  • Logical decoding — pour le Change Data Capture (CDC) via les slots de réplication
  • Les logs sont envoyés dans le journal PostgreSQL (syslog, CSV, stderr)

Oracle — Unified Audit

-- Créer une politique d'audit unifiée
CREATE AUDIT POLICY sensitive_data_audit
    ACTIONS
        SELECT ON app.clients,
        UPDATE ON app.clients,
        DELETE ON app.clients,
        INSERT ON app.clients
    WHEN 'SYS_CONTEXT(''USERENV'', ''SESSION_USER'') NOT IN (''APP_USER'')'
    EVALUATE PER SESSION;

-- Activer la politique
AUDIT POLICY sensitive_data_audit;

-- Fine-Grained Auditing (FGA)
BEGIN
    DBMS_FGA.ADD_POLICY(
        object_schema  => 'APP',
        object_name    => 'CLIENTS',
        policy_name    => 'AUDIT_SALARY',
        audit_column   => 'SALAIRE',
        audit_condition => 'SALAIRE > 100000',
        statement_types => 'SELECT'
    );
END;
/

-- Consulter les logs d'audit
SELECT event_timestamp, dbusername, action_name, object_name, sql_text
FROM unified_audit_trail
WHERE event_timestamp > SYSDATE - 1
ORDER BY event_timestamp DESC;
  • Unified Audit (depuis 12c) — consolide tous les types d'audit en un seul flux
  • Fine-Grained Auditing (FGA) — audit conditionnel sur des colonnes spécifiques. Permet d'auditer uniquement quand certaines conditions sont remplies (ex : accès aux salaires > 100k).
  • Oracle Audit Vault and Database Firewall (AVDF) — solution centralisée pour collecter, stocker et analyser les logs d'audit de plusieurs bases
  • Flashback Data Archive — conservation de l'historique des modifications sur une longue durée (compliance, forensics)
  • Oracle est considéré comme ayant les capacités d'audit les plus complètes

10. Réseau et hardening

Le durcissement (hardening) de la configuration du serveur de base de données est une étape cruciale, souvent négligée. Une installation par défaut contient généralement des paramètres permissifs qui doivent être resserrés avant la mise en production.

Bonnes pratiques communes

  • Changer le port par défaut — 1433 (SQL Server), 5432 (PostgreSQL), 1521 (Oracle) sont les premiers ports scannés
  • Règles de pare-feu — n'autoriser que les adresses IP des serveurs applicatifs
  • Principe de moindre privilège — aucun compte applicatif ne doit être administrateur
  • Supprimer les bases d'exemple — Adventure Works, Northwind, HR, SCOTT, etc.
  • Gestion des patches — appliquer les correctifs de sécurité dans un délai raisonnable
  • Sauvegardes chiffrées — les backups doivent être chiffrés et stockés séparément
  • Supervision des connexions — alertes sur les connexions échouées, les connexions inhabituelles

SQL Server — Hardening spécifique

  • Compte sa — renommer ou désactiver. Ne jamais utiliser en production.
  • xp_cmdshell — toujours désactivé. Permet l'exécution de commandes OS depuis SQL.
  • Surface Area Configuration — désactiver les fonctionnalités inutilisées (OLE Automation, CLR, Database Mail, etc.)
  • SQL Server Browser — désactiver si non nécessaire (évite la découverte d'instances)
  • Ports dynamiques — configurer un port fixe plutôt que des ports dynamiques
-- Désactiver xp_cmdshell
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 0;
RECONFIGURE;

-- Désactiver le compte sa
ALTER LOGIN sa DISABLE;

-- Vérifier les fonctionnalités activées
SELECT name, value_in_use
FROM sys.configurations
WHERE name IN ('xp_cmdshell', 'clr enabled',
    'Ole Automation Procedures', 'cross db ownership chaining');

PostgreSQL — Hardening spécifique

  • pg_hba.conf — le fichier le plus critique. Bannir trust et md5, utiliser scram-sha-256 ou cert.
  • listen_addresses — restreindre aux interfaces réseau nécessaires (pas '*' en production)
  • Limites de connexion — max_connections, connection pooling (PgBouncer)
  • Rôle postgres — protéger comme root, ne jamais utiliser pour les applications
  • Extensions — n'installer que les extensions nécessaires, auditer régulièrement
# postgresql.conf — paramètres de sécurité
listen_addresses = '10.0.1.5'           -- PAS '*'
max_connections = 100
password_encryption = 'scram-sha-256'
log_connections = on
log_disconnections = on
log_statement = 'ddl'

# pg_hba.conf — exemple sécurisé
local   all   postgres               peer
hostssl all   app_user  10.0.1.0/24  scram-sha-256
host    all   all       0.0.0.0/0    reject

Oracle — Hardening spécifique

  • DBMS_NETWORK_ACL_ADMIN — contrôle granulaire des connexions réseau sortantes depuis PL/SQL (UTL_HTTP, UTL_TCP, UTL_SMTP)
  • AUDIT_SYS_OPERATIONS — auditer les opérations effectuées par SYSDBA/SYSOPER
  • O7_DICTIONARY_ACCESSIBILITY = FALSE — empêcher l'accès aux vues dictionnaire par les utilisateurs non privilégiés
  • Comptes par défaut — verrouiller tous les comptes inutilisés (DBSNMP, SCOTT, HR, etc.)
  • Oracle Database Vault — empêcher le DBA d'accéder aux données applicatives
  • Listener — sécuriser le listener (mot de passe, logging, restriction d'administration distante)
-- Contrôle d'accès réseau sortant (ACL)
BEGIN
    DBMS_NETWORK_ACL_ADMIN.APPEND_HOST_ACE(
        host       => 'api.example.com',
        lower_port => 443,
        upper_port => 443,
        ace        => xs$ace_type(
            privilege_list => xs$name_list('http'),
            principal_name => 'APP_USER',
            principal_type => xs_acl.ptype_db
        )
    );
END;
/

-- Auditer les opérations SYSDBA
ALTER SYSTEM SET audit_sys_operations = TRUE SCOPE = SPFILE;

-- Verrouiller les comptes inutilisés
ALTER USER scott ACCOUNT LOCK;
ALTER USER hr ACCOUNT LOCK;
ALTER USER dbsnmp ACCOUNT LOCK;
Rappel : Le hardening n'est pas un événement ponctuel. Il doit être revu régulièrement, en particulier après chaque mise à jour du SGBD, changement d'architecture ou audit de sécurité. Utilisez les CIS Benchmarks comme référence.

11. Conformité RGPD

Le Règlement Général sur la Protection des Données (RGPD / GDPR) impose des obligations strictes aux organisations qui traitent des données personnelles de résidents de l'UE. Les bases de données étant le lieu principal de stockage de ces données, leur sécurisation est directement liée à la conformité RGPD.

Articles clés et leur application aux bases de données

Article RGPD Obligation Application technique
Art. 25 Protection des données dès la conception (privacy by design) Intégrer le chiffrement, le masquage et le contrôle d'accès dès la phase de conception du schéma
Art. 32 Mesures techniques et organisationnelles appropriées Chiffrement (TDE, TLS), pseudonymisation, contrôle d'accès, audit, tests de sécurité réguliers
Art. 33 Notification de violation à l'autorité (72h) Si les données sont chiffrées et les clés non compromises, la notification peut ne pas être requise
Art. 34 Communication aux personnes concernées Exemption si les données sont rendues inintelligibles (chiffrement)
Art. 17 Droit à l'effacement (droit à l'oubli) Suppression effective ou crypto-shredding (destruction de la clé = destruction des données)
Art. 20 Droit à la portabilité Capacité d'exporter les données d'un individu dans un format structuré (CSV, JSON)
Art. 30 Registre des traitements Documentation des bases, des colonnes sensibles, des accès, des durées de conservation

Crypto-shredding : la destruction par la clé

Le crypto-shredding est une technique élégante pour le droit à l'effacement : plutôt que de supprimer physiquement les données (ce qui peut être complexe avec les backups, la réplication, les archives), on détruit la clé de chiffrement. Sans la clé, les données chiffrées deviennent définitivement inaccessibles, ce qui équivaut à une suppression effective.

Avantage du crypto-shredding : Il s'applique rétroactivement à toutes les copies des données — backups, réplicas, archives — sans avoir à les localiser et les modifier individuellement. C'est particulièrement utile dans les architectures distribuées.

Comment chaque SGBD aide à la conformité

SQL Server

  • TDE pour le chiffrement au repos
  • Always Encrypted pour les données ultra-sensibles
  • Dynamic Data Masking pour limiter l'exposition
  • Temporal Tables pour l'historique et la traçabilité
  • SQL Audit pour la journalisation
  • Data Classification (labels dans SSMS)
  • Azure Purview pour la gouvernance

PostgreSQL

  • pgcrypto / pg_tde pour le chiffrement
  • RLS pour l'isolation des données
  • pgaudit pour l'audit
  • postgresql_anonymizer pour la pseudonymisation
  • Gratuit — accessible aux PME
  • Extensible — s'adapte à tout contexte
  • SCRAM-SHA-256 pour l'authentification forte

Oracle

  • TDE (le plus mature) pour le chiffrement
  • Data Redaction pour le masquage temps réel
  • VPD / OLS pour l'isolation fine
  • Unified Audit / FGA pour la traçabilité
  • Database Vault pour la séparation des rôles
  • Oracle Data Safe (cloud) pour l'évaluation de conformité
  • Label Security pour la classification

13. Recommandations par cas d'usage

Startup / PME

Recommandation : PostgreSQL

  • RLS natif très flexible pour le multi-tenancy
  • pgcrypto pour le chiffrement applicatif
  • SCRAM-SHA-256 pour l'authentification forte
  • Large communauté et documentation abondante
  • Facile à héberger (on-premise ou cloud)

Enterprise Windows / .NET

Recommandation : SQL Server

  • Intégration native avec Active Directory
  • Always Encrypted pour la protection contre le DBA
  • Dynamic Data Masking intégré
  • Excellent outillage (SSMS, Azure Data Studio)
  • Temporal Tables pour la conformité
  • Ecosystème Microsoft cohérent

Grande entreprise / Banques / Assurances

Recommandation : Oracle Database

  • TDE le plus mature du marché
  • Database Vault pour la séparation des rôles
  • Label Security pour la classification
  • Unified Audit + FGA pour la conformité
  • Oracle Key Vault pour la gestion centralisée des clés
  • Support enterprise 24/7
  • Audit Vault and Database Firewall

Cloud-native / Microservices

Recommandation : Services managés

  • AWS : RDS PostgreSQL/MySQL, Aurora, DynamoDB
  • Azure : Azure SQL, Azure Database for PostgreSQL
  • OCI : Oracle Autonomous Database
  • GCP : Cloud SQL, AlloyDB
