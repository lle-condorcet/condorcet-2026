Guide du Logging en .NET 10

Toutes les methodes de logging avec Serilog, et quand envoyer directement a Elasticsearch ou passer par Logstash

Pourquoi le logging structure ?

Le logging est la premiere source d'information pour diagnostiquer des problemes en production, detecter des incidents de securite et comprendre le comportement d'une application. En .NET 10, le logging structure permet de generer des evenements JSON exploitables par des outils comme Elasticsearch, au lieu de simples chaines de texte.

Logging non structure

Console.WriteLine(
  $"User {userId} ordered {qty} items");

// Resultat : texte brut, impossible
// a filtrer ou agreger

Logging structure

logger.LogInformation(
  "User {UserId} ordered {Quantity} items",
  userId, qty);

// Resultat : JSON avec champs UserId
// et Quantity indexables
Principe cle : En logging structure, le message est un template avec des placeholders nommes ({UserId}), pas une string interpolee. Les valeurs sont transmises separement, ce qui permet l'indexation, le filtrage et l'agregation dans Elasticsearch.

Niveaux de log

.NET definit 6 niveaux de log, du plus verbeux au plus critique. Chaque niveau a un usage precis. Il est essentiel de choisir le bon niveau pour eviter le bruit en production tout en capturant les informations essentielles.

Niveau .NET / Serilog Quand l'utiliser Exemple concret
Trace Trace / Verbose Details ultra-fins, jamais active en production Entering method GetProductById with id=42
Debug Debug / Debug Informations utiles au developpement et au diagnostic Cache miss for key "products:42", querying DB
Information Information / Information Flux normal de l'application, jalons importants Order ORD-123 created for customer user@test.com
Warning Warning / Warning Situation anormale, non bloquante mais a surveiller Request to /api/products took 850ms (threshold: 500ms)
Error Error / Error Echec d'une operation, intervention peut-etre requise Failed to process order: product out of stock
Critical Critical / Fatal Panne systeme, l'application ne peut plus fonctionner Database connection lost, shutting down
Attention : Les noms different entre Microsoft.Extensions.Logging et Serilog. Le niveau Critical de .NET correspond a Fatal chez Serilog, et Trace correspond a Verbose.

Methode 1 : ILogger (logging built-in .NET)

ILogger<T> est l'abstraction de logging fournie par le framework .NET. Elle est injectee automatiquement par le conteneur de dependances et constitue le point d'entree standard pour tout logging en .NET.

Injection et utilisation de base

public class ProductService
{
    private readonly ILogger<ProductService> _logger;

    public ProductService(ILogger<ProductService> logger)
    {
        _logger = logger;
    }

    public async Task<Product?> GetByIdAsync(int id)
    {
        // Logging structure : {ProductId} est un placeholder nomme
        _logger.LogInformation("Fetching product {ProductId}", id);

        var product = await _db.Products.FindAsync(id);

        if (product is null)
        {
            _logger.LogWarning("Product {ProductId} not found", id);
            return null;
        }

        return product;
    }
}

Toutes les methodes de ILogger

Methode Niveau Usage type
LogTrace(message, args) Trace Details de flux internes
LogDebug(message, args) Debug Valeurs de variables, chemins logiques
LogInformation(message, args) Information Operations reussies, jalons
LogWarning(message, args) Warning Situations anormales non bloquantes
LogError(exception, message, args) Error Echecs avec stack trace
LogCritical(exception, message, args) Critical Pannes systeme
Log(level, message, args) Variable Niveau dynamique (determine au runtime)

Logger avec une exception

try
{
    await _orderService.CreateAsync(order);
}
catch (InvalidOperationException ex)
{
    // L'exception est passee en PREMIER parametre
    // Serilog capture automatiquement le stack trace
    _logger.LogError(ex,
        "Failed to create order for product {ProductId}, quantity {Quantity}",
        order.ProductId, order.Quantity);
    throw;
}
Erreur courante : Ne jamais utiliser l'interpolation de string ($"...") dans les messages de log. Cela detruit le logging structure car les valeurs sont integrees dans le texte au lieu d'etre des champs distincts.

Mauvais (string interpolation)

// Les valeurs sont perdues dans le texte
_logger.LogInformation(
    $"Order {orderId} created");

// Pas de champ OrderId dans le JSON
// Impossible a filtrer dans Kibana

Correct (message template)

// Le placeholder est un champ indexable
_logger.LogInformation(
    "Order {OrderId} created",
    orderId);

// Champ OrderId exploitable dans
// Elasticsearch et Kibana

Methode 2 : Serilog

Serilog est la bibliotheque de logging structuree la plus utilisee en .NET. Elle remplace le provider de logging par defaut et offre un ecosysteme riche de sinks (destinations), d'enrichisseurs (contexte automatique) et de filtres. Dans le projet ElkLoggingLabApp, Serilog est configure comme provider principal.

Installation

# Package principal pour ASP.NET Core
dotnet add package Serilog.AspNetCore

# Sink vers Elasticsearch
dotnet add package Serilog.Sinks.Elasticsearch

# Enrichisseurs de contexte
dotnet add package Serilog.Enrichers.Environment
dotnet add package Serilog.Enrichers.Process
dotnet add package Serilog.Enrichers.Thread

Configuration dans Program.cs

using Serilog;
using Serilog.Events;
using Serilog.Sinks.Elasticsearch;

Log.Logger = new LoggerConfiguration()
    // Niveau minimum global
    .MinimumLevel.Debug()

    // Surcharges par namespace (reduire le bruit des frameworks)
    .MinimumLevel.Override("Microsoft", LogEventLevel.Information)
    .MinimumLevel.Override("Microsoft.AspNetCore", LogEventLevel.Warning)
    .MinimumLevel.Override("System", LogEventLevel.Warning)

    // Enrichisseurs : contexte ajoute automatiquement
    .Enrich.FromLogContext()
    .Enrich.WithMachineName()
    .Enrich.WithProcessId()
    .Enrich.WithThreadId()
    .Enrich.WithEnvironmentName()
    .Enrich.WithProperty("Application", "MonApp")

    // Sinks : ou envoyer les logs
    .WriteTo.Console()
    .WriteTo.Elasticsearch(new ElasticsearchSinkOptions(
        new Uri("http://localhost:9200"))
    {
        IndexFormat = "myapp-logs-{0:yyyy.MM.dd}",
        AutoRegisterTemplate = true,
        NumberOfShards = 1,
        NumberOfReplicas = 0
    })
    .CreateLogger();

var builder = WebApplication.CreateBuilder(args);
builder.Host.UseSerilog(); // Remplace le logging .NET par Serilog

API de logging Serilog (statique)

En plus de l'injection de ILogger<T>, Serilog offre une API statique via Log :

// API statique - utile dans Program.cs ou des classes non-DI
Log.Information("Application starting up");
Log.Warning("Configuration {Key} is missing, using default", key);
Log.Error(exception, "Unhandled error in {Component}", component);
Log.Fatal("Application crashed");

// Fermer proprement (flush les buffers)
Log.CloseAndFlush();
Bonne pratique : Preferez l'injection de ILogger<T> dans vos classes. Reservez Log.Information() (API statique) pour le code de demarrage dans Program.cs et les situations ou l'injection de dependances n'est pas disponible.

Methode 3 : Logging structure avance

Le logging structure va au-dela des simples messages textuels. Chaque log est un evenement avec des proprietes typees et exploitables.

Destructuration d'objets

L'operateur @ devant un placeholder indique a Serilog de serialiser l'objet complet au lieu d'appeler ToString() :

var product = new Product { Id = 1, Name = "Laptop", Price = 999.99m };

// ToString() : affiche le type
_logger.LogInformation("Created product {Product}", product);
// Resultat : "Created product MyApp.Models.Product"

// Destructuration : serialise l'objet complet en JSON
_logger.LogInformation("Created product {@Product}", product);
// Resultat : { "Product": { "Id": 1, "Name": "Laptop", "Price": 999.99 } }
Attention : Ne destructurez pas d'objets contenant des donnees sensibles (mots de passe, tokens). Utilisez des classes DTO specifiques pour le logging si necessaire.

Contexte avec PushProperty

LogContext.PushProperty ajoute une propriete a tous les logs dans le scope courant. Ideal pour ajouter un contexte transversal (ID utilisateur, Correlation ID, etc.) :

using (LogContext.PushProperty("OrderId", orderId))
using (LogContext.PushProperty("CustomerId", customerId))
{
    // Tous les logs dans ce bloc auront OrderId et CustomerId
    _logger.LogInformation("Processing order");
    await _paymentService.ChargeAsync(amount);
    _logger.LogInformation("Payment completed");
}
// Ici, OrderId et CustomerId ne sont plus dans le contexte

ForContext : logger avec un sous-contexte

// Creer un logger enrichi pour une operation specifique
var orderLogger = Log.ForContext("OrderId", orderId)
                     .ForContext("Operation", "Fulfillment");

orderLogger.Information("Starting fulfillment");
orderLogger.Warning("Inventory low for {ProductId}", productId);
// Les deux logs contiennent OrderId et Operation

Methode 4 : LoggerMessage source generators

Depuis .NET 6, les source generators permettent de generer du code de logging a la compilation. C'est la methode la plus performante car elle evite le boxing, l'allocation de tableaux et le parsing des templates a chaque appel.

Syntaxe avec l'attribut [LoggerMessage]

public partial class OrderService
{
    private readonly ILogger<OrderService> _logger;

    // Le source generator cree le corps de la methode a la compilation
    [LoggerMessage(
        EventId = 1001,
        Level = LogLevel.Information,
        Message = "Order {OrderId} created for customer {CustomerEmail}")]
    partial void LogOrderCreated(string orderId, string customerEmail);

    [LoggerMessage(
        EventId = 1002,
        Level = LogLevel.Warning,
        Message = "High-value order {OrderId}: {Total:C} exceeds threshold")]
    partial void LogHighValueOrder(string orderId, decimal total);

    [LoggerMessage(
        EventId = 1003,
        Level = LogLevel.Error,
        Message = "Failed to process order {OrderId}")]
    partial void LogOrderFailed(Exception exception, string orderId);

    public async Task CreateAsync(Order order)
    {
        // Appel simple, zero allocation si le niveau est desactive
        LogOrderCreated(order.Id, order.CustomerEmail);

        if (order.TotalPrice > 1000)
            LogHighValueOrder(order.Id, order.TotalPrice);
    }
}

Avantages des source generators

Critere LoggerMessage generator ILogger classique
Allocations memoire Zero (si niveau desactive) Tableau params[] a chaque appel
Boxing des value types Aucun Boxing de int, decimal, etc.
Parsing du template A la compilation A chaque appel
Verification du template Erreur de compilation Erreur au runtime
Event IDs Obligatoire, bien organise Optionnel
Recommandation : Utilisez les source generators dans le code a forte frequence d'appel (middleware, boucles de traitement, services critiques). Pour du code occasionnel (demarrage, configuration), ILogger.LogInformation() reste parfaitement acceptable.

Methode 5 : Scopes et contexte

Les logging scopes de .NET permettent de regrouper des proprietes contextuelles qui seront ajoutees a tous les logs emis dans le scope. Serilog les supporte nativement.

BeginScope avec ILogger

public async Task ProcessOrderAsync(Order order)
{
    // Toutes les proprietes du dictionnaire sont ajoutees a chaque log
    using (_logger.BeginScope(new Dictionary<string, object>
    {
        ["OrderId"] = order.Id,
        ["CustomerId"] = order.CustomerId,
        ["CorrelationId"] = Activity.Current?.Id ?? Guid.NewGuid().ToString()
    }))
    {
        _logger.LogInformation("Starting order processing");

        await ValidateStock(order);
        _logger.LogDebug("Stock validated");

        await ChargePayment(order);
        _logger.LogInformation("Payment charged: {Amount}", order.TotalPrice);

        // Chaque log ci-dessus contient OrderId, CustomerId et CorrelationId
    }
}

Scopes imbriques

using (_logger.BeginScope("RequestId={RequestId}", requestId))
{
    _logger.LogInformation("Handling request");
    // Log contient RequestId

    using (_logger.BeginScope("UserId={UserId}", userId))
    {
        _logger.LogInformation("Authenticated user");
        // Log contient RequestId ET UserId
    }
}

Les enrichisseurs ajoutent automatiquement des proprietes a chaque evenement de log. Contrairement aux scopes qui sont temporaires, les enrichisseurs sont globaux et permanents.

Sinks : ou envoyer les logs ?

Un sink est une destination de log. Serilog permet de configurer plusieurs sinks simultanement. Les logs sont envoyes en parallele a chacun d'eux.

┌──────────────────┐ ┌──>│ Console (dev) │ │ └──────────────────┘ │ ┌──────────────────┐ ┌──────────────┐ ├──>│ Fichier (.log) │ │ Application │──Serilog──┤ └──────────────────┘ │ .NET 10 │ │ ┌──────────────────┐ └──────────────┘ ├──>│ Elasticsearch │ (direct) │ └──────────────────┘ │ ┌──────────────────┐ └──>│ Logstash (TCP) │──> Elasticsearch └──────────────────┘

Sink Console & Fichier

Console

// Template personnalise avec couleurs
.WriteTo.Console(outputTemplate:
    "[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj} {Properties:j}{NewLine}{Exception}")

// Sortie JSON (utile pour Docker / containers)
.WriteTo.Console(new RenderedCompactJsonFormatter())

Fichier avec rotation

// Package: Serilog.Sinks.File
.WriteTo.File(
    path: "logs/app-.log",
    rollingInterval: RollingInterval.Day,     // Nouveau fichier chaque jour
    retainedFileCountLimit: 30,               // Garder 30 jours
    fileSizeLimitBytes: 100_000_000,          // Max 100 Mo par fichier
    rollOnFileSizeLimit: true,                // Nouveau fichier si depasse
    outputTemplate: "[{Timestamp:yyyy-MM-dd HH:mm:ss.fff}] [{Level:u3}] {Message:lj}{NewLine}{Exception}"
)

// Fichier JSON (pour ingestion par Filebeat, Fluentd...)
.WriteTo.File(
    new CompactJsonFormatter(),
    path: "logs/app-.json",
    rollingInterval: RollingInterval.Day
)

Sink Elasticsearch (envoi direct)

Le sink Serilog.Sinks.Elasticsearch envoie les logs directement a Elasticsearch via HTTP, sans intermediaire. C'est l'approche utilisee dans le lab ELK.

Configuration complete

var elasticUrl = Environment.GetEnvironmentVariable("ELASTICSEARCH_URL")
    ?? "http://localhost:9200";

.WriteTo.Elasticsearch(new ElasticsearchSinkOptions(new Uri(elasticUrl))
{
    // Index journalier pour faciliter la rotation
    IndexFormat = "myapp-logs-{0:yyyy.MM.dd}",

    // Creer automatiquement le template d'index
    AutoRegisterTemplate = true,
    AutoRegisterTemplateVersion = AutoRegisterTemplateVersion.ESv7,

    // Configuration de l'index (lab = 1 shard, 0 replica)
    NumberOfShards = 1,
    NumberOfReplicas = 0,

    // Niveau minimum pour ce sink specifiquement
    MinimumLogEventLevel = LogEventLevel.Debug,

    // Buffer en memoire (lot d'envoi)
    BatchPostingLimit = 50,          // Envoyer par lots de 50
    Period = TimeSpan.FromSeconds(2), // Ou toutes les 2 secondes

    // Gestion des erreurs
    EmitEventFailure = EmitEventFailureHandling.WriteToSelfLog |
                       EmitEventFailureHandling.RaiseCallback,
    FailureCallback = e =>
        Console.Error.WriteLine($"Unable to submit event: {e.MessageTemplate}")
})

Configuration avec authentification (production)

.WriteTo.Elasticsearch(new ElasticsearchSinkOptions(new Uri(elasticUrl))
{
    IndexFormat = "myapp-logs-{0:yyyy.MM.dd}",
    AutoRegisterTemplate = true,

    // Authentification basique
    ModifyConnectionSettings = conn =>
        conn.BasicAuthentication("elastic", "my-secret-password")
            .ServerCertificateValidationCallback((o, cert, chain, errors) => true),

    // Ou avec une API key
    // ModifyConnectionSettings = conn =>
    //     conn.ApiKeyAuthentication("id", "api_key")
})

Sink Logstash (envoi via pipeline)

Au lieu d'envoyer directement a Elasticsearch, on peut envoyer les logs a Logstash qui les transforme, enrichit et route vers Elasticsearch.

Option A : Sink TCP vers Logstash

// Package: Serilog.Sinks.Network
.WriteTo.TCPSink(
    "tcp://localhost:5000",
    new CompactJsonFormatter()
)

Option B : Sink HTTP vers Logstash

// Package: Serilog.Sinks.Http
.WriteTo.Http(
    requestUri: "http://localhost:5000",
    queueLimitBytes: 10_000_000,   // 10 Mo de buffer
    textFormatter: new CompactJsonFormatter()
)

Option C : Fichier + Filebeat vers Logstash

// L'app ecrit en fichier JSON...
.WriteTo.File(
    new CompactJsonFormatter(),
    "logs/app-.json",
    rollingInterval: RollingInterval.Day
)

// ...Filebeat lit le fichier et envoie a Logstash
// Configuration filebeat.yml :
# filebeat.yml
filebeat.inputs:
  - type: log
    paths:
      - "/app/logs/app-*.json"
    json.keys_under_root: true
    json.add_error_key: true

output.logstash:
  hosts: ["logstash:5044"]

Configuration Logstash correspondante

# logstash.conf - Pipeline qui recoit les logs
input {
    # Depuis Serilog TCP sink
    tcp {
        port => 5000
        codec => json_lines
    }

    # Depuis Filebeat
    beats {
        port => 5044
    }
}

filter {
    # Enrichissement : ajouter des tags selon le contenu
    if "SECURITY" in [messageTemplate] {
        mutate { add_tag => ["security_event"] }
    }
    if "SLOW" in [messageTemplate] {
        mutate { add_tag => ["slow_query"] }
    }

    # GeoIP pour localiser les adresses IP
    if [fields][ClientIp] {
        geoip { source => "[fields][ClientIp]" }
    }
}

output {
    elasticsearch {
        hosts => ["http://elasticsearch:9200"]
        index => "myapp-logs-%{+YYYY.MM.dd}"
    }
}

Elasticsearch direct vs Logstash : quel choix ?

C'est une question d'architecture fondamentale. Les deux approches ont des cas d'usage distincts. Voici une comparaison detaillee pour vous aider a choisir.

Comparaison rapide

Critere Elasticsearch direct Via Logstash
Complexite Simple : 1 composant en moins Plus complexe : composant supplementaire
Latence Plus faible : envoi direct Hop supplementaire (~10-50ms)
Transformation Limitee : cote application uniquement Riche : grok, geoip, mutate, etc.
Buffering En memoire (sink buffer) Persistant (file d'attente disque)
Multi-sources Non (une app = un sink) Oui : agrege plusieurs sources
RAM consommee Negligeable (~10-50 Mo) 256-512 Mo pour Logstash (JVM)
Resilience Logs perdus si ES est down Buffering si ES est down temporairement
Securite L'app connait l'URL d'ES ES isole du reseau applicatif

Arbre de decision

Quand envoyer directement a Elasticsearch

Choisir l'envoi direct quand :

  • Application unique ou peu nombreuses — Pas besoin d'agreger des sources multiples
  • Logs deja structures — Serilog produit du JSON propre, pas besoin de transformation
  • Latence minimale requise — Monitoring temps reel sans intermediaire
  • Infrastructure simple — Lab, POC, petite equipe, pas d'ops dediee
  • Ressources limitees — Logstash consomme 256-512 Mo de RAM (JVM)
  • Developpement local — Docker Compose avec Elasticsearch + Kibana suffit

Quand passer par Logstash

Choisir Logstash quand :

  • Sources multiples et heterogenes — Logs .NET + logs Nginx + logs systeme + metriques
  • Transformation necessaire — Parsing de logs non structures, enrichissement GeoIP, anonymisation
  • Routage complexe — Envoyer les logs de securite a un index dedie, les metriques a un autre
  • Resilience critique — Le buffer persistant de Logstash protege contre les pannes d'ES
  • Securite renforcee — Elasticsearch n'est pas expose aux applications (seul Logstash y accede)
  • Multi-environnements — Pipeline centralisee qui normalise les logs de Dev, Staging et Prod
  • Conformite — Besoin de filtrer ou masquer des donnees sensibles avant indexation

Architectures types

Architecture 1 : Simple (lab / petite app)

C'est l'architecture utilisee dans le projet ElkLoggingLabApp.

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ .NET App │──HTTP──>│ Elasticsearch │<────────│ Kibana │ │ (Serilog │ │ │ │ │ │ ES sink) │ │ :9200 │ │ :5601 │ └──────────────┘ └──────────────┘ └──────────────┘

Avantages : Simple, peu de ressources, latence minimale.
Inconvenients : Pas de transformation, pas de buffer persistant, l'app connait ES.

Architecture 2 : Standard (production)

┌──────────────┐ ┌──────────────┐ │ .NET App 1 │──TCP──┐ │ │ ┌──────────┐ └──────────────┘ │ ┌─────────┴──┐ │ │ │ ┌──────────────┐ ├─>│ Logstash │──HTTP──> │ ES │<────────>│ Kibana │ │ .NET App 2 │──TCP──┤ │ (pipeline) │ │ Cluster │ │ │ └──────────────┘ │ └─────────┬──┘ │ │ └──────────┘ ┌──────────────┐ │ │ │ │ │ Nginx logs │──file─┘ filter: geoip └─────────┘ └──────────────┘ filter: security tags filter: anonymize PII

Avantages : Transformation, multi-sources, ES isole, buffer persistant.
Inconvenients : Logstash consomme 256-512 Mo RAM, composant supplementaire a operer.

Architecture 3 : Hybride (le meilleur des deux)

┌──────────────┐ │ .NET App │──Serilog──┬──> Elasticsearch (direct, pour les logs structures) │ │ │ └──────────────┘ └──> Fichier JSON (pour archivage / retraitement) │ Filebeat ──> Logstash ──> ES (index secondaire)

Usage : Les logs structures Serilog vont directement a ES pour le monitoring temps reel. Filebeat lit les fichiers pour le retraitement, l'enrichissement GeoIP et l'archivage long terme.

Performance du logging

Regles d'or

  1. Verifier le niveau avant de construire le message
// Mauvais : le message est construit meme si Debug est desactive
_logger.LogDebug("Processing items: {Items}",
    string.Join(", ", items.Select(i => i.Name)));

// Correct : verifier d'abord
if (_logger.IsEnabled(LogLevel.Debug))
{
    _logger.LogDebug("Processing items: {Items}",
        string.Join(", ", items.Select(i => i.Name)));
}

// Encore mieux : utiliser les source generators (verification gratuite)
  1. Ne pas loguer dans les boucles a haute frequence
// Mauvais : 10 000 logs pour 10 000 items
foreach (var item in items)
{
    _logger.LogDebug("Processing item {ItemId}", item.Id);
    Process(item);
}

// Correct : un seul log pour le lot
_logger.LogInformation("Processing {Count} items", items.Count);
foreach (var item in items)
    Process(item);
_logger.LogInformation("Processed {Count} items in {Duration}ms", items.Count, sw.ElapsedMilliseconds);
  1. Configurer le batching du sink Elasticsearch
// Envoyer les logs par lots plutot qu'un par un
new ElasticsearchSinkOptions(uri)
{
    BatchPostingLimit = 50,                 // Lots de 50 evenements max
    Period = TimeSpan.FromSeconds(2),        // Envoi toutes les 2 secondes
    QueueSizeLimit = 100_000,               // File d'attente max en memoire
}

Securite du logging

Ne JAMAIS loguer

  • Mots de passe (meme hashes)
  • Tokens JWT, API keys, session tokens
  • Numeros de carte bancaire, IBAN
  • Donnees de sante (RGPD/HIPAA)
  • Cles de chiffrement, secrets
  • Corps complet de requetes POST

A loguer systematiquement

  • Tentatives d'authentification (succes/echec)
  • Operations CRUD sur donnees sensibles
  • Changements de permissions/roles
  • Tentatives d'injection (SQL, XSS)
  • Rate limiting declenche
  • Erreurs d'autorisation (403)

Masquer les donnees sensibles

// Enrichisseur personnalise pour masquer les emails
public class SensitiveDataMaskingEnricher : ILogEventEnricher
{
    public void Enrich(LogEvent logEvent, ILogEventPropertyFactory factory)
    {
        var properties = logEvent.Properties.ToList();
        foreach (var prop in properties)
        {
            if (prop.Key.Contains("Email", StringComparison.OrdinalIgnoreCase))
            {
                var masked = MaskEmail(prop.Value.ToString().Trim('"'));
                logEvent.AddOrUpdateProperty(
                    factory.CreateProperty(prop.Key, masked));
            }
        }
    }

    private static string MaskEmail(string email)
    {
        var parts = email.Split('@');
        if (parts.Length != 2) return "***";
        return $"{parts[0][0]}***@{parts[1]}";
    }
}

// Utilisation
.Enrich.With<SensitiveDataMaskingEnricher>()

Filtrer avec Logstash

Avantage de Logstash : on peut anonymiser les donnees apres l'envoi par l'application, sans modifier le code source :

filter {
    # Masquer les emails dans tous les champs
    mutate {
        gsub => [
            "[fields][CustomerEmail]", "[a-zA-Z0-9._%+-]+@", "***@"
        ]
    }

    # Supprimer les champs sensibles avant indexation
    mutate {
        remove_field => ["[fields][Password]", "[fields][Token]"]
    }
}
C'est un cas ou Logstash est indispensable : si vous ne pouvez pas garantir que l'application ne logue jamais de donnees sensibles (code legacy, bibliotheques tierces), Logstash agit comme filet de securite en filtrant avant l'indexation.
