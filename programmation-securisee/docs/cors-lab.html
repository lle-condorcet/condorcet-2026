CORS Lab

Cross-Origin Resource Sharing — Guide complet

Qu'est-ce que CORS ?

CORS (Cross-Origin Resource Sharing) est un mecanisme de securite implemente par les navigateurs qui controle quelles origines web peuvent acceder aux ressources d'un serveur.

Une origine est definie par trois composants :

ComposantExemple
Scheme (protocole)http:// ou https://
Host (domaine)localhost, example.com
Port5300, 5301, 443
Important https://localhost:5300 et https://localhost:5301 sont des origines differentes car leurs ports different. C'est pour cela que notre labo necessite deux applications.

Same-Origin Policy (SOP)

La Same-Origin Policy est la regle de securite par defaut des navigateurs. Elle empeche un script d'une origine A de lire les reponses d'une origine B.

Site malveillant
http://evil.com
→ fetch() →
API Banque
http://banque.com
  1. Le navigateur envoie la requete au serveur (le serveur la recoit !)
  2. Le serveur repond normalement avec les donnees
  3. Le navigateur bloque la lecture de la reponse par le JavaScript
Subtilite La SOP ne bloque pas la requete elle-meme, mais la lecture de la reponse. Le serveur recoit bien la requete et repond. C'est le navigateur qui refuse de montrer la reponse au script.

Scenario 1 : Sans CORS

Le serveur ne renvoie aucun en-tete CORS. Le navigateur applique la SOP et bloque la lecture.

// Le serveur ne configure aucune politique CORS pour ces routes
app.MapGet("/api/no-cors/compte", () => Results.Json(compte));
// Pas de .RequireCors() → aucun en-tete CORS dans la reponse

Requete et reponse

// Requete
GET /api/no-cors/compte HTTP/1.1
Host: localhost:5300
Origin: https://localhost:5301

// Reponse — aucun en-tete CORS
HTTP/1.1 200 OK
Content-Type: application/json

→ Le navigateur bloque la lecture (pas de Access-Control-Allow-Origin)
Securise par defaut Ne pas configurer CORS est la configuration la plus restrictive. C'est le comportement par defaut d'ASP.NET Core.

Scenario 2 : Wildcard *

Access-Control-Allow-Origin: * autorise toute origine a lire la reponse, mais interdit l'envoi de credentials (cookies, en-tetes d'authentification).

options.AddPolicy("Wildcard", policy =>
{
    policy.AllowAnyOrigin()    // Access-Control-Allow-Origin: *
          .AllowAnyHeader()
          .AllowAnyMethod();
});

Avec et sans credentials

Sans credentials — Succes

fetch(url)
// → Reponse lisible

Les donnees publiques sont accessibles depuis toute origine.

Avec credentials — Echec

fetch(url, {
  credentials: 'include'
})
// → Erreur CORS

La specification interdit * + credentials.

Bon choix pour les API publiques Le wildcard est adapte pour les API qui servent des donnees publiques (meteo, taux de change, etc.) sans authentification.

Scenario 3 : Vulnerable

C'est la faille CORS critique. Le serveur reflete l'en-tete Origin de la requete et autorise les credentials. Tout site peut voler les donnees de l'utilisateur connecte.

options.AddPolicy("Vulnerable", policy =>
{
    policy.SetIsOriginAllowed(_ => true)   // Accepte TOUTE origine
          .AllowAnyHeader()
          .AllowAnyMethod()
          .AllowCredentials();                  // Envoie les cookies
});
Danger critique Cette configuration est equivalente a desactiver completement la protection CORS. N'importe quel site malveillant peut voler les donnees bancaires de l'utilisateur connecte.

Scenario 4 : Securise

Le serveur autorise uniquement les origines de confiance via une whitelist explicite.

options.AddPolicy("Secure", policy =>
{
    policy.WithOrigins("https://localhost:5301")  // Seule cette origine
          .AllowAnyHeader()
          .AllowAnyMethod()
          .AllowCredentials();                       // Cookies autorises
});

Origine autorisee

Origin: https://localhost:5301
→ Access-Control-Allow-Origin: https://localhost:5301
→ Acces autorise

Origine non autorisee

Origin: http://evil.com
→ Pas d'en-tete CORS
→ Bloque par le navigateur
Bonne pratique Toujours utiliser WithOrigins() avec une liste explicite d'origines. C'est la seule configuration securisee pour les API avec authentification.

Ce diagramme de sequence montre ce qui se passe quand un script tente d'acceder a une API cross-origin sans configuration CORS :

Lecture du diagramme

Ce diagramme illustre le comportement par defaut d'un navigateur lorsqu'un script tente de lire une ressource sur une autre origine (ici, evil.com essaie de lire l'API bancaire sur localhost:5300).

Le point cle a comprendre : la requete HTTP est bien envoyee au serveur, et le serveur repond normalement avec les donnees (etape 3). La protection se situe dans le navigateur, qui refuse de transmettre la reponse au JavaScript (etape 5). C'est pour cela qu'on dit que la SOP bloque la lecture, pas la requete.

En pratique, si vous ouvrez la console DevTools dans le navigateur, vous verrez le message d'erreur Access to fetch at '...' from origin '...' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource. Pourtant, dans l'onglet Network, la reponse du serveur est bien presente (le navigateur la cache simplement au JavaScript).

A retenir Sans aucune configuration CORS cote serveur, les donnees sont protegees contre la lecture cross-origin. C'est le comportement le plus securise et c'est le defaut d'ASP.NET Core.

Diagramme : Requete Preflight

Quand le navigateur detecte une requete "non simple" (methode PUT/DELETE, en-tete custom...), il envoie d'abord une requete OPTIONS pour demander la permission :

Lecture du diagramme

Le preflight est un mecanisme de negociation automatique entre le navigateur et le serveur. Le developpeur n'a rien a coder cote client : le navigateur detecte seul qu'une requete est "non simple" et envoie le preflight de maniere transparente.

Phase 1 — La demande de permission : le navigateur envoie une requete OPTIONS (sans body, sans cookie) qui contient trois informations : l'origine appelante, la methode HTTP souhaitee (Access-Control-Request-Method) et les en-tetes personnalises prevus (Access-Control-Request-Headers). Le serveur repond avec les en-tetes Access-Control-Allow-* correspondants. Si la methode ou les en-tetes ne sont pas autorises, le serveur peut repondre sans ces en-tetes et le navigateur arrete la.

Phase 2 — La requete reelle : uniquement si le preflight est valide, le navigateur envoie la vraie requete (DELETE, PUT, etc.) avec les cookies et les en-tetes. Le serveur traite la requete normalement.

Quand le preflight se declenche-t-il ? Pour toute requete qui n'est pas "simple", c'est-a-dire :

  • Methode autre que GET, POST ou HEAD
  • En-tetes personnalises (ex: Authorization, X-Custom-Header)
  • Content-Type autre que text/plain, multipart/form-data ou application/x-www-form-urlencoded

Un GET avec credentials: 'include' et sans en-tete custom est une requete "simple" : pas de preflight, le navigateur verifie simplement les en-tetes CORS dans la reponse.

Performance Le preflight ajoute un aller-retour reseau supplementaire. Utilisez l'en-tete Access-Control-Max-Age pour que le navigateur mette en cache le resultat et evite de refaire le preflight a chaque requete.

Diagramme : Attaque via CORS Vulnerable

Voici le scenario complet d'une attaque exploitant une mauvaise configuration CORS (SetIsOriginAllowed(_ => true) + AllowCredentials()) :

Lecture du diagramme

Ce diagramme montre une attaque complete en 3 phases, impliquant 4 acteurs. Il est essentiel de comprendre pourquoi cette attaque fonctionne et comment chaque element s'imbrique.

Phase "LEGIT" — La victime se connecte normalement

Jean Dupont se connecte a sa banque en ligne de maniere tout a fait normale. L'API repond avec un cookie Set-Cookie: session_banque=user_jean_dupont. Le navigateur stocke ce cookie et l'enverra automatiquement a chaque requete vers localhost:5300. Jusque la, rien d'anormal.

Phase "PIEGE" — La victime visite un site malveillant

Plus tard, la victime clique sur un lien (email de phishing, publicite, forum...) qui l'amene sur evil.com. Ce site contient du JavaScript malveillant qui s'execute automatiquement dans le navigateur de la victime. La victime ne voit rien de suspect — la page peut ressembler a un article normal, un jeu, ou n'importe quoi d'autre.

Phase "VOL" — Le JavaScript vole les donnees

Le script malveillant execute fetch('https://localhost:5300/api/vulnerable/compte', {credentials: 'include'}). Deux choses critiques se produisent :

  1. Le cookie est envoye automatiquement. Le navigateur voit que la requete va vers localhost:5300 et qu'il a un cookie pour ce domaine. Avec credentials: 'include' et SameSite: None, le cookie part avec la requete. L'API pense que c'est Jean Dupont qui demande ses donnees.
  2. Le serveur reflete l'origine. Puisque la politique CORS utilise SetIsOriginAllowed(_ => true), le serveur repond avec Access-Control-Allow-Origin: http://evil.com (il copie simplement l'Origin de la requete). Combine avec Access-Control-Allow-Credentials: true, le navigateur autorise le JavaScript de evil.com a lire la reponse.

Le script peut alors lire le JSON contenant l'IBAN, le solde et les transactions, puis l'envoyer a son propre serveur. La victime n'a rien vu, rien clique, rien confirme.

Pourquoi c'est si grave L'attaque est invisible pour la victime. Elle ne requiert aucune interaction. Il suffit de visiter une page web. Tout utilisateur connecte a la banque est vulnerable, et l'attaquant peut automatiser le vol de donnees a grande echelle.

Pourquoi la configuration securisee bloque cette attaque

Avec WithOrigins("https://localhost:5301"), le serveur ne renvoie l'en-tete Access-Control-Allow-Origin que si l'Origin de la requete correspond exactement a https://localhost:5301. Quand evil.com fait la meme requete, le serveur ne renvoie pas cet en-tete, et le navigateur bloque la lecture — meme si la reponse contient les donnees, le JavaScript ne peut pas y acceder.

Comprendre les 4 scenarios

Scenario 1 — Sans CORS (bleu) : C'est le comportement par defaut. Le serveur ne renvoie aucun en-tete CORS, donc le navigateur applique la Same-Origin Policy et bloque la lecture. C'est la configuration la plus restrictive et la plus sure. Elle convient aux API qui ne sont appelees que depuis la meme origine (ex: une application MVC classique ou le front-end et le back-end partagent le meme domaine).

Scenario 2 — Wildcard * (orange) : Le serveur repond avec Access-Control-Allow-Origin: *, ce qui autorise toute origine a lire la reponse. Cependant, la specification CORS interdit formellement la combinaison * + credentials. Le navigateur refuse d'envoyer des cookies si l'en-tete ACAO vaut *. C'est une protection deliberee : si n'importe qui peut lire, alors les donnees authentifiees ne doivent pas fuiter. Cette configuration est adaptee aux API publiques qui servent des donnees ouvertes (meteo, taux de change, catalogue produits...).

Scenario 3 — Vulnerable (rouge) : Le serveur accepte n'importe quelle origine (SetIsOriginAllowed(_ => true)) ET autorise les credentials. Pour contourner la limitation du wildcard, ASP.NET Core reflete l'en-tete Origin de la requete dans Access-Control-Allow-Origin. Resultat : le navigateur voit une origine specifique (pas *) avec Access-Control-Allow-Credentials: true, et autorise tout — y compris l'envoi de cookies. C'est la pire configuration possible. Elle revient a desactiver completement la protection CORS.

Scenario 4 — Securise (vert) : Le serveur n'autorise qu'une liste precise d'origines (WithOrigins("https://localhost:5301")). Quand une requete arrive depuis une origine non listee, le serveur ne renvoie tout simplement pas d'en-tete Access-Control-Allow-Origin, et le navigateur bloque la lecture. Les cookies sont autorises mais uniquement pour les origines de confiance. C'est la seule configuration correcte pour une API avec authentification.

Lecture de la matrice de securite

La matrice ci-dessus croise quatre criteres pour chaque configuration :

  • Lecture cross-origin : est-ce qu'un script sur une autre origine peut lire la reponse ?
  • Cookies envoyes : est-ce que le navigateur attache les cookies a la requete cross-origin ?
  • Attaque possible : est-ce qu'un site malveillant peut voler les donnees d'un utilisateur connecte ?
  • Cas d'usage : dans quel contexte cette configuration est-elle appropriee ?

La ligne rouge (origin reflechie + credentials) ne devrait jamais apparaitre dans une application en production. Si vous voyez SetIsOriginAllowed(_ => true) combine avec AllowCredentials() dans un code review, c'est une faille de securite critique a corriger immediatement.

Comment utiliser cet arbre

Commencez par la question du haut et suivez les branches selon votre cas. La premiere question est la plus importante : votre API utilise-t-elle des cookies ou des en-tetes d'authentification ?

Si non (branche gauche) : votre API ne gere pas de sessions utilisateur. Si elle sert des donnees publiques accessibles a tous (ex: une API meteo), utilisez AllowAnyOrigin() (wildcard *). Si elle est interne et ne doit pas etre appelee depuis d'autres origines, ne configurez pas CORS du tout — la SOP fera le travail.

Si oui (branche droite) : votre API utilise des cookies ou des tokens. La question devient : connaissez-vous les origines qui doivent y acceder ? Si oui (ex: votre SPA est sur app.example.com et votre API sur api.example.com), listez-les explicitement avec WithOrigins(). C'est la configuration recommandee.

La branche rouge en bas a droite (SetIsOriginAllowed(_ => true) + credentials) n'est jamais la bonne reponse en production. Si vous ne connaissez pas vos origines, c'est un probleme d'architecture a resoudre, pas une raison d'ouvrir toutes les portes.

Regle d'or En cas de doute, ne configurez pas CORS du tout. La SOP protege par defaut. N'ouvrez CORS que pour les origines dont vous avez explicitement besoin.

Pour certaines requetes (methodes autres que GET/POST, en-tetes personnalises, etc.), le navigateur envoie d'abord une requete OPTIONS (preflight) pour demander au serveur si la requete reelle est autorisee.

Configuration ASP.NET Core

Politiques nommees

builder.Services.AddCors(options =>
{
    // Politique securisee
    options.AddPolicy("Secure", policy =>
    {
        policy.WithOrigins("https://localhost:5301")
              .AllowAnyHeader()
              .AllowAnyMethod()
              .AllowCredentials();
    });
});

Application par route

// Appliquer une politique CORS a une route specifique
app.MapGet("/api/secure/compte", () => Results.Json(compte))
    .RequireCors("Secure");

// Route sans politique CORS (bloquee par SOP)
app.MapGet("/api/no-cors/compte", () => Results.Json(compte));
// Pas de .RequireCors() → aucun en-tete CORS

Bonnes pratiques

  1. Ne jamais utiliser SetIsOriginAllowed(_ => true) avec AllowCredentials() — c'est la faille la plus grave
  2. Utiliser WithOrigins() avec une liste explicite d'origines de confiance
  3. * uniquement pour les API publiques sans authentification
  4. Appliquer CORS par route (avec .RequireCors()) plutot que globalement
  5. Limiter les methodes et en-tetes autorises au minimum necessaire
  6. Configurer Access-Control-Max-Age pour eviter les preflight repetitifs
  7. Ne pas confondre CORS et authentification — CORS controle qui peut lire la reponse, pas qui peut envoyer des requetes
Rappel CORS est un mecanisme du navigateur. Un script cote serveur (cURL, Postman, etc.) peut toujours acceder a l'API sans restriction CORS. C'est pour cela que CORS ne remplace pas l'authentification et l'autorisation cote serveur.

Pourquoi utiliser CORS concretement ?

CORS n'est pas une lubie technique — c'est la reponse a un besoin reel des architectures modernes. Voici les cas concrets ou CORS est indispensable.

1. Architecture front-end / back-end separees

Dans une architecture SPA (React, Angular, Vue.js), le front-end est souvent servi depuis un domaine different de l'API : 

┌─────────────────────────────┐      ┌──────────────────────────────┐
│  Front-end (SPA)            │      │  API Back-end                │
│  https://app.monsite.com    │ ───► │  https://api.monsite.com     │
│                             │      │                              │
│  React / Angular / Vue      │      │  ASP.NET / Node / Django     │
└─────────────────────────────┘      └──────────────────────────────┘
     Origine A                             Origine B
     → Le navigateur bloque sans CORS !

Sans CORS configure sur l'API, le navigateur bloque toutes les reponses. C'est le cas d'usage le plus courant.

2. Microservices et API Gateway

Dans une architecture microservices, un portail web peut devoir appeler plusieurs API sur des sous-domaines differents : 

https://portal.company.com  appelle :
   ├── https://auth.company.com/api/login
   ├── https://orders.company.com/api/orders
   ├── https://billing.company.com/api/invoices
   └── https://analytics.company.com/api/stats

→ Chaque sous-domaine = origine differente = CORS necessaire

3. Widgets et integrations tierces

Un widget integre sur un site client (chatbot, formulaire, carte interactive) doit communiquer avec votre API depuis l'origine du client.

4. API publiques

Les API publiques (meteo, taux de change, donnees ouvertes) utilisent Access-Control-Allow-Origin: * pour etre consommables depuis n'importe quel site web.

5. Environnements de developpement

En dev, le front-end tourne souvent sur localhost:3000 (Vite/Webpack) et l'API sur localhost:5000 — deux origines differentes.

Regle simple Si votre front-end et votre API n'ont pas exactement le meme scheme + host + port, vous avez besoin de CORS. C'est aussi simple que cela.

CORS au-dela de l'application : Reverse Proxy, CDN, WAF

CORS est un mecanisme HTTP (des en-tetes de reponse). Il peut donc etre configure a n'importe quel niveau de l'infrastructure qui traite des reponses HTTP — pas uniquement dans le code applicatif.

Nginx — Configuration CORS

# /etc/nginx/conf.d/api.conf
server {
    listen 443 ssl;
    server_name api.monsite.com;

    location /api/ {

        # Gestion du preflight OPTIONS
        if ($request_method = 'OPTIONS') {
            add_header 'Access-Control-Allow-Origin' 'https://app.monsite.com';
            add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE';
            add_header 'Access-Control-Allow-Headers' 'Authorization, Content-Type';
            add_header 'Access-Control-Allow-Credentials' 'true';
            add_header 'Access-Control-Max-Age' 86400;
            return 204;
        }

        # En-tetes CORS sur les reponses normales
        add_header 'Access-Control-Allow-Origin' 'https://app.monsite.com' always;
        add_header 'Access-Control-Allow-Credentials' 'true' always;

        proxy_pass http://backend:5000;
    }
}

CORS vs Firewall vs WAF — Qui fait quoi ?

Une confusion frequente est de penser que CORS remplace un firewall ou un WAF. Ces trois mecanismes operent a des niveaux differents et sont complementaires.

Critere CORS Firewall (L3/L4) WAF (L7)
Couche OSI Application (L7) — navigateur Reseau / Transport (L3/L4) Application (L7) — serveur
Applique par Le navigateur du client Le routeur / switch / OS Le proxy/serveur
Protege contre Lecture cross-origin depuis un navigateur Acces reseau non autorise (IP, port) Attaques applicatives (SQLi, XSS, bots)
Bloque cURL/Postman ? Non Oui (si IP bloquee) Oui (si regle matchee)
Bloque un script malveillant dans un navigateur ? Oui (lecture de la reponse) Non (la requete passe) Partiellement (selon les regles)
Granularite Par origine, methode, en-tete Par IP, port, protocole Par pattern HTTP, user-agent, payload
Configurable par le dev ? Oui Non (equipe infra/reseau) Parfois (regles custom)
Exemples En-tetes HTTP CORS iptables, pf, NSG Azure, Security Groups AWS ModSecurity, AWS WAF, Cloudflare WAF, Azure Front Door

Analogie : la securite d'un immeuble

┌─────────────────────────────────────────────────────────────┐
│  FIREWALL = La grille d'entree de l'immeuble               │
│  → Filtre qui peut ENTRER (adresse IP / port)               │
│  → Ne regarde pas ce que les gens font une fois entres      │
│                                                             │
│  WAF = Le vigile dans le hall                               │
│  → Inspecte les sacs (payloads HTTP)                        │
│  → Bloque les comportements suspects (SQLi, XSS, bots)     │
│  → Peut aussi verifier les badges (tokens, signatures)      │
│                                                             │
│  CORS = Le badge d'acces aux etages                         │
│  → Controle quels VISITEURS (origines) peuvent acceder      │
│    a quelles DONNEES (reponses)                             │
│  → Ne bloque pas l'entree, bloque la LECTURE de la reponse  │
│  → Applique par le visiteur lui-meme (le navigateur)        │
│  → Un visiteur mal intentionne avec son propre outil         │
│    (cURL) peut ignorer le badge                             │
└─────────────────────────────────────────────────────────────┘

Defense en profondeur : combiner les couches

La bonne approche est d'utiliser toutes les couches ensemble :

┌────────────────────────────────────────────────────────────┐
│  Internet                                                  │
│      │                                                     │
│      ▼                                                     │
│  ┌──────────────────────┐                                  │
│  │ FIREWALL (L3/L4)     │  Bloquer les IP/ports non        │
│  │ NSG / Security Group │  necessaires                     │
│  └──────────┬───────────┘                                  │
│             ▼                                              │
│  ┌──────────────────────┐                                  │
│  │ WAF (L7)             │  Bloquer SQLi, XSS, bots,        │
│  │ AWS WAF / Cloudflare │  rate limiting                   │
│  └──────────┬───────────┘                                  │
│             ▼                                              │
│  ┌──────────────────────┐                                  │
│  │ Reverse Proxy        │  TLS termination, CORS headers,  │
│  │ Nginx / Traefik      │  load balancing                  │
│  └──────────┬───────────┘                                  │
│             ▼                                              │
│  ┌──────────────────────┐                                  │
│  │ APPLICATION          │  CORS (code), authentication,    │
│  │ ASP.NET Core         │  authorization, validation       │
│  └──────────────────────┘                                  │
└────────────────────────────────────────────────────────────┘
A retenir CORS protege les utilisateurs du navigateur contre le vol de donnees par des sites tiers. Le firewall protege le serveur contre les acces reseau non autorises. Le WAF protege l'application contre les attaques applicatives. Les trois sont necessaires — aucun ne remplace les autres.

Quand configurer CORS au niveau infra plutot que dans le code ?

Situation Ou configurer CORS Pourquoi
Monolithe unique Dans l'application Simple, proche du code, facile a maintenir
Microservices (5+ APIs) API Gateway ou Reverse Proxy Evite de dupliquer la config dans chaque service
Assets statiques (fonts, images) CDN (CloudFront, Cloudflare) Les fichiers statiques n'ont pas de code applicatif
API heritee (legacy) sans acces au code Reverse Proxy (Nginx) Ajouter CORS sans modifier l'application
Multi-cloud / multi-techno WAF ou API Gateway Politique uniforme quel que soit le langage backend
Piege courant Si CORS est configure a plusieurs niveaux (ex: Nginx + ASP.NET), les en-tetes peuvent etre dupliques (Access-Control-Allow-Origin apparait deux fois), ce qui provoque une erreur CORS dans le navigateur. Choisissez un seul niveau pour gerer CORS, ou assurez-vous que les niveaux intermediaires ne rajoutent pas d'en-tetes en double.
