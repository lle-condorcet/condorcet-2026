Content Security Policy

Comprendre et implementer CSP pour securiser les applications web

Objectif du cours A la fin de cette documentation, vous serez capable de comprendre le role de CSP, rediger des politiques adaptees, et implementer CSP dans une application .NET.

Content Security Policy (CSP) est un mecanisme de securite implemente par les navigateurs web qui permet aux developpeurs de controler quelles ressources (scripts, styles, images, etc.) peuvent etre chargees et executees sur leurs pages.

CSP fonctionne via un en-tete HTTP (ou une balise <meta>) qui declare une liste blanche de sources autorisees. Toute ressource ne correspondant pas a cette politique est bloquee par le navigateur. 

// Exemple d'en-tete CSP
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com

Pourquoi utiliser CSP ?

Le probleme : les attaques par injection

Sans CSP, un navigateur execute aveuglément tout code present dans la page HTML. Si un attaquant parvient a injecter du contenu (via XSS, injection HTML, etc.), le navigateur ne fait aucune difference entre le code legitime et le code malveillant.

Sans CSP

  • Le navigateur execute tout script present dans le HTML
  • Les scripts inline malveillants s'executent
  • Les ressources externes non controlees se chargent
  • Vol de cookies, redirection, keylogging possibles

Avec CSP

  • Seules les sources autorisees sont chargees
  • Les scripts inline sont bloques par defaut
  • Les connexions non prevues sont refusees
  • Le navigateur rapporte les violations

CSP comme couche de defense en profondeur

Attention CSP n'est pas un substitut a la validation et l'encodage des entrees. C'est une couche supplementaire de defense (defense in depth). Meme avec CSP, il faut continuer a encoder les sorties et valider les entrees.

Methodes de declaration

1. En-tete HTTP (recommande) :

Content-Security-Policy: default-src 'self'

2. Balise meta (fallback) :

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'">
Note L'en-tete HTTP est prefere car il couvre toutes les ressources, y compris celles chargees avant le parsing du HTML. La balise <meta> ne supporte pas toutes les directives (ex: frame-ancestors, report-uri).

Directives principales

Directive Controle Exemple
default-src Fallback pour toutes les directives non specifiees default-src 'self'
script-src Sources autorisees pour JavaScript script-src 'self' 'nonce-abc123'
style-src Sources autorisees pour CSS style-src 'self' 'unsafe-inline'
img-src Sources autorisees pour les images img-src 'self' data: https:
connect-src URLs autorisees pour fetch, XHR, WebSocket connect-src 'self' https://api.example.com
font-src Sources autorisees pour les polices font-src 'self' https://fonts.gstatic.com
frame-src Sources autorisees pour les iframes frame-src 'none'
frame-ancestors Qui peut embarquer cette page en iframe frame-ancestors 'self'
object-src Sources pour <object>, <embed>, <applet> object-src 'none'
base-uri URLs autorisees pour <base> base-uri 'self'
form-action URLs cibles autorisees pour les formulaires form-action 'self'
upgrade-insecure-requests Force HTTPS pour toutes les requetes upgrade-insecure-requests

Valeurs de source

Valeur Signification Securite
'self' Meme origine (protocole + domaine + port) SURE
'none' Aucune source autorisee SURE
https://example.com Domaine specifique SURE
https: Tout domaine en HTTPS MOYEN
'nonce-<base64>' Script avec attribut nonce correspondant SURE
'sha256-<hash>' Script dont le contenu correspond au hash SURE
'strict-dynamic' Fait confiance aux scripts charges par un script autorise SURE
'unsafe-inline' Autorise les scripts/styles inline DANGER
'unsafe-eval' Autorise eval(), new Function(), etc. DANGER
* Toute source (wildcard) DANGER
A eviter absolument 'unsafe-inline' et 'unsafe-eval' annulent la protection CSP contre les XSS. Utilisez des nonces ou des hashes a la place.

Exemples concrets de politiques

Politique stricte (recommandee)

Content-Security-Policy:
  default-src 'none';
  script-src 'self' 'nonce-r4nd0m';
  style-src 'self';
  img-src 'self';
  font-src 'self';
  connect-src 'self';
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';
  object-src 'none'

Politique pour site avec CDN

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.jsdelivr.net;
  style-src 'self' https://cdn.jsdelivr.net;
  img-src 'self' data: https:;
  font-src 'self' https://fonts.gstatic.com

Politique permissive (a eviter en production)

// MAUVAIS EXEMPLE - ne fait quasiment rien
Content-Security-Policy:
  default-src * 'unsafe-inline' 'unsafe-eval'

Nonces et Hashes

Les nonces et hashes permettent d'autoriser des scripts inline specifiques sans ouvrir la porte a 'unsafe-inline'.

Nonce (Number used ONCE)

Un nonce est une valeur aleatoire unique generee a chaque requete :

// En-tete CSP
Content-Security-Policy: script-src 'nonce-abc123XYZ'

// Dans le HTML - ce script s'execute
<script nonce="abc123XYZ">
  console.log("Autorise !");
</script>

// Ce script est BLOQUE (pas de nonce)
<script>
  document.location = "https://evil.com";
</script>
Regle critique Le nonce doit changer a chaque requete. Un nonce statique est inutile car l'attaquant pourrait l'inclure dans son injection. Utilisez un generateur cryptographiquement sur (ex: RandomNumberGenerator en .NET).

Hash

Alternative au nonce : autoriser un script par le hash de son contenu :

// En-tete CSP avec hash SHA-256
Content-Security-Policy: script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='

// Le script dont le hash SHA-256 correspond
<script>alert('Hello');</script>

Reporting des violations

CSP peut rapporter les violations a un endpoint de votre choix, ce qui est utile pour :

  • Detecter des tentatives d'attaque
  • Identifier des ressources bloquees par erreur
  • Tester une politique avant de la deployer (mode report-only)

Mode Report-Only

// Ne bloque rien, rapporte seulement
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report

Exemple de rapport JSON

{
  "csp-report": {
    "document-uri": "https://example.com/page",
    "violated-directive": "script-src 'self'",
    "blocked-uri": "https://evil.com/malware.js",
    "original-policy": "default-src 'self'; script-src 'self'",
    "disposition": "enforce",
    "status-code": 200
  }
}

Strategie de deploiement recommandee

  1. Report-Only : deployer en mode observation pendant 1-2 semaines
  2. Analyser : corriger les faux positifs identifies dans les rapports
  3. Enforce : passer en mode actif une fois la politique validee
  4. Surveiller : continuer a collecter les rapports en production

Erreurs courantes

1. Utiliser 'unsafe-inline' pour "faire marcher" le site C'est la premiere erreur des debutants. Utilisez des nonces ou externalisez vos scripts.
2. Oublier default-src Sans default-src, les directives non specifiees n'ont aucune restriction. Toujours commencer par default-src 'none' ou default-src 'self'.
3. Politique trop permissive avec wildcard script-src * autorise n'importe quel domaine a executer du JavaScript. Privilegiez la liste blanche de domaines specifiques.
4. Nonce statique ou previsible Le nonce doit etre cryptographiquement aleatoire et change a chaque requete. Un nonce code en dur est equivalent a 'unsafe-inline'.
5. Ignorer les rapports de violation Les rapports CSP sont une mine d'or pour detecter les attaques et les erreurs de configuration.
