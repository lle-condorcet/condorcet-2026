Git — Bonnes Pratiques et Workflows

Du commit local au deploiement — Maitriser Git en ligne de commande et avec Fork

1. Fondamentaux de Git

Qu'est-ce que Git ?

Git est un systeme de controle de version distribue (DVCS) cree par Linus Torvalds en 2005 pour le developpement du noyau Linux. Contrairement aux systemes centralises (SVN, TFS), chaque developpeur possede une copie complete de l'historique du projet.

Centralise (SVN, TFS)

  • Un seul serveur central
  • Connexion requise pour commiter
  • Point de defaillance unique
  • Branches lourdes et couteuses

Distribue (Git)

  • Chaque clone est un repo complet
  • Travail hors-ligne possible
  • Pas de point de defaillance unique
  • Branches ultra-legeres et rapides

Concepts cles

ConceptDescription
RepositoryDossier contenant le projet et tout son historique (dans .git/)
CommitInstantane (snapshot) de l'etat du projet a un moment donne
BranchPointeur mobile vers un commit — permet le developpement parallele
RemoteVersion distante du depot (ex: origin sur GitHub/GitLab)
HEADPointeur vers le commit/branche actuellement "checked out"
SHA-1Hash unique de 40 caracteres identifiant chaque commit (ex: a3f5c2d...)
TagReference nommee et fixe vers un commit (pour les versions/releases)
IndexZone de staging — fichiers prepares pour le prochain commit

Les 3 zones de Git

Comprendre les 3 zones est essentiel pour maitriser Git. Chaque fichier passe par ces etapes avant d'etre sauvegarde dans l'historique.

┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ Working │ │ Staging Area │ │ Repository │ │ Directory │────>│ (Index) │────>│ (.git) │ │ │ add │ │commit│ │ │ Fichiers │ │ Pret a commit │ │ Historique │ │ modifies │ │ │ │ complet │ └─────────────────┘ └─────────────────┘ └─────────────────┘ │ │ │<──────────────────────────────────────────────│ │ checkout │
ZoneDescriptionCommande associee
Working Directory Vos fichiers tels qu'ils sont sur le disque. Les modifications apparaissent ici. git diff
Staging Area (Index) Zone de preparation. Seuls les fichiers "stages" seront inclus dans le prochain commit. git add, git diff --staged
Repository (.git) L'historique complet. Chaque commit est un snapshot immuable. git commit, git log
Cycle de vie d'un fichier : Untracked → Staged (git add) → Committed (git commit) → Modified → Staged → Committed → ...

Configuration initiale

Avant de commencer a utiliser Git, configurez votre identite et vos preferences :

# Identite (obligatoire)
git config --global user.name "Votre Nom"
git config --global user.email "votre@email.com"

# Branche par defaut (main au lieu de master)
git config --global init.defaultBranch main

# Fin de ligne (important sous Windows!)
git config --global core.autocrlf true

# Strategie de pull (merge par defaut, pas rebase)
git config --global pull.rebase false

# Editeur par defaut
git config --global core.editor "code --wait"

# Activer les couleurs
git config --global color.ui auto

# Alias utiles
git config --global alias.st "status"
git config --global alias.co "checkout"
git config --global alias.br "branch"
git config --global alias.lg "log --oneline --graph --all --decorate"

# Verifier la configuration
git config --list
core.autocrlf sous Windows : Mettez cette option a true pour eviter les problemes de fin de ligne (LF vs CRLF) lors de la collaboration avec des developpeurs sous macOS/Linux.

2. Operations courantes

Pour chaque operation, nous montrons la commande CLI et l'equivalent dans Fork (client Git graphique).

Clone — Copier un depot distant

CLI Ligne de commande

# Clone via HTTPS
git clone https://gitlab.example.com/team/project.git

# Clone via SSH (recommande)
git clone git@github.com:user/project.git

# Clone dans un dossier specifique
git clone git@github.com:user/project.git mon-dossier

# Clone partiel (shallow) — plus rapide
git clone --depth 1 https://github.com/user/project.git

Fork Client graphique

File → Clone... (ou Ctrl+Shift+O)

  1. Collez l'URL du depot
  2. Choisissez le dossier de destination
  3. Cliquez sur Clone

Fork detecte automatiquement le protocole (HTTPS ou SSH) et vous propose de configurer les credentials si necessaire.

Add & Commit — Preparer et sauvegarder

CLI Ligne de commande

# Stager un fichier specifique
git add src/MonFichier.cs

# Stager plusieurs fichiers
git add src/Auth.cs src/Login.cs

# Stager tout (attention aux fichiers non voulus!)
git add .

# Stager des parties d'un fichier (interactif)
git add -p src/MonFichier.cs

# Commiter avec un message
git commit -m "feat: ajouter la validation du formulaire"

# Commiter avec un message multi-ligne
git commit -m "feat: ajouter OAuth2" -m "Ajoute le support Google et Microsoft."

# Modifier le dernier commit (message ou contenu)
git commit --amend -m "feat: nouveau message"

Fork Client graphique

Dans l'onglet Changes :

  1. Les fichiers modifies apparaissent dans la liste
  2. Cochez les fichiers a stager (ou cliquez Stage All)
  3. Ecrivez le message de commit en bas
  4. Cliquez Commit ou Ctrl+Enter

Astuce : Cliquez sur un fichier pour voir le diff. Vous pouvez stager des lignes individuelles en selectionnant et en cliquant Stage Selected Lines.

Attention avec git add . : Cette commande ajoute tous les fichiers, y compris ceux que vous ne voulez peut-etre pas commiter (fichiers de build, secrets, logs...). Utilisez toujours un .gitignore a jour et preferez ajouter des fichiers specifiques.

Push, Pull, Fetch — Synchronisation

CLI Ligne de commande

# Pousser vers le remote
git push origin main

# Pousser et lier la branche locale au remote
git push -u origin feature/ma-branche

# Tirer les changements (fetch + merge)
git pull origin main

# Recuperer sans fusionner
git fetch --all

# Pousser les tags
git push --tags

Fork Client graphique

PushCtrl+P
PullCtrl+Shift+P
FetchCtrl+Shift+F

Les boutons correspondants sont egalement visibles dans la barre d'outils superieure. Fork affiche le nombre de commits en avance/retard par rapport au remote.

Local Remote (origin) ┌──────────────┐ ┌──────────────┐ │ main │ ── git push ──> │ main │ │ ● ● ● ● │ │ ● ● ● ● │ │ │ <── git pull ── │ │ │ │ (fetch + merge) │ │ │ │ │ │ │ │ <── git fetch ── │ │ │ │ (sans merge) │ │ └──────────────┘ └──────────────┘
Pull = Fetch + Merge : git pull telecharge les changements distants et les fusionne automatiquement. Si vous voulez d'abord inspecter les changements, utilisez git fetch puis git merge origin/main.

Status & Log — Inspecter l'etat

# Voir l'etat des fichiers
git status

# Version courte
git status -s

# Historique compact avec graphe
git log --oneline --graph --all

# Historique formate
git log --pretty=format:"%h %s (%an, %ar)"

# Voir les differences non stagees
git diff

# Voir les differences stagees (pretes a commit)
git diff --staged

# Voir les modifications d'un fichier specifique
git diff src/MonFichier.cs

# Qui a modifie chaque ligne ? (blame)
git blame src/MonFichier.cs

# Historique d'un fichier
git log --follow src/MonFichier.cs

Fork L'onglet Activity affiche le graphe visuel des branches et commits. L'onglet Changes montre les fichiers modifies avec un diff colore. Clic droit sur un fichier → Blame pour voir l'historique ligne par ligne.

3. Branches — Strategies et exemples

Cycle de vie d'une branche

main ●───●───────────────●──────────────●───● \ ↑ merge / feature/auth ●───●───●────────────────────● \ ●───● (revue de code / PR)

Les branches Git sont des pointeurs legers vers des commits. Creer une branche ne copie rien — c'est instantane, quelle que soit la taille du projet.

Creer et naviguer

# Creer et basculer (ancienne syntaxe)
git checkout -b feature/login

# Creer et basculer (nouvelle syntaxe, recommandee)
git switch -c feature/login

# Creer sans basculer
git branch feature/login

# Lister les branches
git branch                    # locales
git branch -r                 # distantes
git branch -a                 # toutes

# Basculer vers une branche existante
git switch main
git checkout main

# Creer une branche depuis un commit specifique
git switch -c fix/bug-123 abc123f

Fork Clic droit sur un commit → Create Branch..., ou menu Repository → Branch → New Branch.... Double-cliquez sur une branche dans la sidebar pour y basculer.

Fusionner (Merge)

# Basculer sur la branche cible
git checkout main

# Fusionner (fast-forward si possible)
git merge feature/login

# Fusionner en creant un commit de merge (recommande)
git merge --no-ff feature/login

# Annuler un merge en cours (conflit)
git merge --abort

Fast-Forward Merge

Avant: main ●───● \ feat ●───● Apres: main ●───●───●───● (main avance simplement)

Merge --no-ff (recommande)

Avant: main ●───● \ feat ●───● Apres: main ●───●───────● (merge commit) \ / feat ●───●
Pourquoi --no-ff ? Il preserve l'historique visuel des branches, meme quand un fast-forward serait possible. On voit clairement quand une feature a ete integree.

Fork Clic droit sur la branche a fusionner → Merge into Current Branch.... Fork propose automatiquement l'option --no-ff.

Supprimer une branche

# Supprimer une branche locale (safe — refuse si non mergee)
git branch -d feature/login

# Supprimer une branche locale (force — meme si non mergee)
git branch -D feature/login

# Supprimer une branche distante
git push origin --delete feature/login

# Nettoyer les references de branches distantes supprimees
git fetch --prune
Attention avec -D : Cette commande force la suppression meme si les commits de la branche n'ont pas ete merges. Vous perdrez du travail si vous n'avez pas merge ou pousse la branche.

4. Workflows — Comparaison detaillee

Git Flow

main ●──────────────────────────────●───────● \ / merge | develop ●───●───●───●───●───●──●──● ● \ / \ | feature/x ●───● \ | \ | release/1.0 ●───● | | hotfix/y ●───●
BrancheRoleDuree de vie
mainCode en production, tague a chaque releasePermanente
developIntegration des features, base pour les branches featurePermanente
feature/*Developpement d'une fonctionnaliteJours / semaines
release/*Preparation d'une release (bug fixes, docs)Quelques jours
hotfix/*Correctif urgent en productionHeures / jours

Ideal pour : logiciels versiones, releases planifiees, equipes structurees.

Outils : Extension git-flow (automatise la creation/fermeture des branches).

# Installation de git-flow et utilisation
git flow init
git flow feature start login
git flow feature finish login
git flow release start 1.0.0
git flow release finish 1.0.0
git flow hotfix start fix-critical
git flow hotfix finish fix-critical

GitHub Flow

main ●───●───●───●───●───●───●───●───● \ ↑PR \ ↑PR \ ↑PR feature/a ●──● │ │ │ │ feature/b ●──● │ │ fix/bug-42 ●──●

Le workflow le plus simple : main + feature branches + Pull Requests. Pas de branche develop, pas de branches release.

  1. Creer une branche depuis main
  2. Faire des commits
  3. Ouvrir une Pull Request
  4. Revue de code par les pairs
  5. Merge dans main (souvent avec deploiement automatique)

Ideal pour : deploiement continu, applications web, equipes agiles.

Trunk-Based Development

main ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─● ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ petits commits frequents (+ feature flags)

Tout le monde commite directement sur main (ou des branches de tres courte duree, < 1 jour). Les fonctionnalites inachevees sont gerees par des feature flags.

Ideal pour : equipes experimentees, CI/CD mature, Google/Facebook-style.

5. Resolution de conflits

Pourquoi les conflits arrivent ?

Un conflit se produit quand deux branches modifient les memes lignes du meme fichier de maniere differente. Git ne peut pas choisir automatiquement quelle version garder.

main ●───●──── modifie ligne 42 ────● \ ↑ CONFLIT! feature/login ●── modifie aussi ligne 42 ──●

Marqueurs de conflit

// Code avant le conflit (OK)
public string Validate(string input)
{
<<<<<<< HEAD
    // Code de la branche actuelle (main)
    return input.Trim().ToLower();
=======
    // Code de la branche entrante (feature/login)
    return input.Trim().ToUpper();
>>>>>>> feature/login
}

Resolution en CLI

# 1. Tenter le merge
git merge feature/login
# CONFLICT (content): Merge conflict in src/Validator.cs

# 2. Voir les fichiers en conflit
git status

# 3. Ouvrir et editer les fichiers en conflit
#    Supprimer les marqueurs, garder le code voulu

# 4. Marquer comme resolu
git add src/Validator.cs

# 5. Finaliser le merge
git commit

# Alternative : annuler le merge
git merge --abort

Resolution dans Fork

Fork propose un outil de merge visuel a 3 panneaux :

  • Panneau gauche (Mine) : votre version (branche actuelle)
  • Panneau droit (Theirs) : la version entrante (branche a fusionner)
  • Panneau central (Base) : l'ancetre commun
  • Panneau bas (Result) : le resultat final que vous construisez

Vous pouvez cliquer sur les fleches pour choisir quelle version garder, ou editer directement le resultat.

Minimiser les conflits

Conseils pour eviter les conflits :
  • Communiquez avec votre equipe sur qui modifie quoi
  • Faites git pull regulierement
  • Gardez vos branches courtes (quelques jours max)
  • Gardez vos Pull Requests petites (300 lignes max)
  • Decoupez les gros fichiers en modules plus petits
  • Utilisez un formateur de code (moins de changements de style)

6. Utilisation avancee

Rebase — Reecrire l'historique

git rebase "replante" vos commits sur une nouvelle base, creant un historique lineaire.

Avant le rebase

main ●───●───●───● \ feature ●───●───●

Apres git rebase main

main ●───●───●───● \ feature ●'──●'──●' (nouveaux SHA, meme contenu) 
# Rebaser la branche courante sur main
git rebase main

# Rebase interactif (squash, edit, reorder, drop)
git rebase -i HEAD~3

# Options du rebase interactif :
# pick   = garder le commit tel quel
# squash = fusionner avec le commit precedent
# fixup  = comme squash mais jeter le message
# edit   = s'arreter pour modifier le commit
# drop   = supprimer le commit
# reword = changer le message

# Annuler un rebase en cours
git rebase --abort

# Continuer apres avoir resolu un conflit
git rebase --continue

Merge vs Rebase

CritereMergeRebase
HistoriquePreserve la chronologie reelleCree un historique lineaire
CommitsAjoute un merge commitPas de commit supplementaire
SHAConservesModifies (nouveaux SHA)
SecuriteSurRisque si branche partagee
LisibilitePeut etre complexePropre et lineaire
REGLE D'OR : Ne jamais rebaser une branche publique/partagee ! Le rebase reecrit les SHA — si d'autres personnes travaillent sur la meme branche, cela causera des conflits impossibles. Rebasez uniquement vos branches locales et personnelles.

Fork Clic droit sur un commit → Interactive Rebase.... Fork offre une interface drag-and-drop pour reordonner, squasher et supprimer des commits.

Cherry-pick — Selectionner des commits

git cherry-pick copie un commit specifique d'une branche vers une autre, sans fusionner toute la branche. 

# Appliquer un seul commit
git cherry-pick abc123f

# Appliquer plusieurs commits
git cherry-pick abc123f def456a

# Appliquer une plage de commits
git cherry-pick abc123f..def456a

# Cherry-pick sans commiter (utile pour combiner)
git cherry-pick --no-commit abc123f

# Annuler un cherry-pick en cours
git cherry-pick --abort
Cas d'usage typique : Backporter un correctif de main vers une branche release/1.x sans fusionner toutes les nouvelles fonctionnalites.

Fork Clic droit sur le commit dans le graphe → Cherry-pick Commit....

Stash — Mettre de cote temporairement

git stash sauvegarde vos modifications en cours sans commiter, pour pouvoir changer de branche proprement. 

# Stasher les modifications
git stash

# Stasher avec un message descriptif
git stash push -m "WIP: formulaire de login"

# Stasher en incluant les fichiers non suivis
git stash -u

# Lister les stashes
git stash list

# Restaurer le dernier stash ET le supprimer
git stash pop

# Restaurer le dernier stash SANS le supprimer
git stash apply

# Restaurer un stash specifique
git stash apply stash@{2}

# Voir le contenu d'un stash
git stash show -p stash@{0}

# Supprimer un stash
git stash drop stash@{0}

# Supprimer tous les stashes
git stash clear

Fork Menu Repository → Stash.... Les stashes apparaissent dans la section Stashes de la sidebar gauche. Clic droit pour appliquer, supprimer ou voir le contenu.

Bisect — Trouver le commit fautif

git bisect effectue une recherche dichotomique dans l'historique pour trouver le commit qui a introduit un bug.

Historique: ●──●──●──●──●──●──●──●──●──● ✓ ✓ ✓ ? ? ? ? ? ✗ ✗ good ↑ bad bisect trouve le coupable ! 
# 1. Demarrer bisect
git bisect start

# 2. Marquer le commit actuel comme mauvais
git bisect bad

# 3. Marquer un commit connu comme bon
git bisect good v1.0

# 4. Git checkout un commit au milieu.
#    Testez, puis indiquez :
git bisect good   # si ca marche
git bisect bad    # si c'est casse

# 5. Repetez jusqu'a trouver le commit fautif

# 6. Terminer bisect
git bisect reset

# Automatiser avec un script de test :
git bisect run npm test
Complexite O(log n) : Avec bisect, trouver le commit fautif parmi 1000 commits ne necessite que ~10 etapes (2^10 = 1024).

Reflog — Le filet de securite

Le reflog enregistre tous les mouvements de HEAD, meme ceux que git log ne montre pas (rebase, reset, amend...). C'est votre dernier recours pour recuperer du travail perdu. 

# Voir l'historique complet de HEAD
git reflog

# Exemple de sortie :
# abc123f HEAD@{0}: commit: feat: ajouter login
# def456a HEAD@{1}: rebase: updating HEAD
# 789bcd0 HEAD@{2}: reset: moving to HEAD~3
# aaa111b HEAD@{3}: commit: feat: formulaire complet

# Revenir a un etat precedent
git checkout HEAD@{5}

# Creer une branche de sauvetage
git branch rescue HEAD@{3}

# Reset dur vers un etat precedent
git reset --hard HEAD@{3}
Rien n'est jamais vraiment perdu dans Git ! Tant que le garbage collector n'a pas tourne (environ 30 jours), vous pouvez recuperer n'importe quel commit via le reflog.

7. Bonnes pratiques

Conventional Commits

La specification Conventional Commits definit un format structure pour les messages de commit, ce qui facilite la generation automatique de changelogs et le versionning semantique. 

# Format
<type>(<scope>): <description>

[corps optionnel]

[footer(s) optionnel(s)]

Exemples concrets

feat: ajouter l'authentification OAuth2
feat(auth): implementer le refresh token
fix: corriger le calcul du total TTC
fix(panier): empecher les quantites negatives
docs: mettre a jour le README
refactor: simplifier la logique de validation
test: ajouter des tests pour le service de paiement
chore: mettre a jour les dependances NuGet
ci: configurer le pipeline GitHub Actions
perf: optimiser la requete de recherche
style: corriger l'indentation dans Program.cs
build: migrer vers .NET 8
revert: annuler "feat: dark mode"

Types de commits

TypeDescriptionExemple
featNouvelle fonctionnaliteAjouter page de login
fixCorrection de bugCorriger le crash au demarrage
docsDocumentation uniquementMettre a jour l'API doc
styleFormatage, points-virgules, etc. (pas de code)Appliquer Prettier
refactorRestructuration sans changer le comportementExtraire une methode
perfAmelioration des performancesCache les resultats SQL
testAjout/modification de testsTests unitaires du panier
buildSysteme de build, dependancesMettre a jour webpack

Atomicite des commits

Un bon commit represente un seul changement logique. Il doit pouvoir etre revert individuellement sans casser d'autres fonctionnalites.

Mauvais : commit fourre-tout

git commit -m "mise a jour"

Contient :
- Fix d'un bug de login
- Ajout d'une page "A propos"
- Mise a jour des dependances
- Correction d'un typo dans le footer
- Changement de couleur du bouton

Bon : commits atomiques

fix(auth): corriger la validation du mot de passe
feat(pages): ajouter la page A propos
chore(deps): mettre a jour les packages NuGet
fix(ui): corriger le typo dans le footer
style(ui): changer la couleur du bouton principal

Chaque commit = 1 changement logique
Regle pratique : Si votre message de commit contient "et", c'est probablement deux commits distincts. Si vous ne pouvez pas decrire le changement en une phrase, c'est trop gros.

Git Hooks — Automatiser les verifications

Les hooks sont des scripts executes automatiquement par Git a certains moments (avant commit, avant push, etc.). Ils vivent dans .git/hooks/.

HookMomentUsage typique
pre-commitAvant le commitLint, formatage, scan de secrets
commit-msgApres ecriture du messageValider les Conventional Commits
pre-pushAvant le pushExecuter les tests
post-mergeApres un mergeInstaller les dependances
post-checkoutApres un checkoutNettoyer les fichiers temporaires

Exemple : pre-commit avec Husky (Node.js)

# Installation
npm install --save-dev husky lint-staged
npx husky init

# .husky/pre-commit
npx lint-staged

# package.json
{
  "lint-staged": {
    "*.{js,ts}": ["eslint --fix", "prettier --write"],
    "*.{json,md}": ["prettier --write"]
  }
}

Exemple : pre-commit pour .NET

#!/bin/sh
# .git/hooks/pre-commit

# Verifier le formatage
dotnet format --verify-no-changes
if [ $? -ne 0 ]; then
    echo "Erreur : formatez votre code avec 'dotnet format'"
    exit 1
fi

# Scanner les secrets
git diff --cached --diff-filter=ACM | grep -iE "(password|secret|api_key|token)\s*=" && {
    echo "ATTENTION : secret potentiel detecte !"
    exit 1
}

8. Fork — Client Git graphique

Presentation

Fork est un client Git rapide et convivial pour Windows et macOS. Il offre une interface visuelle pour toutes les operations Git, avec un accent sur la performance et la simplicite.

Site officiel : git-fork.com — Gratuit pour l'evaluation, licence payante pour un usage continu.

Interface principale

9. Plateformes de depot

GitHub

La plateforme la plus populaire pour l'hebergement de code, acquise par Microsoft en 2018. Reference pour l'open source.

Fonctionnalites principales

  • Pull Requests : Revue de code, discussions, approbations, CODEOWNERS
  • GitHub Actions : CI/CD integre via des workflows YAML
  • Issues & Projects : Gestion de projet Kanban
  • Packages : Registre de packages (npm, NuGet, Docker, Maven...)
  • Codespaces : Environnements de dev cloud
  • Copilot : Assistant IA pour le code
  • GitHub Pages : Hebergement de sites statiques
  • Dependabot : Alertes de securite et mises a jour automatiques
  • CodeQL : Analyse statique de securite (SAST)

Branch Protection Rules

Sur GitHub, vous pouvez proteger des branches avec des regles :

  • Exiger des Pull Request reviews (1 ou 2 approbations)
  • Exiger que les checks CI passent avant le merge
  • Exiger des commits signes
  • Interdire le force push
  • Exiger un historique lineaire
  • Limiter qui peut pousser sur la branche

Exemple GitHub Actions

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v4

    - name: Setup .NET
      uses: actions/setup-dotnet@v4
      with:
        dotnet-version: '8.0.x'

    - name: Restore
      run: dotnet restore

    - name: Build
      run: dotnet build --no-restore

    - name: Test
      run: dotnet test --no-build --verbosity normal

    - name: Security Scan
      run: dotnet list package --vulnerable --include-transitive

GitLab

Plateforme DevSecOps complete, disponible en self-hosted (Community Edition gratuite) ou en cloud (gitlab.com). Connue pour son CI/CD integre, le plus puissant du marche.

Fonctionnalites principales

  • Merge Requests : Equivalent des Pull Requests, avec revue et approbation
  • CI/CD Pipelines : Le point fort — CI/CD natif via .gitlab-ci.yml
  • GitLab Runner : Agent d'execution des pipelines (self-hosted ou partage)
  • Container Registry : Registre Docker integre
  • Security Scanning : SAST, DAST, Dependency Scanning, Container Scanning, Secret Detection — tous integres
  • Issues & Boards : Gestion de projet avec epics et milestones
  • GitLab Pages : Hebergement de sites statiques
  • Web IDE : Editeur de code integre dans le navigateur
  • Auto DevOps : Configuration CI/CD automatique

Exemple .gitlab-ci.yml

# .gitlab-ci.yml
stages:

    - template: Security/SAST.gitlab-ci.yml

Azure DevOps

La plateforme DevOps de Microsoft, fortement integree avec Visual Studio, Azure et l'ecosysteme .NET. Offre des outils complets pour le cycle de vie du logiciel.

Fonctionnalites principales

  • Azure Repos : Hebergement Git avec Pull Requests et branch policies
  • Azure Pipelines : CI/CD multi-plateforme (Windows, Linux, macOS)
  • Azure Boards : Gestion de projet agile (Scrum, Kanban, sprints)
  • Azure Artifacts : Registre de packages (NuGet, npm, Maven, Python)
  • Azure Test Plans : Gestion des tests manuels et automatises
  • Integration Visual Studio : Connexion native depuis l'IDE

Branch Policies (Azure DevOps)

  • Nombre minimum de reviewers
  • Build validation (le pipeline doit reussir)
  • Lier un work item (tracer chaque changement a une tache)
  • Resoudre tous les commentaires avant merge
  • Strategie de merge (merge commit, squash, rebase)
  • Limiter les types de merge autorises

Exemple azure-pipelines.yml

# azure-pipelines.yml

  vmImage: 'ubuntu-latest'

  displayName: 'Restore NuGet packages'

  displayName: 'Build'

- script: dotnet test --configuration $(buildConfiguration) --no-build
  displayName: 'Run Tests'

- task: DotNetCoreCLI@2
  inputs:
    command: 'publish'
    publishWebProjects: true
    arguments: '--configuration $(buildConfiguration) --output $(Build.ArtifactStagingDirectory)'

- task: PublishBuildArtifacts@1
  inputs:
    PathtoPublish: '$(Build.ArtifactStagingDirectory)'
    ArtifactName: 'drop'

11. Securite Git

Commits signes (GPG/SSH)

Signer vos commits prouve cryptographiquement que vous etes l'auteur. Les commits signes affichent un badge "Verified" sur GitHub/GitLab. 

# Configurer la signature GPG
git config --global commit.gpgsign true
git config --global user.signingkey ABCDEF1234567890

# Ou avec une cle SSH (Git 2.34+)
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub

# Verifier les signatures
git log --show-signature

# Signer un tag
git tag -s v1.0.0 -m "Release 1.0.0"

Proteger les secrets

Ne commitez JAMAIS de secrets ! Mots de passe, cles API, tokens, certificats... Une fois dans l'historique Git, un secret est extremement difficile a supprimer completement. 
# Installer gitleaks (outil de detection de secrets)
# https://github.com/gitleaks/gitleaks

# Scanner le repo
gitleaks detect --source .

# Scanner avant chaque commit (pre-commit hook)
gitleaks protect --staged

# Autre outil : git-secrets (AWS)
git secrets --install
git secrets --register-aws
git secrets --scan

SSH vs HTTPS

CritereHTTPSSSH

AuthentificationMot de passe / tokenCle cryptographique

# Generer une cle SSH Ed25519 (recommandee)
ssh-keygen -t ed25519 -C "votre@email.com"

# Ajouter la cle a l'agent SSH
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# Copier la cle publique (a coller dans GitHub/GitLab)
cat ~/.ssh/id_ed25519.pub

# Tester la connexion
ssh -T git@github.com

Git LFS — Large File Storage

Git n'est pas fait pour les gros fichiers binaires (images, videos, modeles 3D...). Git LFS les stocke separement et ne garde qu'un pointeur dans le repo. 

# Installer Git LFS
git lfs install

# Suivre les fichiers par extension
git lfs track "*.psd"
git lfs track "*.mp4"
git lfs track "*.zip"

# Le .gitattributes est mis a jour automatiquement
git add .gitattributes

# Voir les fichiers suivis par LFS
git lfs ls-files

Supprimer des donnees sensibles de l'historique

# Avec git filter-repo (outil recommande)
# Installation : pip install git-filter-repo

# Supprimer un fichier de TOUT l'historique
git filter-repo --path secrets.json --invert-paths

# Remplacer un texte dans tout l'historique
git filter-repo --replace-text expressions.txt

# ATTENTION : cela reecrit TOUT l'historique !
# Tous les collaborateurs devront re-cloner le repo.
Apres avoir nettoye l'historique :
  • Changez immediatement tous les secrets qui ont ete exposes
  • Forcez le push : git push --force-with-lease
  • Demandez a tous les collaborateurs de re-cloner
  • Revoquez les tokens/cles compromis
